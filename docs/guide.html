Loop Engine 使用指南

从第一次启动到合并：每一步看哪里、什么时候需要你。

第一次启动建卡看懂任务卡 处理「待你处理」评审与验收设置 常见问题内置 agent 定义

第一次启动

结论：跑通自检、启动两个进程、接入一个项目，页头角标显示「运行中」就可以建卡了。

Loop Engine 是一块需求看板，后面接着一组分工明确的 AI agent。你在聊天里说清要做什么，它变成一张需求卡；调度器按卡上的流程依次拉起分析、开发、评审、验收等角色，全部关卡通过后自动合并。每一步都有检查，所以便宜的模型也能稳定产出。

  1. 按仓库里的 docs/quickstart.md 装好依赖、配好模型和运行体。
  2. 运行环境自检：.venv/bin/python scripts/doctor.py，输出「硬失败 0 项」即通过。
  3. 启动：./scripts/run_local.sh 同时拉起看板（本页所在的网页服务）和调度器（后台推进卡片的进程）。
  4. 左栏顶部点 + 接入项目：填项目名、仓库路径（可多个）、主干分支和一句话项目目标。
  5. 看页头右上角的角标：显示「运行中」说明调度器在工作。
看板只监听 127.0.0.1:8899，没有登录鉴权。不要把它暴露到局域网或公网。

先认识几个词

词意思
需求卡一条需求。卡上有标题、notes（要做什么）、状态和走到哪一步。
流程卡片要走的一串节点，比如「开发 → 代码审查 → 验收 → 收尾」。
角色一类 agent 工作：需求分析、技术方案、方案评审、开发、代码审查、验收、冲突解决。
闸门能让卡片停下的检查：工具审批、评审结论、收尾校验、需要你拍板的提问。
运行体实际跑 agent 的命令行工具：kimi、opencode、claude-code、codex。
worktree每张卡独立的代码副本和分支，开发不碰你的主工作区。
产物agent 写下的文件：分析报告、方案、自测报告、评审意见、result.json 等。
need_confirmagent 或调度器需要你决定时发出的提问，会出现在「待你处理」。

建卡

结论：在聊天里说清需求，确认后落卡；新卡默认「暂缓」，改成「待开发」才会开工。

  1. 点「+ 新建」（或按 N，或点项目名旁的 +），打开该项目的建卡聊天。
  2. 用对话描述需求。agent 整理出标题和 notes 草稿，你预览后确认建卡。可以附上本机 HTML 原型作参考（粘贴、拖拽或点「参考文件」）。
  3. 新卡默认暂缓。想让它开始开发，把状态改成待开发。

聊天用不了时：展开聊天上方的「直接填表」，填标题、项目、需求详情和状态即可建卡。当前运行体起不了聊天（没装、或不支持聊天会话）时，表单会自动展开，聊天区也会提示去「设置 → 模型设置」改哪里。

notes 怎么写：只写要做什么——目标、范围、验收标准、参考资料；不写讨论过程。排除项写成「不提供：X、Y」。notes 会进入每个角色的提示词，写清验收标准是减少打回最有效的办法。

  • 多仓库项目可写 repos: 仓库A, 仓库B 指定涉及的仓库。
  • 写 timeout: 120 调整单次运行时限（分钟，15–480，默认 240）。

需求助手

每张卡的会话列表顶部都有「需求助手」入口，任何状态都能用。它是针对这张卡的独立对话：问进度、解释产物、改 notes、把暂缓改成待开发。默认只读，只有你明确要求时才写。

看懂任务卡

结论：状态告诉你卡在哪个阶段，顶部进度条告诉你走到流程哪一步；看到橙色，就是在等你决定。

卡片状态

暂缓 later ──(改为 open)──▶ 待开发 open ──(调度器捞起)──▶ 进行中 doing ──▶ 已完成 done
不做了：任何未完成的卡 ──▶ 已废弃 dropped
状态名称含义
later暂缓只记录，不开发。新建的卡默认在这里；改成 open 才进入自动开发。
open待开发调度器只捞这个状态的卡。卡片静置约 1 分钟没人编辑后被拉起。
doing进行中有 agent 在跑；等你回答或正在合并时也停在这里。
done已完成流程走完并已合并（或已推送分支）。
dropped已废弃不做了。只有 later / open / dropped 的卡可以删除。
agent 运行失败（崩溃、超时、没写结果文件）会自动重试 1 次；仍失败，卡片转为暂缓，原因写在卡片摘要里。修好后改回 open 即可重跑。

顶部进度条

开跑过的卡片顶部有一条细线，按这张卡的流程分段：第一段是需求分析，后面每段对应一个流程节点（收尾不单独占段）。

  • 亮色段：已完成的步骤。已完成的卡整条点亮。
  • 呼吸的段：正在进行的步骤。
  • 橙色段：这一步卡住了，在等你决定（有待确认的问题、合并受阻、或开跑后被停成暂缓）。整个看板里，橙色只用来表示「需要你决定」。
  • 还没开跑的暂缓 / 待开发卡不显示进度条。鼠标悬停可以看到完整步骤和当前位置。

流程与角色

卡片被捞起后，先由需求分析（analysis）读需求和代码，推荐一条流程并列出涉及的仓库，之后按流程逐个节点推进：

流程节点适合
quick 快速开发 → 收尾文案、配置值等极小改动。改到项目声明的高风险路径会自动升级为标准流程。
standard 标准开发 → 代码审查 → 验收 → 收尾方案一眼可定的常规改动。
heavy 复杂技术方案 → 方案评审 → 开发 → 代码审查 → 验收 → 收尾需要设计取舍、跨仓库或高风险的改动。分析没给出合法推荐时也走这条。
角色做什么权限
analysis 需求分析调研需求与代码，写 analysis.md，推荐流程和仓库只读
tech 技术方案写技术设计 tech.md只读
tech_review 方案评审审技术方案，给出 pass / reject只读
dev 需求开发在 worktree 里改代码、自测、提交，写 self-test.md可写本卡 worktree、可执行命令
code_review 代码审查审本次 diff，给出 pass / reject只读
accept 测试验证在独立测试实例上跑真实链路，写 accept.md可跑测试，不能改源码或提交
merge_resolve 冲突解决合并冲突时自动拉起，尝试解决冲突受限 git 命令

流程、角色名和模型都来自仓库根目录的 flows.json 与 prompts/*.md；本页最后的「内置 agent 定义」按当前配置实时显示。

产物、会话与上下文

  • 产物目录：~/.req-board/artifacts/<项目>/req-<编号>/，存放 analysis.md、tech.md、self-test.md、code_review.md、accept.md 等。它不在任何仓库里，清理分支也不会丢。卡片详情的「产物」行可以直接点开。
  • 结果文件：每个角色结束前写 result.json（status 为 done / blocked / need_confirm，外加摘要和问题），调度器据此推进卡片。agent 声明的遗留待办（todos）会显示在完成通知和卡片摘要里。
  • 会话：卡片下方列出这张卡的所有 agent 会话。点开一条，右栏实时显示消息、思考、工具调用和 diff。
  • 插话 / 续跑：在会话下方的聊天框发消息，调度器会恢复该会话并把你的话交给 agent。人工续跑一律走这个聊天框。
  • 会话状态行：聊天框上方的一行字说明会话是否活着。绿色在工作；琥珀色表示响应偏慢；红色表示疑似卡死，此时会出现「重启调度器」入口。
  • 「上下文」页签：卡片详情里与「概要」并列。按角色和轮次列出每次会话实际收到的提示词分层（平台规则、角色模板、项目约定、技能、本卡数据）、用的模型和运行体，以及和上一轮相比改了什么。想知道 agent 为什么这么做，先看这里。

处理「待你处理」

结论：页头「待你处理」有数字，就点开逐条处理；点一行会直接打开那张卡。

你会看到意思怎么处理
有一个问题需要你确认agent 主动提问，或需要你确认推荐流程在卡片右栏回答，或点确认按钮（见下文）
评审多次打回，需要人工决定同一评审节点第 4 次仍未通过看每轮打回要点，放行或再打回一轮
收尾校验需要你裁决agent 报完成，但收尾校验不过，且申请了豁免「豁免完成」或「退回待开发」
合并受阻，请检查冲突或 Git 身份合并冲突没能自动解决，或本机没有 git 提交身份按提示修好后「重试合并」，或「人工接管」
等待外部角色提交产物项目把某个角色交给外部 agent 负责外部写好产物后，把卡指向下一节点并改回待开发
调度器异常调度器没有正常上报心跳见下文「页头角标与调度器健康」

回答 agent 的提问

需要人拍板时，卡片停在 doing，顶部进度条当前段变橙，详情里显示待确认的问题（通常附带 agent 的倾向建议）。

  • 在看板上回答：打开卡片，在右栏聊天框输入答复，或点卡片上的确认按钮。答复会交给 agent 续跑，同时记进卡片摘要，之后的会话也看得到，不会重复问。
  • 在飞书里回答（可选）：回复 y 编号 [补充说明] 同意，n 编号 原因 否决。网页按钮与飞书 y/n 走同一套逻辑。

回复格式

意图格式说明
同意 / 继续y 116 [说明] 或 同意 116 [说明]编号前可带 #；说明会交给继续跑的 agent
否决 / 退回n 116 原因 或 拒绝 116 原因原因写进卡片摘要和时间线，建议写明
  • 只识别 y / yes / 同意 与 n / no / 拒绝 开头的回复，其它内容不触发流转。
  • 编号要用问题所属卡片的编号。编号和问题对不上时，回复会被拒绝、不改动任何卡，按提示里的编号重发即可。

飞书回复与状态流转

待确认类型何时出现回复 y（或网页「同意」类按钮）回复 n（或网页「退回」类按钮）
需要确认
need_confirm		 agent 提问；评审第 4 次未通过；需要确认推荐流程 卡保持 doing，答复注入 agent 后续跑；评审超限 = 放行到下一节点；流程确认 = 采纳推荐流程 卡退回 open，约 1 分钟后从当前节点重跑（原因交给 agent）；评审超限 = 再打回修一轮；流程确认 = 转暂缓由人工处理
合并冲突
merge_conflict		 收尾合并冲突，且冲突解决角色没能解决 「重试合并」：成功 → done；仍冲突 → 继续等待 「人工接管」：卡转暂缓，分支和 worktree 保留
评审打回
verdict: "reject"		 方案评审或代码审查不通过 前 3 次自动退回上一节点重做，不需要你回复；第 4 次转为上面的「需要确认」
收尾校验豁免
need_confirm		 agent 报完成，但收尾校验不过（如没有代码变更），且 agent 申请了豁免（waive_gate） 「豁免完成」：留痕后直接 done 「退回待开发」：卡退回 open 重跑；原因以 later 开头则转暂缓
会让卡变成暂缓的回复只有三种：合并冲突时回 n、豁免时回 n 编号 later …、否决推荐流程。其余 n 都只是退回 open，稍后自动重跑。agent 反复追问时，网页上的「停止追问转暂缓」按钮可以直接让它停下。

飞书聊天建卡与看板助手（可选）

接了飞书机器人后，私聊机器人的普通文字由跨项目的看板助手回答：查项目、需求卡、服务状态，或确认项目后建卡。回答里的卡号和状态都来自服务端数据，查不到会直说。另有四项能力需要在「设置 → 通知渠道 → 飞书机器人 → 看板助手能力」里逐项开启，四项默认关闭：

  1. 代码只读分析：跨项目读文件、检索代码，结论附文件与行号；
  2. 状态变更：仅支持把卡从暂缓改为待开发；
  3. 需求卡清单卡片：按项目发送卡片清单，太长会自动分页；
  4. 代码拉取与提交：先指定项目，拉取当前分支最新代码；有冲突时暂停并给出选项；提交先预览，你确认后下一轮才真正提交，不 push、不切换分支。
指令 / 消息效果
确认建卡落卡：草稿生成后回复它，调用 /api/chat/<id>/confirm 建卡（默认暂缓）。还没有草稿时只提示「还没有草稿」。
结束建卡结束当前建卡会话。
新建建卡关闭当前会话，下一条消息重新选择项目开始建卡。
群聊消息只处理 @机器人 的文字和图文消息，交给看板助手，回复发回该群；群聊不参与 y/n 和建卡。
图片 / 文档链接作为附件交给助手或建卡会话（单文件 ≤20MB，每轮最多 5 个）。

匹配规则（整行全等）：三条建卡指令去掉首尾空白和标点后必须与指令完全相同才生效，并且只在有进行中的建卡会话时生效；句子里顺带提到「确认建卡」不会触发。y/n 回复的优先级高于这些指令。

建卡会话和看板助手可以跑在 kimi 或 opencode 上，两者都经过运行体认证套件验证（见「运行体」）。

评审与验收

结论：评审不过会自动打回重做，第 4 次才交给你；验收在独立测试实例上跑真实链路；全部通过后自动合并。

  • 评审角色（方案评审、代码审查）给出 pass 就进入下一节点；给出 reject 就把卡退回上一个产出节点，并把评审意见交给它重做。
  • 同一个评审节点第 1–3 次打回自动重做。第 3 次时，如果项目配置了 escalation_model，会先给作者角色换更强的模型。
  • 第 4 次仍未通过，转成 need_confirm 交给你裁决，问题里附有每一轮的打回要点：回 y 放行，回 n 再打回修一轮。
  • 评审结论缺失或格式不对，一律按打回处理，不会直接合并。评审意见只存在评审记录和产物里，不进卡片 notes。

验收

验收角色（accept）按 notes 里的验收标准，在独立测试实例上跑真实链路，结果写进 accept.md。它可以跑测试和命令，但不能改源码或提交。涉及浏览器的改动需要真开浏览器验证；工具不可用时会写明「未覆盖项」，留给你人工验收。测试实例怎么起，由项目的 .loop/project.json 声明（见「项目配置指引」页签）。

worktree、分支与合并

  • 卡片第一次被拉起时，调度器为项目的每个仓库从主干建一个 worktree（位于 ~/.req-board/worktrees/），分支名 f-YYYYMMDD-<编号>。本卡所有角色都在这里工作，主工作区不受影响。
  • 流程走到收尾时，调度器先做收尾校验：开发节点必须有代码变更，其它节点必须有产物。通过后用 --no-ff 合并回主干，清理 worktree 与分支。
  • 走 PR / CI 的仓库可在 projects.json 配 branch_only: true：只把分支推到远端，不在本地合并。git_sync 可配开工前拉取、完成后推送；不配置就完全不碰远端。纯本地仓库（没有远端）是正常形态。
  • 合并冲突时，先自动拉起冲突解决角色；解决不了就进「待你处理」。本机没有 git 提交身份时不会误判成冲突，会提示你怎么配。
  • 项目配置了 restart 配方的服务，卡片完成时由调度器自动重启并检查就绪。

设置

结论：大多数设置在左栏底部齿轮打开的设置抽屉里；改 flows.json、.env 或 prompts/ 默认文件需要重启看板和调度器，抽屉里的提示词和技能改动下一次拉起会话就生效。

设置抽屉有五个页签：全局信息、模型设置、通知渠道、提示词、技能库。

接入与管理项目（左栏）

左栏顶部 + 接入新项目；项目目标会提供给需求分析角色。项目行悬停可编辑或移除接入；移除只是不再显示，历史卡片保留；还有进行中的卡时不能移除。

模型

  • 模型设置页签：编辑 kimi 运行体读取的 config.toml（位于 harness home，默认 ~/.kimi-code-deepseek）：厂商、API Key、模型别名、默认模型。保存前会校验，失败不写入。
  • 项目级调参（项目信息条最右侧）：按「项目 × 角色」指定模型，下一张卡生效，无需重启。

角色模型按以下顺序取第一个有值的：

  1. 项目级（projects.json 的 models，即上面的调参）；
  2. 角色级（flows.json 的 roles.<角色>.model）；
  3. 环境变量 KIMI_MODEL_<角色大写>；
  4. 全局 KIMI_MODEL（默认 deepseek/v4.1-flash）。

运行体

每个角色通过 ACP（Agent Client Protocol）驱动一个运行体子进程。每次工具调用都由 Loop Engine 按角色审批，只读角色改不了代码。

运行体流水线角色建卡与助手说明
kimi（默认）全部支持kimi-code CLI（kimi acp），模型在 harness home 的 config.toml 配置

{"my-project": {"paths": ["/path/to/repo"], "runtimes": {"dev": "claude-code"}}}

提示词

每次发给 agent 的提示词按层拼成：平台规则 → 角色模板 → 项目约定 → 条件说明 → 技能 → 本卡数据。「提示词」页签列出引擎自带的每一段文案：

  • 编辑后保存，写进不进 git 的 prompts.local/，下一次拉起会话就生效，无需重启。
  • 「恢复默认」= 删除本机覆盖。升级后默认文本变了，该项标「默认已更新」，由你决定采用新默认还是保留覆盖。
  • 调度器要解析的句子（如结果契约）被锁定，删改会被拒绝保存。项目约定部分只读，改它要去项目仓库。
  • 「在注入预览里看效果」：选项目和角色（可再选一张卡），用和调度器同一个编译器预览完整提示词，不拉会话、不花 token。

技能库

技能是可复用的操作步骤（比如「改 UI 前先截图」），按角色挂载。「技能库」页签可以新建、编辑、废弃技能，并查看近 30 天加载次数。

  • 激活方式：始终（角色匹配就放进提示词）、自动（命中路径或关键词时放进）、按需（只列在目录里，agent 自己取）、手动（卡片 notes 点名才加载）。
  • 角色 × 技能矩阵：点格子循环切换某个角色对该技能的激活方式。
  • 新建的技能是草稿，改成「启用」之前不会进入任何真实会话。本机修改写进 prompts.local/skills/，项目仓库自带的技能只读。

通知渠道

  • 飞书机器人（可选）：App ID / App Secret、测试连通性、看板助手能力开关。改凭据后需重启调度器。支持双向：推送通知，也能在飞书里回复 y/n、建卡。
  • Webhook / Slack：只发出站通知。可启用、发送测试、按事件订阅（待确认、完成、失败、阻塞、合并冲突），保存即生效。

外观

「全局信息」页签底部的「外观」里可以打开动态背景。默认关闭（静态底纹，更省电），切换后刷新页面生效。明暗主题用页面上的明暗切换按钮，本指南与看板共用同一偏好。

时限与预算

单次运行默认最长 240 分钟；工具调用步数上限默认 dev 1000、accept 与 code_review 500、merge_resolve 200、其余 400。到上限会被截停并给一轮收尾机会。可在 projects.json 的 budgets 按角色调整，如 {"dev": {"max_steps": 800, "max_minutes": 120}}。

项目约定 .loop/project.json

每个接入的仓库可以在根目录放 .loop/project.json，声明测试命令、测试实例启停命令、给各角色看的指引和技能、高风险路径。写法与示例见「项目配置指引」页签。

常见问题

现象处理
卡片一直不被捞起确认状态是 open、编辑后已静置 1 分钟以上、卡片项目名与 projects.json 的键完全一致，并且页头角标是「运行中」。
聊天建卡起不来按聊天区的提示去「设置 → 模型设置」检查运行体和模型；急用时展开「直接填表」先把卡建上。
会话起不来 / 模型报错 / 401检查 harness home 的 config.toml 里的 API Key 与模型名，并与 KIMI_MODEL 对齐；找不到 kimi 时设置 KIMI_BIN。用 opencode 时检查 LOOP_OPENAI_* 变量。
agent 报目录未被信任用同一个 harness home 在该目录交互运行一次 kimi 并接受信任：KIMI_CODE_HOME=~/.kimi-code-deepseek kimi。
worktree 创建失败项目路径必须是有提交、有主干分支的 git 仓库；必要时在项目里配置 base_branch。
合并失败，提示没有 git 身份在该仓库配置 user.name 与 user.email 后「重试合并」；scripts/doctor.py 会提前检查。
浏览器验证提示没有工具在 harness home 的 mcp.json 配置名为 playwright 的 MCP server（名字必须一致）。
改了 flows.json / prompts/ 不生效这两处没有热加载：重启看板与调度器（前台直跑时 Ctrl-C 后重跑 scripts/run_local.sh）。设置抽屉里保存的提示词覆盖不需要重启。
卡片转为暂缓、摘要里有失败原因按原因修正后把卡改回 open；或在会话聊天框里给出指示续跑。

页头角标与调度器健康

页头角标只回答一个问题：引擎在不在跑。绿色「运行中」= 调度器心跳正常；红色 = 心跳过期或调度器没有上报，卡片不会被领取。飞书是可选渠道：没配置或显式停用都是正常状态，只写在悬浮说明里；配置了但连不上才会在角标后面注明。

调度器每轮轮询（约 15 秒）更新心跳文件 data/dispatcher_heartbeat.json，超过 180 秒没有更新就视为「心跳过期」。它手上的待办（待确认问题、重试计数、worktree 基线等）记在 data/dispatcher_state.json。

  • 环境自检：.venv/bin/python scripts/doctor.py（退出码 0 且输出「硬失败 0 项」即通过）。
  • 重启调度器：scripts/dispatcher-restart.sh <pid>；重启前先确认没有正在跑的 agent。
  • 更多细节见仓库 docs/quickstart.md 与 docs/dispatcher.md。

应用架构：看板、调度器、ACP 客户端、运行体和各类存储如何连接。调用链路：一张卡从建卡到合并经过的每一步与每道闸门。图内可缩放、搜索、切换明暗；源文件在 docs/diagrams/src/*.json。

项目配置指引：让 agent 按你项目的规则开发

接入一个新项目时，把「项目已有能力、扩展方式、业务边界、怎么验证」写进该项目的仓库，每张卡只写本次要做什么和验收标准。不需要改 Loop Engine 的全局角色模板。下面用一个假设的 ERP 平台新增模块做示例，路径、模块名和脚本都要换成你项目的真实内容。

内容放哪层接入顺序 清单示例Guide 示例 Skill 示例需求卡示例 各角色读什么续跑与规则更新 AGENTS.md 与分层改提示词 启动前核对

一、内容放在哪一层

长期事实和约束写 Guide，可复用的操作步骤写 Skill，本次目标和验收写卡片。

层写在哪里写什么
通用协议引擎内置（公共尾段、角色能力）结果契约、工具权限、写入边界、进程安全。接入项目时不用动。
角色职责prompts/<角色>.md、flows.json各角色的输入、输出和职责，跨项目复用，不写具体项目内容。
项目约定仓库的 AGENTS.md、.loop/project.json、.loop/guides/*.md项目定位、框架与模块地图、业务术语、数据红线、测试与部署方式。
场景技能.loop/skills/<名>.md，在清单 skills.<角色> 挂载反复使用的检查步骤和证据格式。
本次需求卡片 title、notes业务行为、范围、验收场景、资料路径。
  • 只把文件放进 .loop/guides/ 不会自动加载，必须在清单里登记。
  • Guide 按 roles 过滤，省略表示所有角色都看；Skill 按角色挂载。
  • 每份 Guide / Skill 注入上限 4000 字符，超出部分截掉。关键规则放前面，长资料放仓库文档并给出路径。
  • AGENTS.md 不会全文注入，提示词里只提示 agent 先去读它，所以它应保持短小。

二、接入顺序

  1. 核对基线：确认仓库路径、远端、主干分支正确，在项目管理里登记 base_branch。
  2. 盘点框架：找一个相近且已上线的模块，记下分层、路由、菜单、权限、迁移等真实入口。
  3. 写稳定规则：全员适用的业务与扩展边界写进 Guide，短红线和导航写进 AGENTS.md，在清单里登记命令和指引。
  4. 验证环境：在隔离测试库上确认安装、启动、健康检查和测试能跑通。
  5. 写第一张卡：按下文格式写目标与验收，先用一张范围明确的卡验证整条链路。
erp-platform/
  AGENTS.md                         # 短规则与资料索引
  .loop/project.json                # 命令、Guide 角色、Skill 角色
  .loop/guides/business.md           # 业务术语与长期约束
  .loop/guides/framework.md          # 已有能力、扩展点、参考模块
  .loop/guides/validation.md         # 验收与回归标准
  .loop/guides/instance.md           # 隔离实例、测试库、部署生效方式

在仓库的 .loop/project.json 登记以下内容。示例里的 scripts/test*.sh 需要你的项目自己实现；<端口> 只是给 agent 看的占位符。

四、Guide：写事实、边界和证据入口

每份 Guide 开头写适用范围和核对基线。规则要具体到「复用什么、去哪里找、什么情况停下来」，不写「遵循最佳实践」这类无法验收的话。

AGENTS.md 短规则示例
# ERP 平台
在已有平台内增加模块；框架能力与扩展入口见 .loop/guides/framework.md。
业务术语见 .loop/guides/business.md，验收标准见 .loop/guides/validation.md。
新增模块沿用现有分层、组件、权限与租户机制，参考已核对的采购订单模块。
不直接编辑框架核心、第三方依赖或生成目录；确需修改先报告影响并请求确认。
不连接或改写生产数据。数据库变更使用增量迁移，不删除重建已有表。
只在本卡 worktree 内开发，不自行 push、合并主干或改卡片状态。
权限、租户、金额、工作流语义冲突时报告 need_confirm，列明冲突出处。
.loop/guides/business.md 业务边界示例
# 业务边界（适用于 erp-platform 全部模块）
基线：填写实际核对的分支与提交；维护时重新核对下列事实。
租户是数据隔离单位；组织是租户内的业务归属，两者不可混用。
模块复用平台现有用户、组织、权限、编号、附件、工作流与审计服务。
采购申请状态与审批动作见 docs/domain/purchase-request.md。
金额精度、币种及舍入规则复用平台现行实现，证据路径填写到真实文件。
不提供：跨租户查询、绕过审批直接生效、自动修改历史单据。
未在需求中定义的取消、撤回、重复提交语义，开发前请求确认。
上述语义须与实际 ERP 核对，示例术语不能直接作为业务事实。
.loop/guides/framework.md 框架扩展约定示例
# 平台扩展约定（适用于 erp-platform）
基线与框架版本：填写实际分支、提交、框架名及已验证版本。
参考模块：采购订单；路径和调用链见 docs/platform/reference-module.md。
模块地图：docs/platform/module-map.md；每项给出真实文件/类/注册入口。
新增模块沿用「页面 → 现有 API 层 → 应用服务 → 数据访问」的既有边界。
菜单、权限点、租户过滤、字典、附件、编号、审批和审计沿用平台公共能力。
不另建登录、权限、审批引擎或并行 UI 组件体系，不直接改第三方依赖。
新增实体用现有基类与隔离规则；新增接口用现有响应、异常及事务约定。
数据库用平台已有迁移机制；说明默认值、历史数据兼容和失败恢复办法。
开发前先定位一个现有端到端实现，以代码证据确认扩展点，不能只凭文档猜接口。
公共能力不能满足本卡时，先写差距、影响面和候选方案，请求确认后再实施。
.loop/guides/validation.md 共享验收标准示例
# 模块验收与回归（适用于 erp-platform）
验收基线：本卡 notes + 已确认需求文档 + 当前项目约定。
验证新增模块的正常路径、异常输入、未授权访问与跨租户访问。
验证重复提交、并发审批与状态冲突；检查事务失败后无部分写入。
核对金额精度、编号、审计记录和历史数据兼容。
回归采购订单及本次触及的公共权限/工作流接口；记录用例与结果。
页面改动在独立实例真开浏览器：菜单 → 列表 → 新建 → 提交 → 审批/驳回。
SQL、API 和页面结果应一致；角色只做其工具能力允许的检查。
记录代码基线、命令、实例地址、样例、预期/实际结果与未覆盖项。
开发在 self-test.md 留证，验收在 accept.md 独立复核；未执行不能写通过。
评审指出偏离哪条约束或哪项验收条件，并附位置与复现方法。
.loop/guides/instance.md 测试环境示例
# 独立测试与生效方式（适用于 erp-platform）
使用清单 instance 命令启动当前 worktree 的实例，先探测端口与进程归属。
测试使用专用测试库和合成租户；不得使用生产连接串或真实客户数据。
连接信息由本机受保护配置提供；Prompt、卡片与仓库只写配置名，不写密钥。
启动脚本必须隔离端口、数据库与文件目录，停止脚本只清理本实例资源。
填写依赖服务、测试账号获取方式、种子数据与 healthcheck 的真实验证步骤。
只重启当前测试实例；共享/生产进程由部署负责人在明确授权后操作。
分别写清后端、前端、迁移及工作流配置何时生效、谁执行、如何验证。
无法启动时记录具体缺项，未覆盖项进入验收报告，不能宣称浏览器验证完成。

五、Skill：可重复使用的方法

Guide 回答「这个项目是什么、必须遵守什么」，Skill 回答「遇到这类任务按什么步骤做」。项目 Skill 会整份替换全局同名 Skill；找不到的 Skill 会被跳过并记日志，首次接入要核对。

.loop/skills/erp-module.md 示例
# ERP 模块扩展检查
1. 读取 AGENTS.md、framework/business/validation 指引和本卡 notes。
2. 对照参考模块定位实体、API、服务、页面、路由、菜单与权限注册入口。
3. 列出「本次新增 / 复用已有 / 不涉及」，附对应文件或接口证据。
4. 核对租户、组织、数据权限、事务、幂等、工作流、审计与迁移兼容性。
5. 开发角色按既有扩展点实现并运行测试；只读角色只查证和报告，不改代码/数据。
6. 用 notes 的每条验收条件对应实现位置与测试证据，标明未执行项。
7. 输出到当前角色规定的产物路径；路径与结果 JSON 契约以运行时注入为准。
遇到未定义业务语义、框架核心改动或权限冲突，报告 need_confirm。

六、需求卡只写本次要做什么

需求卡示例
title：在现有 ERP 平台新增采购申请模块

notes：
目标：支持租户内员工创建采购申请，并使用已有工作流提交审批。
范围：列表、详情、新建、编辑草稿、提交、审批、驳回与查询。
复用：现有用户/组织、权限、编号、附件、工作流及审计能力。
业务规则：仅本人可编辑草稿；提交后不可编辑；驳回后可编辑再提交。
权限：使用平台现有权限注册机制；申请人与审批人按既有组织规则授权。
不提供：跨租户数据共享、库存扣减、付款、历史单据批量导入。
参考：.loop/guides/framework.md；docs/domain/purchase-request.md。
验收：
1. 授权用户可从现有菜单进入模块，创建含两条明细的申请并保存草稿。
2. 提交后走已有工作流；通过/驳回后的状态与审计记录符合需求文档。
3. 未授权角色无法调用接口或操作按钮；另一租户不能查询或修改该申请。
4. 采购订单及本次触及的公共能力回归通过，并提供可复现证据。
生效方式：迁移、后端部署、前端发布分别按项目部署指引执行，由部署负责人触发。
notes 和 summary 会进入每个角色的提示词。不要把评审结论、讨论记录、账号密钥写进去；评审意见留在评审产物里。

八、续跑与规则更新

新会话拿到完整提示词。调度器自动续跑旧会话时，会先把这次要发的内容和该会话上次收到的内容逐项对比：

  • 没有变化：只发简短的续跑提示。
  • 项目约定、条件说明、技能或卡片内容变了：续跑消息前面附「上下文更新」，逐条列出变了什么并附新正文，要求 agent 回读确认。
  • 平台通用约束或角色模板变了：不再续用旧会话，改开新会话（带完整提示词和一段交接说明）。

这套对比只对上线后建立的会话生效；更早的会话、以及看板聊天框里的人工续跑，仍需你在消息里说明改了哪些文件、已确认的目标和剩余工作，并要求 agent 先重读。规则相互冲突时，agent 应报 need_confirm。

九、AGENTS.md 与提示词分层

AGENTS.md 是项目自己的规则文件（很多编码 agent 都认这个文件名）。仓库根放一份写全局约定；某个子目录有特殊约定时，在那个目录再放一份，离改动越近的越优先。

  • Loop Engine 只指路、不内联：「项目约定」层提示 agent 先读仓库根的 AGENTS.md；这张卡涉及的子目录如果有自己的 AGENTS.md，卡片输入里会列出「改 src/api/ 下的文件前先读 src/api/AGENTS.md」。涉及哪些目录，开发前看需求 notes、需求分析和技术方案里写到的路径，审查和验收时看真实 diff。
  • 记录读的是哪一版：每次拉起会话都会记下指向的每份 AGENTS.md 及其内容指纹（读的是 agent 实际所在的 worktree），事后能查清当时的规则版本。自带 AGENTS.md 加载能力的运行体（Codex）只记录、不重复指路。
  • 和 .loop/guides 的分工：AGENTS.md 是人和任何 agent 都会读的短规则；.loop/guides 是 Loop Engine 按角色挑选、直接放进提示词的项目事实（每份 4000 字以内）。同一条事实只写一处。
  • 谁说了算：Loop Engine 平台约束（结果契约、写入边界、进程安全）> 最近的子目录 AGENTS.md > 仓库根 AGENTS.md > 角色模板（仅限命令、端口、路径这类事实）。权限始终由工具白名单强制，任何一层的文字都改变不了。
  • 保持精简：scripts/doctor.py 会检查根和每个子目录 AGENTS.md 的长度，子目录文件大段照抄根文件时也会告警。
  • 在哪看：设置抽屉「提示词」页的项目约定部分（只读）和卡片详情的「上下文」页会列出这些文件（接口 GET /api/prompts 返回同样的数据）。

完整分层（从稳定到多变）：平台约束 → 角色模板 → 项目约定（清单、指引、AGENTS.md 指路）→ 条件说明（如仅推分支、自动重启）→ 常驻技能 → 技能目录 → 本卡数据（标题、notes、上游产物、返工问题清单，用 <card-data> 标出，是数据不是指令）→ 运行参数。前几层跨卡稳定，便于模型缓存。

十、在本机改提示词

发给 agent 的每一段引擎文案都是文件：默认版本随代码在 prompts/，你在设置抽屉「提示词」页保存的修改写进不进 git 的 prompts.local/（目录结构一一对应），编译时有覆盖用覆盖，没有用默认，改完下一次拉起会话就生效、不用重启。「恢复默认」就是删掉覆盖文件。升级 Loop Engine 后默认文本变了，该项会标「默认已更新」，仍用你的覆盖，由你决定是否合并。结果契约等调度器要解析的句子被锁定，删改会被拒绝保存。

十一、第一张卡启动前核对

  • 仓库路径、远端、base_branch 正确；Guide 里写的接口和目录真实存在。
  • 清单是合法 JSON，Guide 与 Skill 文件都存在、名字和角色正确，单文件关键内容不超过 4000 字符。
  • 测试命令能在 worktree 里运行；测试实例的端口、数据库和目录相互隔离；提示词里没有生产凭据。
  • 卡片有范围、排除项、可复现的验收标准和生效方式。
  • 运行 .venv/bin/python scripts/doctor.py 检查项目清单格式。
