三、飞书回复与状态流转

#419 起人工介入只剩「需要确认」（need_confirm）一条通道——通道确认与人工评审两个中间态已取消（新流程不再产生；过渡窗口照存的历史 route/review 待办仍保留消费分支，仅兼容不再新增），回复 y/n 后的变化如下：

确认节点触发时机回复前状态回复 y 后回复 n 后
需要确认
need_confirm		 任意节点 agent 提问（带倾向建议）；评审节点连续 3 轮未通过仍自动打回，第 4 轮仍未通过转人工裁决（附各轮打回要点）；confirm 项目或识别到清单外仓库时确认推荐流程 doing 保持 doing，恢复原会话继续跑，你写的文字作为答复注入给 agent，并追加一行「人工答复（问题：…）：…」到开发总结留档（该字段会进 agent 上下文，会话重开/重试后的新 agent 也能看到这条澄清，不会重复追问）；评审超限场景 = 放行进入下一节点；流程确认场景 = 采纳推荐流程并继续推进 退回 open，原因写入 summary；约 1 分钟后按卡上流程快照的当前节点重跑（原因进历史）；评审超限场景 = 打回前驱节点再修一轮；流程确认场景 = 转人工处理（置 later）

收尾校验豁免
need_confirm（confirm_override）		 agent 报 done 但收尾校验不通过（无代码变更/缺产物等），且 result.json 带 waive_gate 申报豁免（#399，如实现已人工提交 main） doing（待处理，未合并） 豁免完成：summary 红字「机制校验未过，人工确认豁免」留档后直接收口 → done 退回 open（按卡上快照的当前节点重跑）；原因以 later 开头则置 later（暂缓），dev 分支与 worktree 保留
网页端确认按钮
confirmations（#400）		 任一待确认卡在网页端渲染的动作按钮（confirm_override「豁免完成/退回待开发/置暂缓」、超限态「停止追问转暂缓」；合并冲突另有「重试合并 / 人工接管」按钮见上）。历史 review_gate 条目（#419 起不再写入）的三档动作 pass/rework/reject 仅在过渡窗口内保留消费，看板前端不渲染这组按钮 doing（待处理） 与飞书 y 等效：点击即由调度器执行（同状态/通知/留痕），按钮转「已提交待处理」，最长 15s 内生效；「停止追问转暂缓」为网页新增明示出口（飞书无对等指令） 与飞书 n 等效（含 later 前缀语义）；对话类选项点击 = 预填右栏聊天框（可编辑后发送，人工输入恒对话类不触发机制动作）
回复编号与条目内容不一致（#27）：待确认条目的键与内容应同源；万一不一致（键指向的卡与问题实际所属的卡不同），调度器不执行任何状态变更——回复会被拒绝，条目按内容归属归位（目标编号已有待确认项时保留原键、累计到第 3 次清条目转人工），并给你一条说明「回复编号 #X 与待确认条目内容不一致（内容属需求 #Y）」。收到这类提示时请按内容所属的编号重新回复；条目内容所属卡已 done/dropped 时该条目直接清理，需按提示人工处理。

#22 起「飞书多轮聊天建卡」相关回复（与上面 need_confirm 的 y/n 通道并存，优先级低于 y/n）：存在活跃建卡会话时，飞书私聊机器人可多轮对话建卡——未给项目时机器人追问并列出项目名清单，选定后进入建卡讨论（素材/文档链接随消息交给 agent），确认（回复 确认建卡）后经 create_requirement 建卡（默认 later）。

#24 起「飞书看板助手」：飞书私聊的普通文本（非 y/n、非素材、非建卡指令，且无活跃建卡会话）由跨项目常驻「看板助手」接管——可用自然语言查项目 / 需求卡 / 服务状态（调度器心跳、运行中会话、待确认项），也可先确认项目再跨项目建卡。回答中的卡号、数字、状态一律来自服务端只读业务工具，查不到会明确说明、不编造。单条消息只跑一次模型，整轮 90 秒超时（超时回固定提示「这轮没查完，重发一次或到网页看。」并取消本轮）。首条消息仍先回一次连接问候，且问候后继续处理本条（#24 修复了原先把首条消息整条吞掉、不入队也不建卡的问题）。#26 起另有几条增强能力，各由一个开关控制、默认关闭（在网页左下角齿轮「设置 → 飞书机器人」标签页的「看板助手能力」分组里开启，保存即生效；#30 起新增第三条「需求卡清单卡片」，#54 起新增第四条「代码拉取与提交」）：①代码只读分析——在被授权范围内读文件、按模式列文件、按内容检索，数据范围是项目清单里的全部项目（跨项目），结论会引用具体文件与行号；②状态变更——仅支持把已建卡从 暂缓改为待开发（约 1 分钟后会被调度器自动纳入开发流程）。③需求卡清单卡片（#30）——说「把 X 项目的卡清单发我」这类清单诉求时，助手以飞书交互卡片发出该项目需求卡清单：每张需求一个独立区块（编号/标题/中文状态/流程/更新时间），超出单条容量自动分多页发送、不丢卡（超出上限会在末页显式提示还剩多少张）。④代码拉取与提交（#54）——必须先指定项目（多仓库项目还要指定仓库）：先回显当前分支与最新提交，再拉取当前分支最新代码；冲突时暂停并列出冲突文件与四个选项（保留我方/保留对方/手动处理/放弃合并），不强制覆盖、不丢本地改动；提交分两步——先预览变更摘要与目标分支，用户确认后的下一轮才真正提交（不 push、不切换分支）。开关关闭时助手会明确回绝（提示去网页开启），不会静默降级或假装完成。

指令 / 行为匹配与效果
结束建卡释放当前活跃建卡会话（调 /api/chat/<id>/close）。匹配规则（整行全等）：文本 strip() 后去首尾中英文标点（，。！？、；：,.!?;: 与引号括号）再全等比较，不做包含/前缀匹配，且仅在存在活跃建卡会话时生效——「那就确认建卡，结束建卡流程」不含整行全等，按普通消息进入建卡讨论。#24：无活跃建卡会话时只回「当前没有进行中的建卡会话」提示，不启动任何会话（原「任意文本都新建单项目建卡会话」的兜底分支已删除）
新建建卡先关闭当前会话再清本地状态，下次消息重新走项目追问（匹配规则同上）。#24：这是无活跃建卡会话时唯一能显式回到单项目建卡的入口
确认建卡用户侧唯一落卡口令：草稿产出后机器人提示「回复『确认建卡』落卡」，收到即调 /api/chat/<id>/confirm 驱动 create_requirement 建卡（status 默认 later，仅明确要求开发时 open），并把建卡结果回发到飞书。尚无草稿时回复它只会收到「还没有草稿」提示（不调 confirm）；已建卡（created）时提示卡号。匹配规则与上面两条相同（整行全等，仅存在活跃建卡会话时生效）；#24：无活跃建卡会话时只回「还没有草稿」提示，不启动任何会话
普通文本（无活跃建卡会话）#24 起进入「看板助手」：非 y/n、非素材、非上述三条指令的任意文本由跨项目看板助手接管（自然语言查项目/卡/服务状态，或确认项目后跨项目建卡）；#26 起另支持只读代码分析（跨项目，引用文件与行号）与状态变更（仅 暂缓 → 待开发），#30 起支持需求卡清单卡片（按项目发交互卡片清单，超长自动分页），#54 起支持按项目拉取最新代码、处理合并冲突与预览后提交（仅限项目清单内项目，不 push、不切换分支）；各能力由网页左下角齿轮「设置 → 飞书机器人」标签页的「看板助手能力」开关控制、默认关闭
群聊消息#22 行为变化 2：群 @ 进看板助手：处理 @机器人 的文本与图文消息（文本剥离 @_user_N 占位符后交给看板助手，回复发回该群）；图文混排（文字+粘贴截图，飞书报文 msg_type=post）按正文+图片一起交给助手，图片作本轮附件（可被识图）；不写 state["chat_id"]（私聊通知通道保持唯一）、不问候、不走 y/n 与建卡链路。前提：应用只订阅「群组中@机器人消息」事件（未开 im:message.group_msg）
素材与链接图片/文档（docx/wiki 链接）随消息交给 agent：素材按句柄延迟下载后落盘，docx 抓正文、wiki 两步解析（仅一层）、普通 http(s) 链接抓正文，失败降级为仅传原链接 + 提示。素材类型限制 = 飞书支持图片/文档白名单（FEISHU_MATERIAL_EXTS），单文件 ≤20MB、单轮 ≤5（超 agent 单文件读取上限 1MB 只提示不阻断）。#44：无活跃旧建卡会话时图片/文件不再新建建卡会话追问项目，而是下载后作为看板助手本轮附件（图片可被识图，文本类正文内联、其余给绝对路径）；只有存在活跃旧建卡会话时素材才照旧进建卡 pending
#44 正在输入反馈：飞书没有原生 typing 接口，机器人改用用户消息上的 Typing 表情表示「正在处理」——只对真正入队的看板助手消息、旧建卡文本与素材消息贴，处理完自动撤除（撤回的是自己贴的那一枚）；建卡指令（结束/新建/确认建卡）与 y/n 确认不贴。表情失败只记日志、不影响回复；应用需在飞书开放平台开通 im:message.reactions:write_only（或 im:message），未开通时只是没有表情。贴上/撤回时可能收到「机器人回应了你的消息」提示。
#24 消息优先级（从高到低）：非 text/post/file/image（贴纸等）忽略且留日志 → 非私聊群聊：@ 文本/图文（post 的正文与图片一起）/图片 → 看板助手（不写 state["chat_id"]、不问候、不走 y/n 与建卡；图片作本轮附件）→ file/image 素材分支（#44：无活跃旧建卡会话时进看板助手当附件，有则照旧进建卡）→ 首条问候（独立「已问候 chat 集合」，同 chat 只问候一次，问候后继续处理本条）→ 文本 y/n 确认 → 有活跃建卡会话则走旧建卡链路 / 无活跃会话时整行「新建建卡」进旧建卡新建 → 其余普通文本进看板助手。y/n 语义不变（仍是文本最高优先级）；相对 #22 的变化：首条消息不再被吞（问候后照常路由），以及无活跃会话的普通文本改由看板助手接管（不再默认新建单项目建卡会话）。
图文消息（msg_type=post）：飞书客户端把「文字 + 粘贴截图」合成一条富文本消息下发，此前不在消息类型白名单内被静默丢弃，表现为「@机器人贴图后没有反应」；现按正文+图片一起进看板助手，图片走素材白名单与 ≤20MB/单轮 ≤5 限制。
会让需求变成 later 的回复有：「自动合并冲突」时的 n、「收尾校验豁免」时 n + later 前缀、「需要确认」中的流程推荐否决，以及历史 review_gate 条目（#419 起不再写入）中的普通 n（n <编号> 转开发 除外，改走复修循环）；其余 n 都只是退回 open，过约 1 分钟会被调度器按卡上流程快照的当前节点重新捞起。
历史遗留：route/review 两个人工中间态已弃用（新流程不再产生），但过渡窗口照存的历史待办仍保留消费分支——route 卡回复 y = 按建议通道继续推进（建议人工收口则直接完成）/ n = 退回 open 重新分析；review 卡回复 y = 通过并推进下一阶段（accept 阶段直接完成）/ n = 打回重做（原因以「需求级」/「reset」开头则退 open 重来）。仅兼容存量，不再新增。

意图格式说明
同意/继续y 116 [原因] 或 同意 116 [原因]编号前可带 #；原因会带给继续跑的 agent
否决/退回n 116 原因 或 拒绝 116 原因原因会写入需求 summary 与时间线，建议必填
转开发复修（历史通道，仅过渡窗口的旧卡）n 116 转开发 [原因]需求保持 doing，原 dev 会话续跑并注入审查反馈（merge_review.md），修复报 done 后重新审查（#411，循环无上限）。#419 起新流程不再产生该待确认条目——评审发现问题由评审 agent 直接报 verdict=reject 自动打回上游开发节点
  • 只识别 y / yes / 同意 和 n / no / 拒绝 开头的回复，其他内容不会触发流转。n 的原因以「转开发」开头时，对代码审查问题（review_gate）触发转开发复修，其余语义不变。
  • 编号必须是问题所属卡的编号：条目键与内容不一致时回复会被拒绝且不改动任何卡（见「三、飞书回复与状态流转」末条说明），请按通知里给出的正确编号重发。
  • 原因可空，但 n 时写明原因有助于后续 agent 按你的意图重跑。
  • 网页端答复同一问题走右栏聊天框：该卡有待答的普通提问时，消息同样留档进开发总结（口径与飞书 y 一致）；机器生成的两类提问（前置流程确认、评审超限裁决）不写这一行。
  • 流程由前置环节产出的 suggested_flow 选定，并按卡上流程快照逐节点推进（各流程的节点序列见本指南内按配置渲染的流程 / 角色区块）；仅 confirm 项目或识别到清单外仓库时会转 need_confirm 请你确认推荐流程（y 采纳 / n 转人工）。看板网页端的确认按钮与飞书 y/n 走同一套逻辑，效果一致。
  • 自动合并冲突（卡片/详情页 doing 待处理状态的「重试合并 / 人工接管」按钮）同样与飞书 y/n 同效：点「重试合并」后调度器最长 15 秒对账执行（成功→done；仍冲突→提示继续处理、按钮重置）；点「人工接管」置暂缓（分支/worktree 保留）。
  • notes 尽量把背景 / 范围 / 验收标准写清：当前流程都不含产品方案节点，需求边界只能靠 notes 表达；standard（标准）流程没有技术设计方案节点（验收标准同样只能靠 notes），开发完过代码审查再进验收；heavy（复杂）流程才有技术方案与方案评审；quick（快速）流程只有开发与自测，没有代码审查和验收，仅限文案/配置类极小改动（改到调度器模块会自动升级为标准流程）。写清验收标准等于给每条流程都补上判据。

  2. 直接对话描述需求，agent 会整理草稿（标题/详情），先预览再确认；
  3. 可把本机 html 原型作为参考文件交给 agent：粘贴 / 拖拽到输入区 / 点「📎 参考文件」选择三种入口，仅收 .html/.htm，单文件 ≤10MB、单轮 ≤5 个（超出或类型不符在前端直接拦截并提示，不发请求）；已选文件以 chip 展示在输入框上方，可单个移除，发送后清空。发送时把「文件名 + 绝对路径」清单随消息交给 agent，agent 用只读工具 read_file 自行读源码理解结构/样式/交互（不内联正文、不渲染 html；浏览器工具仅 http/https）。
  4. 参考文件落盘在 ~/.req-board/materials/<项目>/chat-<会话id>/（可用 REQ_BOARD_MATERIALS 覆盖，本机数据区）；建卡成功后同一份文件再复制一份到该需求产物目录 ~/.req-board/artifacts/<项目>/req-<id>/materials/，路径写进需求卡 notes，供后续分析/开发复用（原上传文件保留不删）。
  5. 确认后建卡，默认 later（暂缓）状态；若项目已接入自动开发，建 open 会被调度器立即捞走；
  6. 切换项目不会中断其它项目正在跑的一轮（后台继续跑完），全站最多 3 个项目并行会话；空闲会话切走后自动回收进程，切回可继续；看板重启后会话可一键继续（省配额）。
思考中发送按钮会变为「取消」，点击可中断本轮（会话与草稿保留，之后可继续会话）；创建/恢复会话期间发送按钮暂不可用。
状态栏「就绪，可继续对话」后可点击「新建会话」：结束当前会话（有草稿时需二次确认）并自动开启同项目新会话，关闭的会话会收进历史背景框并展示会话信息。
若项目在 projects.json 中配置了 mysql，agent 可用 mysql_query 只读查询该项目 MySQL 生产库（连接参数由服务端读取，凭据不会展示在聊天中）。

六、需求助手

  • 每张需求卡片会话信息栏顶部固定一行「需求助手」（任何状态含 later/done 可用），点击在右栏打开独立需求助手视图（头部=需求标题+状态徽标+会话信息，中部=消息流，底部=状态卡片+输入框；详情页不再常驻聊天区）；一张卡一个对话，历史关闭行保留可回看，终态后可新建。
  • 底部状态卡片（#430 与 agent 会话同款）：绿=思考中（本轮执行中，带「已 Ns」计时）/ 灰=可继续对话、自动路径已停止、对话已结束 / 红=对话建立失败 / 蓝=本轮收尾中；整卡可展开三行判定依据（事件流 = 最后事件距今；模型层 = 在途请求与中断来源；判定 = 活着/已停止），计时基准是本轮最后一条用户消息。主按钮恒为「发送」，「取消本轮」/「新建对话」在卡片动作位（失败/已结束可新建；活跃对话发送即续上下文），本轮执行中不显示输入区。需求助手没有调度器的心跳/阶段证据，因此不做判死、不提供「重启调度器」。
  • 回合制：发一条消息 → agent 完整跑一轮 → 事件写入 req_chat_events；每轮结束关闭进程（低频维护场景不保持），session_id 保留，下一轮自动 session/resume 续上下文；单轮 10 分钟超时；全站最多 3 个对话并行（超出 429）；board 重启后残留会话标 interrupted，页面可一键「继续」。
  • 安全：默认只读（项目目录只读 MCP 工具 + 看板数据读工具）；写仅限 显式授权 的工具（未经明确要求不得调用）：create_requirement（建新需求卡：project 强制等于本需求所属项目、status 限 later/open 默认 later、同标题幂等防重复）、update_requirement（title/notes/summary 白名单，#434 起加 status——仅 later/open 两值，置 open 会让调度器立即捞卡开发）、write_artifact（仅本需求产物目录）、post_review（#434：追加一轮评审记录到 req_reviews，只追加不可改删，轮次与署名 reviewer 由服务端填——reviewer 取写入时刻的实时底层模型）、tapd_comment（进程内调 TAPD API 发评论，token 不进 agent 上下文）。
  • 文件写白名单（#434）：项目工作目录（#355 合并授权）+ 临时目录（/tmp 与系统 TMPDIR，会话专属子目录 /tmp/req_board_reqchat_<id>/）；其它绝对路径一律拒绝。此前白名单只含工作目录，而审批层/fs 落地层只认产物目录（#107 遗留口径），评审时写 /tmp 探针会被拦并取消整轮——三处闸门现已同源（写入边界见acp_shared 的 _in_explicit_write_roots）。
  • git 授权：git add/commit 本地提交 + 合并授权（#355）：git merge（受限 flag）、git checkout/switch（仅切分支）、git stash/push -m/list/show/pop/apply——均经 Bash 白名单校验（禁 push/reset/rebase/amend/cherry-pick/revert 等）；配套放开项目工作目录（主工作区）内文件写入。合并授权供「需求完成后代码合并冲突由需求助手直接解决」，仅用户明确要求处理合并/冲突时启用。
  • 善后工具（#324）：restart_dispatcher（按 launchd label 重启调度器并核对心跳/健康）、按 projects.json restart 配方重启项目服务、白名单范围读日志（/tmp/req_board_dispatcher.log、/tmp/req_board_agent_*.log、日志目录 ~/Library/Logs/req-board/ 下 req-board*.log 含轮转档）。
  • 会话与事件独立于调度器体系（不进 agent_sessions / agent_events），中间栏仅以置顶「需求助手」入口行展示。

七、产物 / 会话 / 执行过程

  • 卡片底部「会话信息」展示模型、上下文占比、分支；点击会话 id 可查看完整执行过程。
  • 后台 agent 模型（四层兜底链，逐层取首个非空值）：① projects.json 项目级 models 段（看板「机器人抽屉 —— 模型调参（项目级）」配置，保存后下一张卡生效）→ ② flows.json 的 roles.<id>.model（角色级，空 = 走下一层）→ ③ 环境变量 KIMI_MODEL_<角色大写> → ④ 全局 KIMI_MODEL（缺省 deepseek/v4.1-flash）。层序唯一判定点在 acp_shared.resolve_role_model / role_model_detail，本页「九、内置 agent 定义」的「生效模型」列即按此链渲染——想知道当前某角色实际用的是什么模型、来源是哪一层，看那一列即可，不必翻配置。会话建立时固定模型（不随 kimi 升级漂移）；思考档位统一模型默认（不请求、不配置、不展示）。终端直接运行 kimi 不受影响（走独立的 ~/.kimi-code/config.toml）。
  • #273 起会话列表展示全部已建立会话（同一角色可有多条，含中断/毒会话；#390 起中间栏不再展示「可继续」灰块徽标，人工继续入口统一在右栏状态行/聊天框；#431 起 session_id 为空的待接管行不展示，调度器接管回填后自动出现）；点击会话行进入右栏执行过程 + 底部聊天框，发消息默认继续该会话（调度器自动 resume 旧会话或新建真实会话并置为进行中）。状态行「新建聊天」#431 起只进入右栏草稿态（不落库、中间栏零变化，草稿文本按需求 id 存 localStorage，刷新/切走后再点可续写；清空输入框即清草稿），发送第一条消息时才落注册行并开始。
  • 「产物」行按流程节点实际产生的产物展示（analysis.md / prd.md / tech.md / self-test.md / accept.md；评审节点为 tech_review.md / code_review.md；另有历史通道闸门时代遗留的 merge_review.md 仍会列出），点击即可查看内容——不同流程走过的节点不同，产物集合也不同（如 standard 流程只有需求分析与验收产物 + 代码审查报告，没有产品方案/技术方案/方案评审产物）。
  • 执行过程面板：进行中由 SSE 推送即时刷新（#416：单条 EventSource + poke，回显 <300ms；SSE 关闭/降级时回落 1 秒轮询，原 2 秒），终态后保留可回看。
  • 产物目录：~/.req-board/artifacts/<项目>/req-<编号>/
  • 结果契约（result.json）：每轮会话结束前 agent 把结果写入产物目录 result.json（旧名工作目录根 .req-board-result.json 仅兜底），调度器读取成功即删；文件不记作者，身份由收尾时传入的会话角色（注册表键 角色:需求编号）确定。必填 status（done/blocked/need_confirm）与要点化 summary（≤10 行），question 仅 need_confirm 时填；可选 suggested_flow（仅前置环节角色：推荐的后置流程 id，须命中 flows.json 且未被软禁用（enabled: false）；缺失/非法/已禁用则兜底默认流程并留痕，不阻塞）、suggested_flow_reason（仅前置环节角色：一句话说明命中了所选流程的哪条适用场景，≤200 字；只落调度事件留档，不进 summary）、repos（涉及仓库清单，前置环节产出，缺失/非法按校验失败处理）、options（仅 need_confirm 时合法：[{label, hint}] 文本选项数组，网页端渲染为预填按钮——点击只是预填右栏聊天框可编辑后再发，不触发机制动作；非法/超限置空不阻断）、waive_gate（字符串：已完成但收尾校验预计不通过时申报豁免理由，非空转人工裁决 y=豁免完成/n=退回，不申报按校验失败处理）、todos。必须 JSON 合法（换行用 \n 转义），非法则改名 result.json.invalid 留现场；缺失/非法/超时按进程级失败重试 1 次后转 later。status=done 按卡上流程快照推进：当前节点完成即进入下一节点（评审节点 pass 前进 / reject 打回前驱节点复修，打回超限转 need_confirm）；末个节点完成后由收尾节点（terminal）执行合并/接测，全流程无人工中间态；need_confirm 转飞书提问；blocked 转 later 停止自动调度；done 但收尾校验不通过 + 申报 waive_gate → 转人工裁决（#399，y=豁免完成/n=退回）。

八、会话详情与 agent 进程管理

会话详情页（中间栏点击会话行进入）展示某条 ACP 会话的完整执行过程，底部聊天框可继续该会话。agent 进程由调度器统一管理，生命周期如下：

  • 消息流转：聊天框发消息 → 写入 manual_commands 队列 → 调度器约 2 秒轮询消费 → 拉起或复用 kimi 进程，经 ACP 协议驱动一轮 → 收尾（result.json 校验、需求状态推进、执行事件与运行记录落库）。
  • 按需拉起：每轮由调度器拉起独立 kimi acp 进程；ACP 会话上下文持久化，续跑走 session/resume 恢复（保留上下文，接续 prompt），进程不常驻。
  • 进程保持（#284）：人工续跑一轮正常结束后进程不关闭，闲置 REQ_BOARD_HELD_TTL_SEC（默认 300 秒）内下一条消息直接复用同一进程（省去拉起与 resume，事件打「agent 复用保持进程」）；超时未用由回收线程自动关闭；保持进程已死自动回退正常拉起。
  • 异常处置：运行超时先发 session/cancel 再杀进程；一轮结束但未提交 result.json 时，同一会话续接一轮补写（上限 1 次）。
  • 重启兜底：调度器重启时按 state 中 pid 镜像清理残留保持进程（pid + 命令行校验，防误杀）；重启对账（#388）：doing 卡 + 产物 result.json 合法（status ∈ done/blocked/need_confirm）时直接采纳推进（不退 open、不重跑），缺失/非法维持退 open 重跑；建卡对话/需求助手进程由看板进程退出时统一清理（SIGTERM 处理器），看板重启后残留会话标 interrupted，页面可一键「继续」（自动恢复，省配额）。
  • 状态栏语义（#421 会话活性状态行）：底部状态行按活性分级并每秒刷新时长——绿：等模型响应 / 思考中（模型推理）/ 响应中（流式输出）；琥珀（自动展开判定依据）：等模型响应偏慢 / 思考偏慢 / 响应偏慢（≥60s 无新证据）；红（自动展开 + 「重启调度器」入口）：疑似卡死 / 输出中断（>180s 无响应、无输出或思考，且事件流同样静默 >180s）；中性蓝：执行命令/写文件（带已运行时长，不计入卡死判定，长命令不受 180s 约束）/ 输出持续中（事件流仍在刷新）/ 已发送，等待调度器接管；灰：会话已结束（可发消息继续）/ 自动路径已停止（中断或毒会话，可发消息继续）/ 需求已完成（不可继续会话，输入区不显示）。整行可点击展开三行判定依据（事件流 / 模型层 / 判定），偏慢与卡死态自动展开、收起后不会被每秒重绘冲掉（#431 起草稿态输入不被全局刷新打断：注册表心跳 / sessions poke / 15s 轮询只重绘中间栏，右栏 textarea 原样保留）；时长按服务端时间计算（心跳时间戳由调度器在状态切换时落库，事件时间取服务端下发的毫秒时间戳），浏览器时钟/时区漂移不影响。运行中（含疑似卡死）不显示输入区；会话已结束/已中断恢复为可输入 + 「新建聊天」；需求已完成不显示输入区。历史行无心跳数据时显示中性「运行中」（不计时、不判卡死，fail-safe 不误报）。「重启调度器」需二次确认，服务端按同一红态口径复核（证据不足一律拒绝），重启会中断其它运行中的会话、卡死进程可能残留为孤儿进程（人工 ps -axo pid,ppid,command 定位 ppid≈1 后 kill）。
    #430 起这张状态卡片是三处共用的单一实现（调度器会话 / 需求助手 / 聊天建卡）：容器、五档配色、图标层级、展开交互与 1 秒计时同一套（.chat-status + chatStatusCardHtml + tickChatStatusCard），差异只在各自的状态模型纯函数（agentActivityModel / reqChatActivityModel / chatAddActivityModel）。需求助手与聊天建卡没有调度器的心跳/阶段证据，只做「会话状态 + 事件流时间」两档证据——不做判死、不给「重启调度器」；两处主按钮恒为「发送」，「取消本轮 / 新建对话（新建会话）」在卡片动作位，不可输入时（本轮执行中、创建/恢复阶段、已建卡）不显示输入区。
  • 消息回显：发送后消息立即以「已发送，等待调度器接管…」标记显示在事件流，调度器接管写入后转为正式记录（乐观回显，不重复）。
自动开发（open 需求自动捞取）不保持进程，行为与人工续跑不同；两种路径共用同一 ACP 会话能力（acp_shared.ACPSession），生命周期管理按宿主各自实现。

十、需求自动开发流程（节点序列生命周期）

研发流程是配置数据：仓库根 flows.json 定义 1 个前置环节共享槽位（pre.role，当前 analysis）+ 若干后置流程（每条流程 = 节点序列，节点按 node_type 分产物/开发/评审/收尾），角色展示名、产物、提示词、模型也在配置里；增删流程与节点、换前置角色都只改配置（改后需重启看板与调度器）；某条流程可置 "enabled": false 软禁用——定义保留（改回 true 即恢复），但不再进入推荐目录与可选列表。一条 open 需求从被捞起到 done 的生命周期如下。

① 拉起之前（主循环 → spawn）

  1. 轮询发现：主循环每 15 秒扫各项目 open 需求（updated_at 静置满 1 分钟；每项目最多 3 个并行，其余排队）；未入流程（无快照）的卡按前置环节角色拉起，已入流程的卡按卡上快照的当前节点角色拉起；
  2. 去重：active_runs 检查，已有活跃 agent 则跳过（防并发重复拉起）；
  3. 角色守卫：role 与卡上快照当前节点角色匹配校验（无快照 → 前置环节角色；当前节点为 terminal 收尾节点时不拉起 agent），防绕过调度器拉起非法角色；
  4. 置 doing：状态置进行中（不再写 phase）；
  5. 建 worktree：在项目全部仓库创建独立 worktree（分支 f-YYYYMMDD-<编号>[-tapd<ID>]），分支显式从主干默认分支（本地 master/main，fallback origin/HEAD）拉取，基线 commit 记录到 state["worktrees"][编号]["base"] —— 全部节点共用，调研基线 = 开发基线 = 主干，不随主工作区 checkout 漂移；
  6. 拼 prompt：角色模板（prompts/<角色>.md）填充（需求 notes、上游节点产物路径清单、仓库清单、产物路径、时间预算、评审反馈、只读工具指引、工作约束检查单）；卡处于前置阶段时另追加 suggested_flow/suggested_flow_reason/repos 输出契约段（契约全文见「九、内置 agent 定义」的 PRE_SLOT_CONTRACT 块）；
  7. 起进程：拉起 kimi acp 子进程（cwd = worktree 聚合目录，按角色能力审批路由，只读 roots = worktree + 全部仓库根 + 产物目录）。

② 运行中（agent 干活，调度器并行观察）

  • 事件流实时写 agent_events（消息文本 + 工具调用摘要），看板「执行过程」面板由 SSE 推送即时刷新（降级 1 秒轮询）；
  • 工具审批（request_permission）按角色能力档位路由（#339）：只读角色（analysis/proposal/tech/review/tech_review/code_review）Bash 走白名单 fail-closed（只读命令放行、其余拒绝，受限工具自动放行）；accept 只放行跑测试类命令（no_commit，禁改源码/git 提交）；dev 全放行（#336 Bash 写主工作区启发式护栏仍生效）；命中进程安全红线的命令一律拦截；
  • 运行超时（默认 240 分钟）先发 session/cancel 再杀进程。时限优先级：需求 notes 里的 timeout: <分钟>（范围 15~480）＞ projects.json 的 budgets.<角色>.max_minutes（可收紧角色时限，无默认值）＞ 默认 240 分钟。除墙钟时限外还有步数硬上限（按角色可配，默认 dev 1000 / accept 与 code_review 500 / analysis、proposal、tech、tech_review 400 / merge_resolve 200，见「十二、预算与配额」）。

③ 结束后（收束 → handle_result，按节点类型分派）

  1. 统一收尾：写 agent_runs 运行记录（起止时间/状态/工具数/context 百分比）；更新会话信息（model/thinking/context/branch/workdir，其中 thinking 仅记录响应观测值、不再展示；branch 统一记录 f-<编号>，不再读主工作区当前分支）；同步 agent_sessions 注册表为 idle；
  2. 产物校验：按节点类型判定——前置环节 = 前置角色产物存在非空 + repos 仓库清单合法（缺失/非法按失败处理）；产物节点 = 本节点产物文件非空；开发节点 = 有实际代码变更；评审节点 = 产物非空且 verdict ∈ {pass, reject}；
  3. 成功路径（前置环节）：清重试计数，repos 存入 state；suggested_flow 命中配置且未被软禁用即采纳（缺失/非法/已禁用 → 兜底默认流程 + 留痕，不阻塞）；免确认项目直接写入流程快照并拉起流程首节点；confirm 项目或 repos 含清单外仓库名（#303）→ 转 need_confirm 请你确认推荐流程（y 采纳推进 / n 转人工），不再有 route 中间态；
  4. 成功路径（流程内节点）：更新卡上快照指针并推进——产物/开发节点进入下一节点；评审节点 pass 前进、reject 打回前驱节点复修（resume 上游会话并把评审意见与产物全文注入续跑消息，打回超限转 need_confirm）；末个节点完成后由收尾节点（terminal）执行合并/接测，全流程无人工中间态；
  5. 失败路径：失败原因写入 retries[编号]；进程级失败（崩溃/超时/未提交结果/非法 JSON）自动重试 1 次（最多跑 2 轮，resume 旧会话并注入上次失败原因）；耗尽转 later 停止自动调度 + 会话标记毒会话，等人工重新开放或续跑；blocked（#385，内容性阻塞结论）不经重试计数——进程正常退出时直接转 later + 毒会话（通知卡片「需求阻塞」，可在看板需求助手续跑），blocked 但进程异常（超时/非 0 退出码）仍走进程级失败重试；done 但收尾校验不通过（#399）：带 waive_gate 申报 → 不计重试转人工裁决（y=豁免完成 / n=退回），未申报 = 视为谎报走原失败通道；

④ 收尾节点（terminal）到 done（调度器动作，不拉起 agent）

  1. 前置校验：done 需有实际代码变更（dev 分支相对基线 diff）或对应产物文件（只读角色/验收）才采信；校验不符时带 waive_gate 申报可转人工裁决（#399，见「③ 结束后」失败路径）；
  2. 合并收尾：普通项目自动 --no-ff 合并回各仓库 main 并清理 worktree/分支；仅推分支项目（branch_only: true，旧名 company 兼容）不本地合并 main，只把有改动仓库的 f-分支 push 到 origin（失败不阻断 done，事件+通知红字），由外部 CI/CD 或人工发版时合并；
  3. 合并冲突：先自动拉起只读 merge_resolve 会话解决（每轮 15 分钟、最多 2 轮）；未解决/耗尽转 need_confirm（y 重试合并 / n 人工接管置 later），dev 分支与 worktree 保留；
  4. 服务重启（#318）：项目配置了 restart 配方的服务由调度器在 done 时自动重启并做就绪校验（无需人工声明重启类待办）；agent 声明的 todos 遗留待办在 done 通知逐条红字展示并写入 summary。
  5. 重启提醒：改动涉及 dispatcher.py 或 acp_shared.py（调度器模块）时，done 流程登记自动重启（#380）——无并行 agent 时调度器自动重启自身（kill 自身、KeepAlive 拉起、新进程自证生效），通知附「调度器将自动重启／将在并行 agent 结束后自动重启」；自动重启多次未生效才兜底提醒需手动重启（kill <pid>）。
基线一致性：前置环节起全部节点共用同一 per-requirement worktree，产物（analysis.md 等）统一在 ~/.req-board/artifacts/<项目>/req-<编号>/（不在任何仓库/worktree 内，不随分支清理丢失）；主工作区（人工日常 checkout）停在任何分支都不影响各节点的调研/开发基线。

十二、配置入口：项目管理 / 模型设置 / 项目清单

上面几节讲的是「跑起来之后会发生什么」，这一节讲「在哪改配置」。三处配置各自负责不同层面，互不重叠。

① 左栏项目管理（接入哪些项目）

  • 左栏项目列表的数据源就是 projects.json 的键——移除接入即从列表消失，但该项目的历史卡与数据全部保留（「所有项目」视图仍可见），重新接入即恢复。
  • 项目行 hover 出现两个操作图标：编辑（改项目名/路径/goal 等）与移除接入；「所有项目」行不提供这两个操作。项目名右侧常显 + 进入该项目的聊天建卡。
  • 左栏顶部 +（新增项目）打开项目模态：项目名、仓库路径（可多个）、base_branch、以及项目目标 goal（可选，一句话说明项目目标/业务背景，会注入需求分析角色的上下文，让分析更贴合项目定位）。
  • fail-closed：项目下还有 doing 卡时阻断移除接入，避免跑到一半的项目被摘掉。

② 设置抽屉（全局配置，左栏底部齿轮）

齿轮抽屉三个标签页：全局信息（只读四分组 + 运行时环境与工具表）、模型设置、飞书机器人。内容懒加载，打开默认停「全局信息」，「重新加载」按钮丢弃未保存修改重取。

  • 模型设置：全量维护 harness 的 config.toml（$KIMI_CODE_HOME/config.toml，即 kimi CLI 与后台 agent 实际读取的那份）——厂商（名称 / base URL / API KEY / 类型）、模型清单（别名 / provider / model / protocol / max_context_size）、default_model 编辑行。写入策略是行级最小拼接（只改目标行/段，未编辑行逐字节保留）+ 写前 TOML 回环校验，失败一律零写入；max_context_size 是必填项，缺失或非正整数整单拒绝。API KEY 只以「是否已配置」回显，明文永不出现在接口响应、日志或错误文案里。
  • 机器人抽屉「模型调参（项目级）」（与设置抽屉是两个入口，别混）：按项目 × 角色配模型，即上面四层兜底链的第 ① 层。保存后下一张卡生效。逐行保存已改为表格标题行右端一个「保存全部」。思考档位统一模型默认，不再提供配置项。
  • 飞书机器人：读写 feishu.json 凭据（密钥永不回显）+ 连通性测试 + 「看板助手能力」分组（代码只读分析 / 状态变更 / 需求卡清单卡片 / 代码拉取与提交四项默认关闭；#52 读图（多模态）默认开启、显式关闭后图片只给文件名与路径，见「三、飞书回复与状态流转」；#54 代码拉取与提交仅限项目清单内项目、不 push、不切换分支，冲突保留现场由用户选择）。

十三、预算、限幅与自验工具

会话预算（硬上限）

每轮 agent 运行有三道闸，到限即截停并留结构化失败原因（budget_exceeded: steps|time），不会无限空转：

  • 步数（工具调用数）：默认 dev 1000 / accept 与 code_review 500 / analysis、proposal、tech、tech_review 400 / merge_resolve 200。接近上限前会提示先写保底结果；真的截停后同会话再给一轮限步收尾专门用来写 result.json，写成了就正常收尾，写不成才按失败归因。
  • 墙钟时长：默认 240 分钟；优先级 notes 的 timeout:（15~480）＞ projects.json 的 budgets.<角色>.max_minutes ＞ 默认值。
  • 上下文 token 上限：未实现（运行中拿不到可靠用量）。实际可观测的是会话信息栏的上下文占比，以及 agent_runs 里落库的 token 峰值——它们只做展示与报表，不触发截停。

覆盖方式：projects.json 每个项目可加 budgets 段，如 {"dev": {"max_steps": 800, "max_minutes": 120}}；非法值（负数/字符串）忽略并回落默认，不会把配置错误变成运行期故障。

只读工具输出限幅

只读工具单次输出有硬上限，超出即截断并告诉你怎么续读，避免一次 grep 把上下文冲爆：单次输出总长 30000 字符；read_file 单次最多 2000 行 / 1MB（截断按整行算，表头给的行数与续读 offset 一定对得上实际返回的行）；list_dir 最多 500 条；search_text 最多 50 条命中；git_status 最多 500 行（超限会显式标注「已截断」，不再静默截断）。

测试实例与视觉闸门（自验用）

  • scripts/test_instance.sh start <端口> [--seed] | stop <端口> | status <端口>：起一个隔离的看板测试实例（默认端口 8901，避开主实例 8899）。加 --seed 会用确定性种子数据 + 冻结时钟，落在每端口的临时数据目录（/tmp/req_board_test_<端口>_data），stop 时连目录一起删。同一个提交起两次，渲染结果逐像素一致（动效关闭时）——这是做视觉比对的前提。
  • scripts/visual_gate.py --url <候选实例> [--baseline-url <基线实例>] [--contract <契约 JSON>] [--out <目录>] [--skins dark,light] [--viewports 1440x900,390x844]：用 CDP 直接驱动无头 Chrome（不新增依赖），跑六道闸门——控制台报错、令牌差异、计算样式（含 :focus-visible 焦点环与 hover 零位移）、布局零位移（逐元素包围盒比对）、对比度、深色皮肤原生控件露白。产出 visual-report.json + 自包含的 HTML 对照报告 + 并排截图。退出码 0=通过 / 1=闸门不过 / 2=工具错误。
  • 契约文件（--contract）用来声明有意为之的差异（放行清单：某几个令牌、某几个选择器、某几处布局位移）和自定义探针，避免闸门把「本来就该变」的改动报成缺陷。契约里的键必须都是已知键，写错键名直接报工具错误而不是静默忽略。

视觉闸门目前只作为命令行工具存在，尚未接进流程节点——也就是说它不会自动在卡上拦人，需要 dev/accept 会话主动调用，或人工在验收时跑。同理，视觉闸门与浏览器级验证是两回事：闸门管确定性检查（对比度、位移、露白），而「这个交互对不对、这个页面好不好看」仍要靠真开浏览器走一遍主路径。

Prompt 配置指引：让下一个项目沿用自己的规则开发

接入一个已有成熟框架的 ERP，并在其上增加模块时，先把「平台已有能力、扩展入口、业务边界、验证方法」写入该项目仓库。每张需求卡只补充本次模块要做什么与验收标准。下面按当前代码的实际加载方式说明，不需要为新项目修改全局角色模板。

内容放哪层ERP 接入顺序 清单示例Guide 示例 Skill 示例需求卡示例 各角色读什么续跑与冲突 上线前检查后续引擎改进

一、项目内容放在哪一层

业务事实和长期约束写 Guide，可复用操作步骤写 Skill，单次目标和验收条件写卡片。下面六类是配置职责的划分，不是六个已经实现的系统消息优先级。

职责层写在哪里 / 谁维护写什么ERP 示例
Policy：通用协议dispatcher.py::COMMON_TAIL、acp_shared.ROLE_CAPABILITIES；引擎维护者结果契约、工具权限、写入边界、进程安全；权限由代码控制，文字不能授权越界不操作生产数据、不越过只读角色能力；接入 ERP 时不改这一层
Role：角色职责prompts/<role>.md、flows.json；引擎维护者各阶段输入、输出、审查职责和流程配置；跨项目复用分析找证据，开发实现，评审查偏差，验收复核；不写 ERP 表名和客户背景
Project：项目约定projects.json + 仓库 AGENTS.md、.loop/project.json、.loop/guides/*.md；项目负责人项目定位、现有框架与模块地图、业务术语、数据红线、扩展方式、测试与部署复用已有权限、租户、工作流、菜单、字典和审计能力；给出真实代码入口与参考模块
Skill：场景方法.loop/skills/<name>.md，通过清单 skills.<role> 挂载；项目负责人反复使用的操作步骤、检查顺序、产物证据格式新增模块时核对注册、权限点、租户隔离、迁移、页面与回归的步骤
Task：本次需求需求卡 title、notes；需求负责人业务行为、范围、输入输出、验收场景、资料路径；summary 不作配置入口本次新增采购申请模块；哪些状态、哪些操作、哪些角色可以看与改
Runtime：运行上下文调度器注入、上游阶段产物、返工补充、看板会话；引擎与当前执行者当前仓库/分支/产物路径、预算、失败原因、评审返工、人工答复和 PID 红线恢复哪张卡、还剩什么、要修哪条问题；不复制为长期项目约定

当前完整新会话的实际拼装顺序是：角色模板 + 公共协议 → 项目约定 → 场景技能 → 卡片输入（含上游产物指路、历史摘要、extra）→ 前置环节契约（适用时）→ PID 安全红线。实现入口：dispatcher.build_prompt_parts / build_prompt / run_agent。

这个顺序不能理解为「越靠后权限越高」。卡片、外部文档、日志和评审引用是任务资料，不能覆盖安全约束或授予写权限。当前尚无统一的输入信任分隔与冲突检测，规则冲突时应报 need_confirm，不能自行挑一条执行。
容易混淆的配置当前实际行为
projects.json.goal一句话定位；当前内置模板中由需求分析角色消费。全员必须知道的业务约束还要写进 Guide，不能只写 goal。
AGENTS.md 与 GuideAGENTS.md 保留短规则与资料索引；当前项目约定层注入「先读 AGENTS.md」指路，并非拼入全文。已登记且匹配角色的 Guide 正文会直接注入。
文件存在与文件注入只把 Markdown 放到 .loop/guides/ 或 .loop/skills/ 不会自动加载；必须在清单里登记。Guide 引用的其它文档也不会递归内联，Agent 需要按路径读取。
配置来源与 worktree当前注入器从 projects.json.paths 登记的仓库目录读取清单/指引/技能；Agent 则在本卡 worktree 工作。只在需求分支修改配置，不等于注入器已经读到。首次开发前先把约定纳入接入基线；已有 worktree 续跑还须核对两边版本。
角色过滤与按需加载Guide 按 roles 过滤，省略 roles 表示所有角色；Skill 按角色名单挂载。目前没有按需求关键词或模块自动选择的机制。
长度与文件边界每个 Guide / Skill 注入上限 4000 字符，超长尾部截断。关键规则放前面，长参考资料放仓库文档并给路径；这不是全部 Prompt 的总长上限。
多仓库当前遍历项目登记的全部仓库加载约定，不只加载本卡的改动仓库。每份 Guide 标明适用仓库；同名 Skill 按仓库顺序取首个匹配，不合并，跨仓库技能宜用不同名字。

二、已有 ERP 平台新增模块：先准备什么

  1. 核对基线：确认远端地址、分支、提交和本地代码一致，在项目管理登记仓库与正确的 base_branch。不要让 Agent 依据错误版本分析已有能力。
  2. 先做框架盘点：找一个最相近且已上线的模块，记录后端分层、前端路由、菜单注册、权限、租户过滤、工作流、审计与数据库迁移的真实入口。分清框架自带、团队已封装和本模块需要新增的能力。
  3. 整理稳定规则：把全员适用的业务与扩展边界写入 Guide，把短红线和导航写入 AGENTS.md；在清单登记命令与按角色指引。
  4. 验证开发环境：在隔离测试库上确认安装、启动、健康检查、模块测试和关键旧模块回归真的能跑；明确新模块如何部署、是否重启、谁触发。
  5. 再写第一张卡：用下文格式写本次目标与验收。成熟 ERP 涉及数据/权限/工作流的新模块，建议由前置分析评估走含技术方案与评审的流程；把风险与范围写清，流程仍由实际配置和分析结果决定。

四、Guide 写事实、边界和证据入口

每份 Guide 开头写适用仓库/模块及核对基线。规则应具体到「复用什么、去哪里找、什么情况停下来」，避免「遵循最佳实践」这种无法验收的句子。项目公共能力发生变化时更新同一份资料，不在每张卡复制一遍。

AGENTS.md：短规则示例
# ERP 平台
在已有平台内增加模块；框架能力与扩展入口见 .loop/guides/framework.md。
业务术语见 .loop/guides/business.md，验收标准见 .loop/guides/validation.md。
新增模块沿用现有分层、组件、权限与租户机制，参考已核对的采购订单模块。
不直接编辑框架核心、第三方依赖或生成目录；确需修改先报告影响并请求确认。
不连接或改写生产数据。数据库变更使用增量迁移，不删除重建已有表。
只在本卡 worktree 内开发，不自行 push、合并主干或改卡片状态。
权限、租户、金额、工作流语义冲突时报告 need_confirm，列明冲突出处。

# 平台扩展约定（适用于 erp-platform）
基线与框架版本：填写实际分支、提交、框架名及已验证版本。
参考模块：采购订单；路径和调用链见 docs/platform/reference-module.md。

# 模块验收与回归（适用于 erp-platform）
验收基线：本卡 notes + 已确认需求文档 + 当前项目约定。
验证新增模块的正常路径、异常输入、未授权访问与跨租户访问。
验证重复提交、并发审批与状态冲突；检查事务失败后无部分写入。

回归采购订单及本次触及的公共权限/工作流接口；记录用例与结果。
页面改动在独立实例真开浏览器：菜单 → 列表 → 新建 → 提交 → 审批/驳回。
SQL、API 和页面结果应一致；角色只做其工具能力允许的检查。
记录代码基线、命令、实例地址、样例、预期/实际结果与未覆盖项。
开发在 self-test.md 留证，验收在 accept.md 独立复核；未执行不能写通过。
评审指出偏离哪条约束或哪项验收条件，并附位置与复现方法。

# 独立测试与生效方式（适用于 erp-platform）
使用清单 instance 命令启动当前 worktree 的实例，先探测端口与进程归属。
测试使用专用测试库和合成租户；不得使用生产连接串或真实客户数据。
连接信息由本机受保护配置提供；Prompt、卡片与仓库只写配置名，不写密钥。
启动脚本必须隔离端口、数据库与文件目录，停止脚本只清理本实例资源。
填写依赖服务、测试账号获取方式、种子数据与 healthcheck 的真实验证步骤。

无法启动时记录具体缺项，未覆盖项进入验收报告，不能宣称浏览器验证完成。

五、Skill 写可重复使用的方法

下面的 Skill 配合 Guide 使用：Guide 回答「本平台是什么、必须遵守什么」，Skill 回答「遇到新增模块任务时按什么步骤检查」。同一个 Skill 可以挂载多个角色，但不能让只读评审角色执行开发或写库动作。

.loop/skills/erp-module.md 示例
# ERP 模块扩展检查
1. 读取 AGENTS.md、framework/business/validation 指引和本卡 notes。
2. 对照参考模块定位实体、API、服务、页面、路由、菜单与权限注册入口。
3. 列出「本次新增 / 复用已有 / 不涉及」，附对应文件或接口证据。
4. 核对租户、组织、数据权限、事务、幂等、工作流、审计与迁移兼容性。
5. 开发角色按既有扩展点实现并运行测试；只读角色只查证和报告，不改代码/数据。
6. 用 notes 的每条验收条件对应实现位置与测试证据，标明未执行项。
7. 输出到当前角色规定的产物路径；路径与结果 JSON 契约以运行时注入为准。
遇到未定义业务语义、框架核心改动或权限冲突，报告 need_confirm。

项目 Skill 优先于全局同名 Skill；同名是整份替换，不是追加继承。不要为了新增 ERP 规则覆盖全局浏览器、安全或结果契约技能。找不到的技能目前会被跳过并记日志，因此首次接入必须核对文件与挂载结果。

六、需求卡只写本次要做什么

下面的 title 与 notes 可作为第一张卡的写法参考；未指定开始开发时建卡默认暂缓。业务细节须经项目负责人确认，不能把示例视为已批准需求。

采购申请模块需求卡示例
title：在现有 ERP 平台新增采购申请模块

notes：
目标：支持租户内员工创建采购申请，并使用已有工作流提交审批。
范围：列表、详情、新建、编辑草稿、提交、审批、驳回与查询。

权限：使用平台现有权限注册机制；申请人与审批人按既有组织规则授权。
不提供：跨租户数据共享、库存扣减、付款、历史单据批量导入。
参考：.loop/guides/framework.md；docs/domain/purchase-request.md。
验收：
1. 授权用户可从现有菜单进入模块，创建含两条明细的申请并保存草稿。
2. 提交后走已有工作流；通过/驳回后的状态与审计记录符合需求文档。
3. 未授权角色无法调用接口或操作按钮；另一租户不能查询或修改该申请。
4. 重复提交不重复创建审批实例；金额与总额在数据库、API、页面一致。
5. 采购订单及本次触及的公共能力回归通过，并提供可复现证据。
生效方式：迁移、后端部署、前端发布分别按项目部署指引执行，由部署负责人触发。

若生效方式尚未核实，卡片改写为「生效方式：待方案确认」。

多仓库且已确认范围时，可在 notes 单独写 repos: 仓库目录名, 另一仓库目录名；名字须来自项目登记的仓库。不要把所有平台背景、完整 Guide、账号密钥、讨论过程或被否决方案粘进 notes。

notes / summary 会进入各阶段 Prompt。不要把评审结论或讨论记录写入这两个字段，评审留在规定的产物或 req_reviews；后者不会自动注入。当前部分模板仍把 summary 称作「评审反馈/历史记录」，这是实现遗留，不是建议的配置方法。正常流程返工由调度器传递，人工评审需经看板会话明确指向对应报告与需修问题，不能只存一条评审记录就假设开发者已经看到。

八、续跑、配置更新与规则冲突

当前限制：新会话发送完整 Prompt；成功 resume 的旧会话发送简化续跑信息、人工消息/失败原因、风格提醒和 PID 红线，不保证重新发送最新模板、清单、Guide、Skill 或卡片全文。修改文件、刷新看板或重启进程，都不能视为旧会话已自动获得新规则。

  1. 修改约定前先看是否有本卡 Agent 运行，避免一边执行一边变更验收口径；有影响的变更应由负责人安排到安全交接点。核对登记仓库与本卡 worktree 的配置版本，不能只改其中一份就假设两边一致。
  2. 通过看板聊天框续跑时，明确列出变更文件、当前基线、已确认目标、剩余任务与验收条件；要求先回读当前规则和代码状态。新会话用看板提供的「新建聊天」入口，不自行启动 ACP。
  3. 保持同一张卡的目标与资料指向一致。规则有冲突时列出双方文件位置与影响，报 need_confirm；人工确认后，把稳定规则更新到对应 Guide，本次范围更新到卡片，确认过程仍留在会话/评审产物。
  4. 开发续跑先检查 worktree 与已提交改动、上游产物和结果文件状态；已验证与待验证分开记录，不能沿用旧报告就宣称当前通过。

九、第一张卡启动前逐项核对

  • 仓库路径、远端、base_branch、提交和框架版本均已核对；文档中的接口/目录真实存在。
  • 现有能力清单和参考模块可追溯，项目红线不是只写在 goal；业务未知项已澄清。
  • 清单是合法 JSON，Guide 路径在仓库内；所有 Skill 文件存在且名字/角色正确，单文件关键内容未超过 4000 字符。
  • 分析、方案、开发、评审与验收都能收到共同的业务/框架/验收依据；多仓库没有同名 Skill 意外覆盖。
  • 命令在 worktree 可运行；端口、测试库和文件目录隔离；无生产凭据或真实客户数据进入 Prompt。
  • 需求卡有范围、范围排除、可复现验收和生效方式；评审记录没有写进 notes/summary。
  • 先用一张范围明确的代表性模块卡验证链路，并从各角色会话实际读到的内容核对注入，不只看文件已存在。

引擎机器可运行 .venv/bin/python scripts/doctor.py 辅助检查项目清单与规范；它不替代目标 ERP 的构建、测试及真实业务验证。更详细的字段说明见仓库 docs/project-manifest.md，当前角色原文见 内置 agent 定义。
