Loop Engine 是什么

Loop Engine 是一块需求看板，后面接着一组分工明确的 AI agent。你把需求写成一张卡片，调度器就按卡片选定的流程依次拉起不同角色：分析、技术方案、方案评审、开发、代码审查、验收，最后自动合并。

  • 评审角色只读，可以打回。被打回的工作自动退给上一步重做，多次打回后交给你裁决。
  • 每张卡一个独立的 git worktree 和分支，全部关卡通过后才合并回主干。
  • 出问题就停下（fail-closed）：配置非法、评审结论缺失、收尾校验不过时不推进、不合并，留下记录等人处理。
  • 需要你拍板时，agent 会提问（need_confirm），你在看板上（或飞书里）回答即可继续。

看板是本机工具，只监听 127.0.0.1:8899，没有登录鉴权。

卡片的一生与状态

暂缓 later ──(改为 open)──▶ 待开发 open ──(调度器捞起)──▶ 进行中 doing ──▶ 已完成 done
不做了：任何未完成的卡 ──▶ 已废弃 dropped
状态名称含义
later暂缓只记录，不开发。在看板上聊天建的卡默认是这个状态。改成 open 就会进入自动开发。
open待开发调度器只会捞取这个状态的卡。卡片静置约 1 分钟没人编辑后被拉起。
doing进行中有 agent 在跑；等你回答问题、或在收尾合并时也停在这里。
done已完成流程走完并已合并（或已推送分支）。
dropped已废弃不做了。只有 later / open / dropped 的卡可以删除。
agent 进程级失败（崩溃、超时、没写结果）会自动重试 1 次；仍失败则卡片转为 暂缓，原因写在卡片摘要里。修好后把卡改回 open 即可重跑。

流程与角色

卡片被捞起后，先由需求分析（analysis）角色读需求和代码，推荐一条流程并列出涉及的仓库。之后按流程逐个节点推进：

流程节点适合
quick 快速开发 → 收尾文案、配置值等极小改动。改到项目声明的高风险路径会自动升级为标准流程。
standard 标准开发 → 代码审查 → 验收 → 收尾方案一眼可定的常规改动。
heavy 复杂技术方案 → 方案评审 → 开发 → 代码审查 → 验收 → 收尾需要设计取舍、跨仓库或高风险的改动。分析没给出合法推荐时也走这条。
角色做什么权限
analysis 需求分析调研需求与代码，写 analysis.md，推荐流程和仓库只读
tech 技术方案写技术设计 tech.md只读
tech_review 方案评审审技术方案，给出 pass / reject只读
dev 需求开发在 worktree 里改代码、自测、提交，写 self-test.md可写本卡 worktree、可执行命令
code_review 代码审查审本次 diff，给出 pass / reject只读
accept 测试验证在独立测试实例上跑真实链路，写 accept.md可跑测试，不能改源码或提交
merge_resolve 冲突解决合并冲突时自动拉起，尝试解决冲突受限 git 命令

流程、角色名称、模型都来自仓库根目录的 flows.json 和 prompts/*.md，本页最后的「内置 agent 定义」按当前配置实时显示。改这两处后需要重启看板和调度器。

流程里没有单独的产品方案环节，需求边界全靠卡片 notes。把背景、范围和验收标准写清楚，是减少打回最有效的办法。

评审、打回与升级

  • 评审角色（方案评审、代码审查）给出 pass 就进入下一节点；给出 reject 就把卡退回上一个产出节点，并把评审意见交给它重做。
  • 同一个评审节点第 1–3 次打回自动重做。第 3 次时，如果项目配置了 escalation_model，会先把作者角色换成更强的模型。
  • 第 4 次仍未通过，转成 need_confirm 交给你裁决，问题里附有每一轮的打回要点：回 y 放行，回 n 再打回修一轮。
  • 评审结论缺失或格式不对，一律按打回处理，不会直接合并。

回答 agent 的提问（need_confirm）

需要人拍板时，卡片停在 doing 并显示待确认的问题，常见三种：agent 主动提问（通常附带倾向建议）；评审第 4 次未通过；需要你确认分析推荐的流程。

  • 在看板上回答：打开卡片，在右栏聊天框输入答复，或点卡片上的确认按钮。你的答复会注入给 agent 并续跑原会话，同时记进卡片摘要，之后的会话也能看到，不会重复问。
  • 在飞书里回答（可选）：回复 y 编号 [补充说明] 同意，回复 n 编号 原因 否决。网页按钮与飞书 y/n 走同一套逻辑，效果相同。

回复格式

意图格式说明
同意 / 继续y 116 [说明] 或 同意 116 [说明]编号前可带 #；说明会交给继续跑的 agent
否决 / 退回n 116 原因 或 拒绝 116 原因原因写进卡片摘要和时间线，建议写明

飞书回复与状态流转

待确认类型何时出现回复 y（或网页「同意」类按钮）回复 n（或网页「退回」类按钮）
需要确认
need_confirm		 agent 提问；评审第 4 次未通过；需要确认推荐流程 卡保持 doing，答复注入 agent 后续跑；评审超限 = 放行到下一节点；流程确认 = 采纳推荐流程 卡退回 open，约 1 分钟后从当前节点重跑（原因交给 agent）；评审超限 = 再打回修一轮；流程确认 = 转暂缓由人工处理
合并冲突
merge_conflict		 收尾合并冲突，且冲突解决角色没能解决 「重试合并」：成功 → done；仍冲突 → 继续等待 「人工接管」：卡转暂缓，分支和 worktree 保留
评审打回
verdict: "reject"		 方案评审或代码审查不通过 前 3 次自动退回上一节点重做，不需要你回复；第 4 次转为上面的「需要确认」
收尾校验豁免
need_confirm		 agent 报完成，但收尾校验不过（如没有代码变更），且 agent 申请了豁免（waive_gate） 「豁免完成」：留痕后直接 done 「退回待开发」：卡退回 open 重跑；原因以 later 开头则转暂缓
会让卡变成暂缓的回复只有三种：合并冲突时回 n、豁免时回 n 编号 later …、否决推荐流程。其余 n 都只是退回 open，稍后自动重跑。网页上还有「停止追问转暂缓」按钮，用于 agent 反复追问时直接停下。

飞书聊天建卡与看板助手（可选）

接了飞书机器人后，私聊机器人的普通文字由跨项目的看板助手回答：查项目、需求卡、服务状态，或确认项目后建卡。回答里的卡号和状态都来自服务端数据，查不到会直说。另有四项能力需要在「设置 → 飞书机器人 → 看板助手能力」里逐项开启，四项默认关闭：

  1. 代码只读分析：跨项目读文件、检索代码，结论附文件与行号；
  2. 状态变更：仅支持把卡从暂缓改为待开发；
  3. 需求卡清单卡片：按项目发送卡片清单，太长会自动分页；
  4. 代码拉取与提交：先指定项目，拉取当前分支最新代码；有冲突时暂停并给出选项；提交先预览，你确认后下一轮才真正提交，不 push、不切换分支。
指令 / 消息效果
确认建卡落卡：草稿生成后回复它，调用 /api/chat/<id>/confirm 建卡（默认暂缓）。还没有草稿时只提示「还没有草稿」。
结束建卡结束当前建卡会话。
新建建卡关闭当前会话，下一条消息重新选择项目开始建卡。
群聊消息只处理 @机器人 的文字和图文消息，交给看板助手，回复发回该群；群聊不参与 y/n 和建卡。
图片 / 文档链接作为附件交给助手或建卡会话（单文件 ≤20MB，每轮最多 5 个）。

匹配规则（整行全等）：三条建卡指令去掉首尾空白和标点后必须与指令完全相同才生效，并且只在有进行中的建卡会话时生效；句子里顺带提到「确认建卡」不会触发。y/n 回复的优先级高于这些指令。

建卡

  1. 左栏项目名右侧点 +，打开该项目的聊天建卡面板。
  2. 用对话描述需求，agent 整理出标题和 notes 草稿，你预览后确认建卡。可以附上本机 HTML 原型作参考（粘贴、拖拽或点「参考文件」）。
  3. 新卡默认暂缓。想让它开始开发，把状态改成待开发。

写 notes 的要点：只写要做什么（目标、范围、验收标准、参考资料），不写讨论过程；排除项写成「不提供：X、Y」。notes 和摘要会进入每个角色的提示词。多仓库项目可写 repos: 仓库A, 仓库B 指定仓库，写 timeout: 120 调整单次运行时限（分钟，15–480）。

需求助手

每张卡的会话列表顶部都有「需求助手」入口，任何状态都能用。它是针对这张卡的独立对话：问进度、解释产物、修改 notes、把暂缓改成待开发等。默认只读，写操作只在你明确要求时进行。

worktree、分支与合并

  • 卡片第一次被拉起时，调度器为项目的每个仓库从主干建一个 worktree（位于 ~/.req-board/worktrees/），分支名 f-YYYYMMDD-<编号>。本卡所有角色都在这里工作，主工作区不受影响。
  • 流程走到收尾时，调度器检查确实有代码变更（或对应产物），然后用 --no-ff 合并回主干并清理 worktree 与分支。
  • 走 PR / CI 的仓库可在 projects.json 配 branch_only: true：只把分支推到远端，不在本地合并。git_sync 可配置开工前拉取、完成后推送等远端同步行为，不配置就完全不碰远端。
  • 合并冲突时，先自动拉起冲突解决角色；解决不了就转人工（见上文「合并冲突」）。
  • 项目配置了 restart 配方的服务，在卡片完成时由调度器自动重启并检查就绪。

产物、会话与执行过程

  • 产物目录：~/.req-board/artifacts/<项目>/req-<编号>/，存放 analysis.md、tech.md、tech_review.md、self-test.md、code_review.md、accept.md 等。它不在任何仓库里，清理分支也不会丢。卡片详情里的「产物」行可以直接点开查看。
  • 结果文件：每个角色结束前写 result.json（status 为 done / blocked / need_confirm，外加摘要和问题），调度器读到后据此推进卡片。agent 可声明需要人工处理的遗留待办（todos），会显示在完成通知和卡片摘要里。
  • 会话：卡片底部列出这张卡的所有 agent 会话（模型、上下文占比、分支）。点开一条会话，右栏实时显示执行过程：消息、思考、工具调用、diff。
  • 续跑会话：在会话下方的聊天框发消息，调度器会恢复该会话并把你的话交给 agent。人工续跑一律走这个聊天框。
  • 状态行：聊天框上方的状态行显示会话是否活着。绿色表示正在工作；琥珀表示响应偏慢；红色表示疑似卡死，此时会出现「重启调度器」入口。

设置与模型

项目管理（左栏）

左栏顶部 + 接入新项目：填项目名、仓库路径（可多个）、主干分支和一句话项目目标（会提供给需求分析角色）。项目行悬停可编辑或移除接入；移除只是不再显示，历史卡片保留。还有进行中的卡时不能移除。

设置抽屉（左栏底部齿轮）

  • 全局信息：只读查看流程、角色、运行时环境与工具。
  • 模型设置：编辑 kimi 运行体读取的 config.toml（位于 harness home，默认 ~/.kimi-code-deepseek）：厂商、API Key、模型别名、默认模型。保存前会校验，失败不写入。
  • 通知渠道：飞书机器人（App ID / App Secret、测试连通性、看板助手能力开关；改凭据后需重启调度器），以及 Webhook、Slack 出站通知（启用、发送测试、按事件订阅，保存即生效）。

项目级模型调参（项目信息条最右侧）

按「项目 × 角色」指定模型，保存后从下一张卡开始生效，无需重启。角色模型按以下顺序取第一个有值的：

  1. 项目级（projects.json 的 models，即这里的调参）；
  2. 角色级（flows.json 的 roles.<角色>.model）；
  3. 环境变量 KIMI_MODEL_<角色大写>；
  4. 全局 KIMI_MODEL（默认 deepseek/v4.1-flash）。

项目约定 .loop/project.json

每个接入的仓库可以在根目录放 .loop/project.json，声明测试命令、测试实例启停命令、给各角色看的指引文件和技能、高风险路径。这些内容会进入提示词的「项目约定」层，下次构建提示词时生效。写法与示例见「项目配置指引」页签。

预算

单次运行默认最长 240 分钟；工具调用步数上限默认 dev 1000、accept 与 code_review 500、merge_resolve 200、其余 400。到上限会被截停并给一轮收尾机会。可在 projects.json 的 budgets 按角色调整，如 {"dev": {"max_steps": 800, "max_minutes": 120}}。

Agent 运行体

每个角色都通过 ACP（Agent Client Protocol）驱动一个 agent 运行体：

运行体可用角色说明
kimi（默认）全部kimi-code CLI（kimi acp），模型在 harness home 的 config.toml 配置
claude-code仅 dev经 @zed-industries/claude-code-acp，使用你已登录的 claude CLI
codex仅 dev经 @zed-industries/codex-acp，使用你已登录的 codex CLI

选择顺序：projects.json 的 <项目>.runtimes.<角色> → <项目>.runtime → flows.json 的 roles.<角色>.runtime → 环境变量 LOOP_AGENT_RUNTIME → kimi。未知运行体会在启动前被拒绝。

{"my-project": {"paths": ["/path/to/repo"], "runtimes": {"dev": "claude-code"}}}
Claude Code 和 Codex 目前只开放给开发角色：还无法证明只读角色的限制在这两个运行体上同样成立，所以分析、评审、验收、冲突解决和助手会话在启动前就会被拒绝。这些角色请保持 kimi。

排障

现象处理
卡片一直不被捞起确认状态是 open、建卡或编辑后已静置 1 分钟以上、卡片项目名与 projects.json 的键完全一致；页头健康角标应为非红色。
会话起不来 / 模型报错 / 401检查 harness home 的 config.toml 里的 API Key 与模型名，并与 KIMI_MODEL 对齐；找不到 kimi 时设置 KIMI_BIN。
agent 报目录未被信任用同一个 harness home 在该目录交互运行一次 kimi 并接受信任：KIMI_CODE_HOME=~/.kimi-code-deepseek kimi。
worktree 创建失败项目路径必须是有提交、有主干分支的 git 仓库；必要时在项目里配置 base_branch。
浏览器验证提示没有工具在 harness home 的 mcp.json 配置名为 playwright 的 MCP server（名字必须一致）。
改了 flows.json / prompts/ 不生效没有热加载：重启看板与调度器（前台直跑时 Ctrl-C 后重跑 scripts/run_local.sh）。
卡片转为暂缓、摘要里有失败原因按原因修正后把卡改回 open；或在会话聊天框里给出指示续跑。

调度器健康

页头右上角的角标显示调度器状态。调度器每轮轮询（约 15 秒）都会更新心跳文件 data/dispatcher_heartbeat.json；超过 180 秒没有更新就显示「心跳过期」，通常意味着调度器挂住或没在运行。它手上的待办（待确认问题、重试计数、worktree 基线等）记录在 data/dispatcher_state.json。

  • 环境自检：.venv/bin/python scripts/doctor.py（退出码 0 且输出「硬失败 0 项」即通过）。
  • 重启调度器：scripts/dispatcher-restart.sh <pid>；重启前先确认没有正在跑的 agent。
  • 详细说明见仓库 docs/quickstart.md 与 docs/dispatcher.md。

项目配置指引：让 agent 按你项目的规则开发

接入一个新项目时，把「项目已有能力、扩展方式、业务边界、怎么验证」写进该项目的仓库，每张卡只写本次要做什么和验收标准。不需要改 Loop Engine 的全局角色模板。下面用一个假设的 ERP 平台新增模块做示例，路径、模块名和脚本都要换成你项目的真实内容。

内容放哪层接入顺序 清单示例Guide 示例 Skill 示例需求卡示例 各角色读什么续跑与规则更新 启动前核对

一、内容放在哪一层

长期事实和约束写 Guide，可复用的操作步骤写 Skill，本次目标和验收写卡片。

层写在哪里写什么
通用协议引擎内置（公共尾段、角色能力）结果契约、工具权限、写入边界、进程安全。接入项目时不用动。
角色职责prompts/<角色>.md、flows.json各角色的输入、输出和职责，跨项目复用，不写具体项目内容。
项目约定仓库的 AGENTS.md、.loop/project.json、.loop/guides/*.md项目定位、框架与模块地图、业务术语、数据红线、测试与部署方式。
场景技能.loop/skills/<名>.md，在清单 skills.<角色> 挂载反复使用的检查步骤和证据格式。
本次需求卡片 title、notes业务行为、范围、验收场景、资料路径。
  • 只把文件放进 .loop/guides/ 不会自动加载，必须在清单里登记。
  • Guide 按 roles 过滤，省略表示所有角色都看；Skill 按角色挂载。
  • 每份 Guide / Skill 注入上限 4000 字符，超出部分截掉。关键规则放前面，长资料放仓库文档并给出路径。
  • AGENTS.md 不会全文注入，提示词里只提示 agent 先去读它，所以它应保持短小。

二、接入顺序

  1. 核对基线：确认仓库路径、远端、主干分支正确，在项目管理里登记 base_branch。
  2. 盘点框架：找一个相近且已上线的模块，记下分层、路由、菜单、权限、迁移等真实入口。
  3. 写稳定规则：全员适用的业务与扩展边界写进 Guide，短红线和导航写进 AGENTS.md，在清单里登记命令和指引。
  4. 验证环境：在隔离测试库上确认安装、启动、健康检查和测试能跑通。
  5. 写第一张卡：按下文格式写目标与验收，先用一张范围明确的卡验证整条链路。

四、Guide：写事实、边界和证据入口

每份 Guide 开头写适用范围和核对基线。规则要具体到「复用什么、去哪里找、什么情况停下来」，不写「遵循最佳实践」这类无法验收的话。

AGENTS.md 短规则示例
# ERP 平台
在已有平台内增加模块；框架能力与扩展入口见 .loop/guides/framework.md。
业务术语见 .loop/guides/business.md，验收标准见 .loop/guides/validation.md。
新增模块沿用现有分层、组件、权限与租户机制，参考已核对的采购订单模块。
不直接编辑框架核心、第三方依赖或生成目录；确需修改先报告影响并请求确认。
不连接或改写生产数据。数据库变更使用增量迁移，不删除重建已有表。
只在本卡 worktree 内开发，不自行 push、合并主干或改卡片状态。
权限、租户、金额、工作流语义冲突时报告 need_confirm，列明冲突出处。
.loop/guides/business.md 业务边界示例
# 业务边界（适用于 erp-platform 全部模块）
基线：填写实际核对的分支与提交；维护时重新核对下列事实。
租户是数据隔离单位；组织是租户内的业务归属，两者不可混用。
模块复用平台现有用户、组织、权限、编号、附件、工作流与审计服务。
采购申请状态与审批动作见 docs/domain/purchase-request.md。
金额精度、币种及舍入规则复用平台现行实现，证据路径填写到真实文件。
不提供：跨租户查询、绕过审批直接生效、自动修改历史单据。
未在需求中定义的取消、撤回、重复提交语义，开发前请求确认。
上述语义须与实际 ERP 核对，示例术语不能直接作为业务事实。
.loop/guides/framework.md 框架扩展约定示例
# 平台扩展约定（适用于 erp-platform）
基线与框架版本：填写实际分支、提交、框架名及已验证版本。
参考模块：采购订单；路径和调用链见 docs/platform/reference-module.md。
模块地图：docs/platform/module-map.md；每项给出真实文件/类/注册入口。
新增模块沿用「页面 → 现有 API 层 → 应用服务 → 数据访问」的既有边界。
菜单、权限点、租户过滤、字典、附件、编号、审批和审计沿用平台公共能力。
不另建登录、权限、审批引擎或并行 UI 组件体系，不直接改第三方依赖。
新增实体用现有基类与隔离规则；新增接口用现有响应、异常及事务约定。
数据库用平台已有迁移机制；说明默认值、历史数据兼容和失败恢复办法。
开发前先定位一个现有端到端实现，以代码证据确认扩展点，不能只凭文档猜接口。
公共能力不能满足本卡时，先写差距、影响面和候选方案，请求确认后再实施。
.loop/guides/validation.md 共享验收标准示例
# 模块验收与回归（适用于 erp-platform）
验收基线：本卡 notes + 已确认需求文档 + 当前项目约定。
验证新增模块的正常路径、异常输入、未授权访问与跨租户访问。
验证重复提交、并发审批与状态冲突；检查事务失败后无部分写入。
核对金额精度、编号、审计记录和历史数据兼容。
回归采购订单及本次触及的公共权限/工作流接口；记录用例与结果。
页面改动在独立实例真开浏览器：菜单 → 列表 → 新建 → 提交 → 审批/驳回。
SQL、API 和页面结果应一致；角色只做其工具能力允许的检查。
记录代码基线、命令、实例地址、样例、预期/实际结果与未覆盖项。
开发在 self-test.md 留证，验收在 accept.md 独立复核；未执行不能写通过。
评审指出偏离哪条约束或哪项验收条件，并附位置与复现方法。
.loop/guides/instance.md 测试环境示例
# 独立测试与生效方式（适用于 erp-platform）
使用清单 instance 命令启动当前 worktree 的实例，先探测端口与进程归属。
测试使用专用测试库和合成租户；不得使用生产连接串或真实客户数据。
连接信息由本机受保护配置提供；Prompt、卡片与仓库只写配置名，不写密钥。
启动脚本必须隔离端口、数据库与文件目录，停止脚本只清理本实例资源。
填写依赖服务、测试账号获取方式、种子数据与 healthcheck 的真实验证步骤。
只重启当前测试实例；共享/生产进程由部署负责人在明确授权后操作。
分别写清后端、前端、迁移及工作流配置何时生效、谁执行、如何验证。
无法启动时记录具体缺项，未覆盖项进入验收报告，不能宣称浏览器验证完成。

五、Skill：可重复使用的方法

Guide 回答「这个项目是什么、必须遵守什么」，Skill 回答「遇到这类任务按什么步骤做」。项目 Skill 会整份替换全局同名 Skill；找不到的 Skill 会被跳过并记日志，首次接入要核对。

.loop/skills/erp-module.md 示例
# ERP 模块扩展检查
1. 读取 AGENTS.md、framework/business/validation 指引和本卡 notes。
2. 对照参考模块定位实体、API、服务、页面、路由、菜单与权限注册入口。
3. 列出「本次新增 / 复用已有 / 不涉及」，附对应文件或接口证据。
4. 核对租户、组织、数据权限、事务、幂等、工作流、审计与迁移兼容性。
5. 开发角色按既有扩展点实现并运行测试；只读角色只查证和报告，不改代码/数据。
6. 用 notes 的每条验收条件对应实现位置与测试证据，标明未执行项。
7. 输出到当前角色规定的产物路径；路径与结果 JSON 契约以运行时注入为准。
遇到未定义业务语义、框架核心改动或权限冲突，报告 need_confirm。

六、需求卡只写本次要做什么

需求卡示例
title：在现有 ERP 平台新增采购申请模块

notes：
目标：支持租户内员工创建采购申请，并使用已有工作流提交审批。
范围：列表、详情、新建、编辑草稿、提交、审批、驳回与查询。
复用：现有用户/组织、权限、编号、附件、工作流及审计能力。
业务规则：仅本人可编辑草稿；提交后不可编辑；驳回后可编辑再提交。
权限：使用平台现有权限注册机制；申请人与审批人按既有组织规则授权。
不提供：跨租户数据共享、库存扣减、付款、历史单据批量导入。
参考：.loop/guides/framework.md；docs/domain/purchase-request.md。
验收：
1. 授权用户可从现有菜单进入模块，创建含两条明细的申请并保存草稿。
2. 提交后走已有工作流；通过/驳回后的状态与审计记录符合需求文档。
3. 未授权角色无法调用接口或操作按钮；另一租户不能查询或修改该申请。
4. 采购订单及本次触及的公共能力回归通过，并提供可复现证据。
生效方式：迁移、后端部署、前端发布分别按项目部署指引执行，由部署负责人触发。
notes 和 summary 会进入每个角色的提示词。不要把评审结论、讨论记录、账号密钥写进去；评审意见留在评审产物里。

七、让各角色用同一套依据

角色需要的资料应留下的证据
analysis业务、框架、验收 Guide，本卡目标已有能力、边界、风险与未知项，附代码出处；推荐流程
tech / tech_review同上，加分析产物扩展入口、复用/新增清单、数据与权限设计、回归范围
dev共享 Guide、模块 Skill、实例指引、上游产物代码、自测报告、每条验收条件对应的测试与未覆盖项
code_review共享 Guide、模块 Skill、方案与 diff偏离约束的具体位置与修复条件
accept验收标准、模块 Skill、实例指引、自测证据独立实例上的端到端证据与回归结果

八、续跑与规则更新

新会话会拿到完整提示词；恢复（resume）的旧会话只拿到简短的续跑信息，不保证看到你刚改的 Guide、Skill 或卡片。改了规则后续跑，请在看板聊天框里明确说明：改了哪些文件、已确认的目标、剩余工作，并要求 agent 先重读这些规则。规则相互冲突时，agent 应报 need_confirm。

九、第一张卡启动前核对

  • 仓库路径、远端、base_branch 正确；Guide 里写的接口和目录真实存在。
  • 清单是合法 JSON，Guide 与 Skill 文件都存在、名字和角色正确，单文件关键内容不超过 4000 字符。
  • 测试命令能在 worktree 里运行；测试实例的端口、数据库和目录相互隔离；提示词里没有生产凭据。
  • 卡片有范围、排除项、可复现的验收标准和生效方式。
  • 运行 .venv/bin/python scripts/doctor.py 检查项目清单格式。
