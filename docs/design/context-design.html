Loop Engine 提示词分层注入与技能管理整体设计

2026-11-05 · 设计稿 · 配套交互原型：context-prototype.html

结论：把现在「六段字符串拼接」升级为一个上下文编译器：每次拉起会话先编译出一份带来源、版本、大小和入选理由的「注入清单」，再按清单渲染提示词。技能改用与 Claude Code 兼容的 SKILL.md 格式，只常驻一行摘要、按需加载正文。引擎里写死的提示词全部搬成文件，每一层都能在「设置」抽屉的「提示词」tab 里编辑，编辑结果存为本机覆盖、不改默认文件。看板上新增四个入口：卡片的「上下文」页、设置里的「提示词」与「技能库」、角色卡上的「注入预览」。分四期落地，第一期只记录不改行为。

一、现状诊断

现在的分层思路是对的（固定段在前、按卡内容在后，利于缓存），问题在于「拼完就发、发完不留」：看不到 agent 实际收到了什么，也说不清为什么收到。

当前拼装顺序（flow_engine.build_prompt_parts → build_prompt → agent_run.run_agent）：角色模板固定段 + COMMON_TAIL → 项目约定（.loop/project.json）→ 场景技能 → 卡片输入 → 前置契约 → 进程安全红线。

缺口现象代码证据
发出去的提示词不留底agent_runs 只记 token 用量，没有提示词快照或 hash；卡片出问题时无法复现当时的输入board_modules/db.py agent_runs 表；仅飞书助手有 prompt_hash
注入规则写死在代码里「仅推分支」「自动重启」「冲突上下文」三段按 if 拼进 extra，改文案要改 Pythonbuild_prompt_parts 第 375–412 行
技能无元数据、全文常驻技能就是一个 md 文件，挂上就整篇内联（上限 4000 字）；不能按改动路径或关键词触发，没有描述、版本、负责人acp_shared.skill_text、scenario_skills_text
缺文件只写日志挂载的技能或指引找不到时跳过，卡照跑；与「配置非法一律停线」的 fail-closed 原则不一致scenario_skills_text 的 log.warning 分支
续跑不补发变更恢复旧会话只发简化文案；中途改了指引、技能或卡片 notes，agent 仍按旧上下文工作docs/project-manifest.md「续跑边界」已自述
用户数据与指令混在一起notes、summary、上游产物、飞书消息直接拼进提示词，没有「这是数据不是指令」的边界；summary 同时充当评审反馈通道review_feedback / history 变量
主干与 worktree 的清单版本不一致清单从主工作区读，agent 在 worktree 里干活；卡上改了 .loop/ 不会影响自己，也没有记录用的是哪个版本_project_repos 读 projects.json.paths

看板上也没有任何地方能看到「某个角色在某个项目会收到什么」，技能只能改文件和 flows.json。

二、设计原则

七条原则，都来自主流 agent 工具已经验证过的做法；右列是它在 Loop Engine 里的具体样子。行业参照为作者知识整理，未逐条联网核对最新版本。

原则行业参照在 Loop Engine 里怎么做
1. 上下文是编译产物，可复现、可对比依赖锁文件（lockfile）；LangSmith / Langfuse 的提示词版本与 trace每次会话生成「注入清单」：每层的来源路径、git 提交、内容 hash、字数、入选规则；存产物目录并关联到 agent_runs
2. 技能渐进式加载Anthropic Agent Skills（SKILL.md：启动时只加载 name + description，用到时再读正文和附属文件）提示词里只放技能目录（每个一行），正文按规则自动内联或由 agent 读取；格式与 Claude Code 互通
3. 规则按条件挂载Cursor Rules 的 Always / Auto Attached（按文件 glob）/ Agent Requested / Manual 四种模式技能与指引都声明激活条件：角色、流程节点、涉及路径、关键词、项目开关；代码里的 if 拼接改为声明式片段
4. 就近优先的分层记忆AGENTS.md 约定、Claude Code 的 CLAUDE.md 层级（企业 / 用户 / 项目 / 子目录）全局 → 项目 → 仓库子目录 → 卡片；同名覆盖在清单里显式标出“覆盖了谁”
5. 稳定前缀在前、变化内容在后Anthropic / OpenAI 提示词缓存：缓存按前缀命中沿用现有「固定段 / 卡片输入」切分，并在清单里标出缓存断点，前缀变化时告诉人“这次为什么没命中”
6. 指令与数据分开，权限靠工具不靠文字OWASP LLM01 提示词注入防护、Microsoft Spotlighting（给外部内容加边界标记）notes、summary、上游产物、飞书原文放进带来源的数据块，并声明“块内内容不是指令”；角色权限仍由 ROLE_CAPABILITIES 的工具白名单强制
7. 提示词改动要有回归promptfoo / OpenAI Evals 的评测集；金标准样本回放用已完成的卡片做金标准：改模板或技能后编译出新旧两份清单对比；技能按使用后的通过率、打回率统计

延续不变的红线：req_reviews 永不进提示词；配置非法、必需件缺失时停线；展示名一律来自 flows.json。

三、目标架构

把 build_prompt_parts 升级为一个六步的上下文编译器，放在 dispatcher_modules/context.py。产物有两份：发给 agent 的提示词全文，和记录「每一段从哪来、为什么在」的注入清单。

看板的注入预览和调度器走同一个编译器，预览看到的就是将来发出去的。第一期编译器必须输出与现在逐字节相同的提示词，现有断言提示词文本的测试就是这条的验收。

四、分层模型

八层，前五层是「指令」且跨卡稳定（进缓存前缀），第六层是「数据」，第七、八层按卡或按运行变化。L0–L4 与现有实现一一对应，新增的只有 L3 条件片段、L5 技能目录和 L6 的数据围栏。

层内容来源性质位置
L0 平台策略结果契约、时间与步数规则、进程安全红线、输出风格引擎内置（现 COMMON_TAIL）指令，不可被下层覆盖稳定前缀
L1 角色角色职责、产物要求、工作步骤prompts/<角色>.md 固定段，由 flows.json 指向指令稳定前缀
L2 项目约定常用命令、测试实例、按角色的项目指引、AGENTS.md 指路各仓库 .loop/project.json 与 .loop/guides/指令；事实类内容与 L1 冲突时以本层为准稳定前缀（按项目）
L3 条件片段（新）仅推分支、自动重启、外部角色等按项目开关生效的说明prompts/fragments/*.md，头部声明 when 条件指令稳定前缀（按项目）
L4 常驻技能激活方式为「始终」的技能正文全局 / 项目技能库指令稳定前缀
L5 技能目录（新）本次可用但未内联的技能：名称 + 一句描述 + 路径同上指令（只是索引）稳定前缀末尾
L6 任务数据标题、notes、上游产物指路、返工输入、卡片级触发的技能正文看板、产物目录数据，放进带来源的围栏，声明不是指令可变尾部
L7 运行参数分支、路径、时限、步数、前置契约、本进程 PID 红线、冲突仓库清单调度器运行时指令（引擎生成）可变尾部

三条编译规则：

  1. 优先级：L0 > L2（仅限事实：命令、端口、路径）> L1 > L3 > L4。L6 是数据，不参与优先级；权限不靠任何一层的文字，靠工具白名单。
  2. 预算：每层有字数上限（沿用单文件 4000 字，另加固定段总预算）。超出时截断并在正文留一句“全文在 <路径>”，清单里记截断字数，看板上黄色提示。
  3. 必需件停线：标记为 required 的技能或指引缺失、解析失败时不拉会话，卡片转暂缓并写明缺什么；非必需件缺失照旧跳过，但在清单和卡片上可见。

五、技能管理

技能从「一个 md 文件 + 在别处点名」升级为「自带元数据的目录」，格式对齐 Anthropic Agent Skills 的 SKILL.md，同一份技能可以直接拿到 Claude Code 里用。

文件格式：skills/<名字>/SKILL.md，可附 references/、scripts/ 等文件，只在用到时读。

---
name: browser-verify
description: 改了 HTML/JS/CSS 或页面行为时使用：浏览器级验证的做法与自测报告「浏览器验证」小节写法
roles: [dev, accept]
activation: auto        # always | auto | on_demand | manual
paths: ["static/**", "templates/**"]
keywords: [页面, 样式, 浏览器]
required: false
owner: frontend
---
（正文）

旧的平铺 <名字>.md 继续有效，按 activation: always、角色取自点名处理，不强制迁移。版本号不靠人工维护：内容 hash 即版本，清单里同时记下所在 git 提交。

四种激活方式

方式什么时候生效放在哪一层适合
始终 always角色匹配就内联正文L4 常驻技能（稳定前缀）短小、每次都得遵守的做法
自动 auto命中路径、关键词或流程节点时内联正文L6 卡片段（不破坏前缀缓存）只在特定改动里用得上的方法
按需 on_demand只进技能目录，agent 自己决定要不要读L5 技能目录长篇参考、偶尔用到的流程
手动 manual只有卡片 notes 点名（skills: x）时加载L6 卡片段一次性或高风险操作手册

「自动」的路径条件在不同阶段依据不同：开发前只有分析产物里的仓库与技术方案列出的文件，审查和验收时才有真实 diff。清单里写明每个技能是被哪条依据命中的。按需技能被 agent 读取时，从工具调用事件里识别并补记为「运行中加载」。

作用域与覆盖：全局 prompts/skills/ → 项目 .loop/skills/ → 卡片点名或排除（skills: a / -skills: b）。同名时近的整份覆盖远的，不合并内容，清单和界面上标出“覆盖了全局版本”。角色点名（flows.json、项目清单）与技能自己声明的 roles 取并集。

运行体适配：kimi 与 Codex 走内联 + 目录；Claude Code 额外把本次可用的技能复制到 worktree 的 .claude/skills/，用它自带的按需加载，内联部分只保留 always 类。

生命周期：草稿 → 启用 → 废弃。草稿只在注入预览里可试用，不进真实会话；废弃的技能仍被引用时告警。

质量门槛与指标

  • 校验（保存时和 doctor 里都跑）：名字合法、description 必填且不超过 200 字、正文不超过预算、引用的附属文件存在、全局技能里不含单个项目的专有内容。
  • 指标：加载次数、加载后该节点的通过率与打回率、平均占用字数。只作参考信号，样本少时不给结论。
  • 沉淀：卡片详情提供「存为技能草稿」，由人把一次经验改写成技能；评审记录本身不自动变成技能，守住 req_reviews 不进提示词的红线。

六、提示词编辑

原则：发给 agent 的每一段文字都是文件，代码只决定什么时候用、往里填什么值。编辑发生在「设置」抽屉新增的「提示词」tab；保存写进本机覆盖目录，不改随代码发布的默认文件。

写死在代码里、要搬成文件的文字（已逐处核对）：

文字现在位置搬到层
通用约束（结果 JSON 契约、时间与步数、输出风格）flow_engine.COMMON_TAILprompts/system/common.mdL0
只读工具说明acp_modules/readonly_tools.READONLY_TOOL_GUIDEprompts/system/readonly-tools.mdL0

续跑提醒、步数用完的收尾指令、失败重试原因agent_run.py、git_sync.resume_failure_hintprompts/system/resume.md、wrapup.md、retry-hint.md运行时文案

每个文件头部声明自己可用的占位符（如 {timeout_minutes}、{result_json}）和生效条件（片段的 when）。保存时校验：用了未声明的占位符、漏掉必需占位符、删改了契约句，一律拒绝保存。编译器每次拉起会话现读文件，改完不用重启。搬迁本身要求输出逐字节不变，现有断言提示词文本的测试就是验收。

各层的编辑权限

层在哪编辑权限
L0 平台策略与引擎协议「提示词」tab，带锁标记受保护编辑：措辞可改；调度器要按它解析的契约句（如 result.json 的字段与取值那几行）锁定不可删改，有测试守着
L1 角色模板「提示词」tab自由编辑
L2 项目约定文件在各项目仓库 .loop/第一期只读展示 + 「打开文件」；在页面上改等于改项目仓库主干，要处理未提交改动和提交，后续再做
L3 条件片段「提示词」tab，显示生效条件自由编辑正文；生效条件只读（由引擎定义）
L4 / L5 技能「技能库」tab自由编辑（见第五节）
运行时文案（续跑、收尾、重试）「提示词」tab自由编辑措辞；里面的值由调度器填
L6 任务数据卡片本身（标题、notes）不在设置里改
L7 运行参数「提示词」tab只能改包在外面的措辞模板，值不可改

默认与覆盖：默认版本随代码发布在 prompts/；页面上保存的内容写进不进 git 的 prompts.local/（目录结构与 prompts/ 一一对应，和 projects.json 一样算本机数据）。编译时有覆盖用覆盖，没有用默认。这样升级 Loop Engine 不会和用户的修改冲突。

  • 界面上每一项标出状态：默认 / 已覆盖 / 默认已更新（覆盖基于旧版默认）。
  • 「恢复默认」= 删除覆盖文件。
  • 覆盖文件记下它基于的默认版本 hash；升级后默认变了，提示并给出三方对比（旧默认 / 新默认 / 你的覆盖），由人决定合并方式。
  • 清单（第七节）里每一项同时记来源是默认还是覆盖，事后能查清当时用的是哪一版。

这与 VS Code 的默认设置 / 用户设置、Claude Code 的 CLAUDE.md 分层是同一个思路：发布方给默认，使用方只保存差异。

七、任务卡执行

每次拉起会话都留一份「执行档案」，续跑时按档案差异补发变更，返工时只传未解决的问题。

执行档案：存在产物目录 runs/<运行号>/，包含 manifest.json（清单）和 prompt.txt（实际发出的全文）。agent_runs 用 ALTER TABLE 加 manifest_path、prompt_hash、prefix_hash 三列，存量行保持空。

{
  "run": 1842, "req": 128, "role": "dev", "node": "standard#0", "runtime": "kimi",
  "model": {"id": "deepseek-v4", "source": "project"},
  "prefix_hash": "9f3a…", "prompt_hash": "c41e…", "chars": 18240,
  "layers": [
    {"layer": "L2", "id": "guide:instance", "src": ".loop/guides/instance.md", "commit": "a9a99e3", "hash": "5d1c…", "chars": 1581, "why": "roles 含 dev"},
    {"layer": "L6", "id": "skill:browser-verify", "src": "prompts/skills/browser-verify/SKILL.md", "hash": "77ab…", "chars": 2109, "why": "auto: 技术方案列出 static/board/60-robot-drawer.js"}
  ],
  "skipped": [{"id": "skill:render-assert", "why": "未命中路径条件"}],
  "warnings": [{"code": "truncated", "id": "guide:service", "cut": 812}]
}

续跑补发：续跑前重新编译清单，与该会话上次的清单对比。

变化范围处理
无变化照现在发简化续跑文案
L2–L6 有变化续跑消息前附「上下文更新」：逐条列出变了什么并附新正文，要求回读确认
L0 或 L1 有变化不续用旧会话，带交接摘要开新会话（与飞书助手的 prompt_hash 重建口径一致）

人工续跑时，聊天框上方先提示「上下文已变化 N 项，发送时会一并补发」，可展开看差异。

返工输入：评审角色打回时在 result.json 里必填 issues（编号、严重程度、位置、问题）。返工会话的 L6 只放「未关闭问题清单 + 评审产物路径」，作者在自己的 result.json 里逐条写处理结果；summary 回归「做了什么」的本意，不再兼做反馈通道。问题来自评审产物，不读 req_reviews。

失败可见：卡片上用小标记提示「缺技能」「有截断」「上下文已变更」；因必需件缺失停线的卡片直接写出缺的是哪个文件，并给出「去技能库修复」的入口。

八、交互设计

四个入口，分别回答四个问题：这张卡的 agent 到底收到了什么；每一层提示词怎么改；我有哪些技能、挂在谁身上；改了配置之后会变成什么样。原型沿用看板现有的玻璃风格与颜色令牌。

入口位置一眼看到什么展开后能做什么
上下文卡片详情新增一页流程节点条（每个节点几轮、结果）；选中一轮后显示分层堆叠条、缓存断点和警告数按层展开每一项的来源、版本、入选理由；与上一轮对比；查看实际发出的全文
提示词「设置」抽屉新增一个 tab按层排的目录（平台策略带锁、角色、条件片段、运行时文案、项目约定只读），每项标默认 / 已覆盖 / 默认已更新编辑正文、插入占位符、实时校验；对比默认、恢复默认、跳到注入预览看效果
技能库「设置」抽屉新增一个 tab技能列表：作用域、挂载角色、激活方式、状态、近 30 天使用次数编辑元数据与正文、看校验结果；切换到「角色 × 技能」矩阵，点格子切换激活方式
注入预览角色卡和技能编辑器上的按钮选项目 + 角色（可选一张已有卡片）后的编译结果试用草稿技能、看改动前后差异；不拉会话、不花 token

各项设置放在哪（「现在」是看板当前的样子，「本方案」是改动后）：

交互原则：

  • 默认只给概要（一条堆叠条 + 警告数），细节点开才出现，不打断看卡片的主路径。
  • 每一层固定一个颜色，卡片、预览、技能库三处一致，看一次就记住。
  • 警告带去处：「缺技能」点过去就是技能库里那一项，「有截断」点过去就是那份指引。
  • 展示名一律取自 flows.json，界面文案进中英词典。

原型：context-prototype.html，三个画面：卡片上下文、设置（提示词 / 技能库两个 tab）、注入预览，均可点击交互，数据为示例。

每期都在 main 上直接开发、全量测试，涉及界面的在中英文、深浅两套皮肤下用真浏览器验证。

十、下一阶段：提示词瘦身

结论：上下文编译器和界面完成后，下一步不是继续加规则，而是给提示词做减法——角色模板只留这个角色最核心的判断，协议交给平台层，确定性的事交给代码，并用执行档案里的指标证明每一处改动是改好了。

依据：现有 7 个角色模板加通用约束共 22 处「禁止」、24 处「不得/不要」，其中多处与工具层已强制的规则重复（如杀进程、写越界）；以最大的 dev.md 为例，真正属于「开发者」的内容约两成，其余是 git 规则、时间管理、todos 写法、进程安全等通用协议。参照了一份公开讨论里的五条经验：XML 隔离语义块、清理旧模型的防御性补丁、确定性计算交给工具、权衡给出两端代价、用「生成—评估—修复」闭环替代巨型提示词。

改动具体做法对应经验
S1 角色模板只写核心统一六段：使命、成功标准、判断原则（附原因）、产物契约、何时停下、常见失误（从真实打回记录提炼）。git 规则、时间与步数、todos、commit 格式、上线操作等协议挪到平台策略或条件片段；测试实例那套（accept.md 后半）做成技能，开发与验收共用—
S2 清理防御性补丁逐条审计「禁止 / 不得」：已由工具强制的（命令审查、写路径白名单、进程红线）只留一句说明或删除，被拦截时由工具返回明确原因；工具管不到的才保留，并写一句为什么第 2 条
S3 确定性的事交给代码测试实例端口由调度器算好直接给值；新增「提交结果」工具，校验格式后原子写入 result.json，删掉各模板里的写法与回读说明；worktree 是否干净由调度器收尾时检查；是否需要「上线操作」由调度器按改动路径与项目配置判断第 3 条
S4 权衡给出两端关键决策点同时写清继续的风险与停下的代价：开发「超范围就停」补上「停下会让卡片等人工，平均等待时长」；评审「打回」补上「每次打回 = 一整轮返工，连续 3 次转人工」，给出判断依据而非单向禁令第 4 条
S5 XML 分块渲染编译器按层输出 <platform_policy>、<role>、<project_conventions>、<skills>、<card_data>、<runtime> 标签块第 1 条
S6 机器先评开发完成后、代码审查前，调度器先跑项目清单声明的测试与 lint 命令；不通过直接带输出回到开发，不花模型审查成本；通过才进审查第 5 条

怎么证明改对了：改动前从执行档案取每个角色近期的打回率、格式类续接轮次数、平均提示词长度做基线；一次只改一个角色，观察所在节点的指标变化，变差用「恢复默认」退回。S5、S6 是机制改动，单独上线、单独观察。

顺序：S5 → S3 → S6 → S2 → S1 → S4。前三项是机制，风险低、收益确定；后三项改文字，依赖前面的指标基线。
