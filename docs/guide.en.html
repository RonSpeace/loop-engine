Loop Engine Guide

From first start to merge: where to look at each step, and when the engine needs you.

First start

In short: pass the self-check, start both processes, connect a project. When the header badge says "Running", you can create cards.

Loop Engine is a requirements board with a team of AI agents behind it. You describe what you want in a chat and it becomes a card. The dispatcher then runs the card through its flow — analysis, development, review, acceptance — and merges once every gate has passed. Because every step is checked, inexpensive models are enough to get steady results.

  1. Follow docs/quickstart.en.md in the repository to install dependencies and set up a model and a runtime.
  2. Run the self-check: .venv/bin/python scripts/doctor.py. It passes when it reports 0 hard failures (「硬失败 0 项」).
  3. Start: ./scripts/run_local.sh launches the board (the web app serving this page) and the dispatcher (the background process that moves cards forward).
  4. Click + at the top of the left column to connect a project: name, repository path(s), base branch and a one-line goal.
  5. Check the badge in the top-right corner. "Running" means the dispatcher is working.
The board listens on 127.0.0.1:8899 only and has no login. Do not expose it to your network or the internet.

Key terms

TermMeaning
CardOne requirement: a title, notes (what to build), a status and its position in the flow.
FlowThe sequence of nodes a card goes through, e.g. dev → code review → accept → finish.

GateA check that can stop a card: tool approval, review verdicts, the exit check, and questions for you.

need_confirmA question from an agent or the dispatcher that needs your decision. It shows up under "Needs you".

Creating cards

In short: describe the requirement in chat and confirm the draft. New cards start as "Deferred"; switch them to "Open" to start work.

  1. Click "+ New" (or press N, or the + next to a project name) to open card chat.
  2. Describe what you need. The agent drafts a title and notes; you review and confirm. You can attach a local HTML prototype for reference (paste, drag, or "Reference files").
  3. New cards start as Deferred. Set the status to Open when you want development to begin.

When chat is unavailable, expand "Fill in a form" above the chat and enter a title, project, details and status. If the configured runtime cannot run chat (not installed, or not certified for chat), the form opens by itself and the chat area tells you what to change under Settings → Models.

Writing notes: say what to build — goal, scope, acceptance criteria, references. Leave out the discussion. Write exclusions as "Not provided: X, Y". Notes go into every role's prompt; clear acceptance criteria are the best way to avoid rejections.

  • For multi-repository projects, add repos: repo-a, repo-b to name the repositories involved.
  • Add timeout: 120 to change the per-run time limit (minutes, 15–480, default 240).

Requirement assistant

Every card's session list starts with a "Requirement assistant" entry, available in any status. It is a separate conversation about this card: ask about progress, have artifacts explained, edit the notes, move the card from Deferred to Open. It is read-only unless you explicitly ask for a change.

Reading a card

In short: the status tells you which stage a card is in, the bar on top tells you where it is in its flow, and orange means it is waiting for you.

Card statuses

later (Deferred) ──(set to open)──▶ open ──(picked up)──▶ doing ──▶ done
Not doing it: any unfinished card ──▶ dropped
StatusNameMeaning
laterDeferredRecorded, not developed. New cards start here; set them to open to start.
openOpenThe only status the dispatcher picks up, after the card has sat unedited for about a minute.
doingDoingAn agent is running, the card is waiting for your answer, or it is being merged.
doneDoneThe flow finished and the work was merged (or the branch pushed).
droppedDroppedNot doing it. Only later, open and dropped cards can be deleted.
If an agent run fails (crash, timeout, no result file), it is retried once. If it fails again, the card moves to Deferred with the reason in its summary. Fix the cause and set it back to open.

The progress bar

Once a card has started, a thin bar runs across its top, split into the card's flow: the first segment is analysis, then one segment per flow node (the finish step has no segment of its own).

  • Lit segments: finished steps. A done card is fully lit.
  • Pulsing segment: the step in progress.
  • Orange segment: the card is stuck here waiting for you — an open question, a blocked merge, or a card deferred after it started. Across the board, orange only ever means "you need to decide".
  • Deferred and open cards that have not started show no bar. Hover the bar to see every step and the current one.

Artifacts, sessions and context

  • Artifacts live in ~/.req-board/artifacts/<project>/req-<id>/: analysis.md, tech.md, self-test.md, code_review.md, accept.md and so on. The folder is outside every repository, so cleaning branches never loses it. Open them from the card's "Artifacts" row.
  • Result file: each role writes result.json before it ends (status done / blocked / need_confirm, plus a summary and a question). The dispatcher moves the card based on it. Follow-up items the agent declares (todos) appear in the completion notice and the card summary.
  • Sessions: every agent session of the card is listed below it. Open one to watch messages, thinking, tool calls and diffs live.
  • Stepping in: type in the chat box under a session. The dispatcher resumes that session and hands your message to the agent. Always continue sessions this way.
  • Session status line: the line above the chat box shows whether a session is alive. Green: working. Amber: slow to respond. Red: probably stuck — a "Restart dispatcher" button appears.
  • Context tab: next to "Overview" in the card details. For every role and round it lists the prompt layers the session actually received (platform rules, role template, project conventions, skills, card data), the model and runtime, and what changed since the previous round. When you wonder why an agent did something, start here.

Answering agent questions

When a decision is needed, the card stays in doing, the current segment of its bar turns orange, and the question (usually with the agent's own recommendation) appears in the details.

  • On the board: open the card and answer in the chat box on the right, or use the confirm buttons. Your answer goes to the agent and into the card summary, so later sessions see it and do not ask again.
  • In Feishu/Lark (optional): reply y <id> [note] to approve or n <id> <reason> to reject. Web buttons and Feishu y/n run the same logic.

Reply format

IntentFormatNotes
Approve / continuey 116 [note] or 同意 116 [note]The id may start with #; the note is passed to the agent
Reject / send backn 116 reason or 拒绝 116 reasonThe reason goes into the card summary and timeline; please give one
  • Only replies starting with y / yes / 同意 or n / no / 拒绝 trigger anything.
  • Use the id of the card the question belongs to. If id and question do not match, the reply is refused and nothing changes; resend with the id from the prompt.

Only three replies defer a card (Deferred): n on a merge conflict, n <id> later … on a waiver, and rejecting a suggested flow. Every other n just sends the card back to open for an automatic rerun. If an agent keeps asking, the web "Stop asking and defer" button halts it.

Feishu chat cards and the board assistant (optional)

With the Feishu/Lark bot connected, plain text you send the bot in a private chat is answered by the cross-project board assistant: projects, cards, service status, or creating a card once you pick a project. Card ids and statuses come from server data; if it cannot find something it says so. Four more capabilities must be switched on one by one under Settings → Notifications → Feishu bot → Assistant capabilities, and all four are off by default:

  1. Read-only code analysis: read and search files across projects, with file and line references;
  2. Status changes: only Deferred → Open;
  3. Card list messages: send a project's card list, paginated when long;
  4. Pull and commit: pick a project, pull the latest code for its current branch, pause with options on conflicts; commits are previewed first and only made in the next turn after you confirm — no push, no branch switching.

Card chat and the board assistant run on kimi or opencode; both pass the runtime certification suite (see "Runtimes").

Review and acceptance

In short: a failed review sends the work back automatically and only reaches you on the 4th rejection; acceptance runs the real thing on a separate test instance; when everything passes the card merges by itself.

  • A reviewer (design review, code review) that returns pass moves the card on; reject sends it back to the previous producing node along with the review notes.
  • The first 3 rejections at the same review node are redone automatically. On the 3rd, if the project sets an escalation_model, the author role switches to that stronger model first.
  • On the 4th rejection the card becomes a need_confirm for you, with every round's rejection points: y lets it through, n sends it back once more.
  • A missing or malformed verdict counts as a rejection; nothing merges on it. Review notes stay in the review records and artifacts, never in the card notes.

Acceptance

The acceptance role (accept) checks the acceptance criteria in the notes by running the real thing on its own test instance and writes accept.md. It can run tests and commands but cannot edit source or commit. Browser-facing changes are checked in a real browser; when that is not possible it lists what was not covered so you can check it by hand. How to start a test instance is declared in the project's .loop/project.json (see the "Project setup" tab).

Worktrees, branches and merging

  • The first time a card runs, the dispatcher creates a worktree from the base branch for each repository (under ~/.req-board/worktrees/) on branch f-YYYYMMDD-<id>. Every role of the card works there; your main working copy is untouched.
  • At the finish step the dispatcher runs the exit check first: a dev node must have changed code, other nodes must have written their artifact. Then it merges with --no-ff and removes the worktree and branch.
  • For PR / CI repositories, set branch_only: true in projects.json to push the branch instead of merging locally. git_sync controls pulling before work and pushing after; without it the remote is never touched. Local-only repositories (no remote) are fine.
  • On a merge conflict, the conflict-resolution role tries first; if it cannot, the card lands in "Needs you". A missing git commit identity is reported as such, with the fix, rather than as a conflict.
  • Services with a restart recipe in the project config are restarted and health-checked when the card completes.

Settings

In short: most settings live in the drawer behind the gear at the bottom left. Changes to flows.json, .env or the default files in prompts/ need a restart of the board and dispatcher; prompt and skill edits made in the drawer apply to the next session.

The drawer has five tabs: Overview, Models, Notifications, Prompts and Skills.

Projects (left column)

Click + at the top of the left column to connect a project; its goal is given to the analysis role. Hover a project to edit or disconnect it. Disconnecting only hides it — past cards stay — and is blocked while a card is in progress.

Models

  • Models tab: edits the config.toml the kimi runtime reads (in the harness home, default ~/.kimi-code-deepseek): providers, API keys, model aliases, default model. It is validated before saving; nothing is written if validation fails.
  • Per-project tuning (far right of the project bar): pick a model per project and role. It applies from the next card, no restart needed.

A role's model is the first one set in this order:

  1. Project (models in projects.json, i.e. the tuning above);
  2. Role (roles.<role>.model in flows.json);
  3. Environment variable KIMI_MODEL_<ROLE>;
  4. Global KIMI_MODEL (default deepseek/v4.1-flash).

Runtimes

Each role drives a runtime subprocess over ACP (Agent Client Protocol). Loop Engine approves every tool call according to the role, so read-only roles cannot change code.

RuntimePipeline rolesChat & assistantNotes
kimi (default)allyeskimi-code CLI (kimi acp); models set in the harness home's config.toml
opencodeallyesOpenCode (opencode acp); works with any OpenAI-compatible API (GLM, DeepSeek, …): set LOOP_OPENAI_BASE_URL, LOOP_OPENAI_API_KEY, LOOP_OPENCODE_MODEL
claude-codedev onlynovia @zed-industries/claude-code-acp; uses your logged-in claude CLI
codexdev onlynovia @zed-industries/codex-acp; uses your logged-in codex CLI

Selection order: projects.json <project>.runtimes.<role> → <project>.runtime → flows.json roles.<role>.runtime → environment variable LOOP_AGENT_RUNTIME → kimi. Unknown runtimes are refused before anything starts.

{"my-project": {"paths": ["/path/to/repo"], "runtimes": {"dev": "claude-code"}}}
Read-only roles, card chat and the board assistant only run on runtimes that pass the runtime certification suite (tests/test_runtime_certification.py): a scripted fake model tries to write files, run commands, read outside the project and spawn sub-agents, and every attempt must be stopped. kimi and opencode pass. claude-code and codex are limited to the dev role until they do; other roles refuse to start on them.

Prompts

Every prompt is built in layers: platform rules → role template → project conventions → conditional notes → skills → card data. The Prompts tab lists each piece of engine text:

  • Saved edits go to prompts.local/ (not in git) and apply to the next session start — no restart.
  • "Restore default" deletes your override. If an upgrade changes a default, the item shows "default updated" and you choose whether to adopt it or keep yours.
  • Sentences the dispatcher parses (such as the result contract) are locked; edits that remove them are refused. Project conventions are read-only here — change them in the project's repository.
  • "Injection preview": pick a project and a role (and optionally a card) to see the full prompt from the same compiler the dispatcher uses — no session, no tokens.

Skills

A skill is a reusable procedure (say, "take a screenshot before changing UI") attached to roles. The Skills tab lets you create, edit and deprecate skills and shows how often each was loaded in the last 30 days.

  • Activation: Always (inlined whenever the role matches), Auto (inlined when a path or keyword matches), On demand (listed in a catalog; the agent fetches it), Manual (loaded only when the card notes name it).
  • Role × skill matrix: click a cell to cycle a role's activation for that skill.
  • New skills start as drafts and never reach a real session until set to active. Local edits go to prompts.local/skills/; skills shipped in a project repository are read-only.

Notifications

  • Feishu/Lark bot (optional): App ID / App Secret, connection test and assistant capability switches. Restart the dispatcher after changing credentials. It works both ways: it sends notices and accepts y/n replies and card chat.
  • Webhook / Slack: outbound only. Enable, send a test and subscribe per event (needs confirmation, done, failed, blocked, merge conflict). Saving applies immediately.

Appearance

Under "Appearance" at the bottom of the Overview tab you can turn on the animated background. It is off by default (a static backdrop saves power); the page reloads to apply. Light and dark mode use the theme toggle, shared between the board and this guide.

Time limits and budgets

A single run lasts at most 240 minutes by default. Tool-call step limits default to dev 1000, accept and code_review 500, merge_resolve 200, everything else 400. At the limit the run is stopped and given one turn to wrap up. Adjust per role with budgets in projects.json, e.g. {"dev": {"max_steps": 800, "max_minutes": 120}}.

Project conventions: .loop/project.json

Each connected repository can have a .loop/project.json declaring test commands, test-instance start/stop commands, guides and skills per role, and high-risk paths. See the "Project setup" tab for examples.

Status badge and dispatcher health

The header badge answers one question: is the engine running? Green "Running" means the dispatcher heartbeat is fresh; red means it is stale or missing, and no work will be picked up. Feishu/Lark is optional: not configured or switched off is normal and only shown in the tooltip; it is flagged on the badge only when configured but broken.

The dispatcher updates data/dispatcher_heartbeat.json on every poll (about every 15 seconds); after 180 seconds without an update the heartbeat counts as stale. Its pending work (open questions, retry counts, worktree baselines) is kept in data/dispatcher_state.json.

  • Self-check: .venv/bin/python scripts/doctor.py (passes when it exits 0 and reports 0 hard failures — 「硬失败 0 项」).
  • Restart the dispatcher: scripts/dispatcher-restart.sh <pid>; make sure no agent is running first.
  • More detail: docs/quickstart.en.md and docs/dispatcher.md in the repository.

Project setup: make agents follow your project's rules

When you connect a project, write down in its own repository what already exists, how to extend it, the business boundaries and how to verify work. Each card then only says what to do this time and how to accept it. You do not need to change Loop Engine's global role templates. The examples below use a hypothetical ERP platform gaining a new module; replace paths, module names and scripts with your project's real ones.

  1. Check the baseline: repository path, remote and main branch are right; set base_branch in project management.

  3. Write stable rules: business and extension boundaries for everyone go into guides; short red lines and pointers go into AGENTS.md; register commands and guides in the manifest.
  4. Prove the environment: install, start, health check and tests all work against an isolated test database.

4. Guides: facts, boundaries and where the evidence is

Start each guide with what it covers and the baseline it was checked against. Make rules concrete — what to reuse, where to find it, when to stop — rather than "follow best practices", which nobody can verify.

AGENTS.md short rules example
# ERP platform
New modules are added inside the existing platform; framework capabilities and extension points: .loop/guides/framework.md.
Business terms: .loop/guides/business.md; acceptance standard: .loop/guides/validation.md.
New modules reuse the existing layering, components, permission and tenant mechanisms; the verified purchase-order module is the reference.
Do not edit the framework core, third-party dependencies or generated directories; if unavoidable, report the impact and ask first.
Never connect to or modify production data. Schema changes use incremental migrations; never drop and recreate tables.
Work only inside this card's worktree; do not push, merge to main or change card status.
On conflicting permission, tenant, amount or workflow semantics, report need_confirm and cite the sources.
.loop/guides/business.md business boundaries example
# Business boundaries (all erp-platform modules)
Baseline: fill in the branch and commit you checked; recheck these facts when maintaining.
A tenant is the data-isolation unit; an organisation is a business unit inside a tenant. Never mix them up.
Modules reuse the platform's users, organisations, permissions, numbering, attachments, workflow and audit services.

8. Resuming after rule changes

A new session gets the full prompt. When the dispatcher resumes an old session, it first compares what it would send now with what that session received last time, item by item:

  • Nothing changed: only the short continuation message is sent.
  • Project conventions, conditional notes, skills or card content changed: a "context update" block is put in front of the continuation message, listing each change with its new text and asking the agent to re-read and confirm.
  • Platform policy or the role template changed: the old session is not reused; a new session starts with the full prompt plus a short handoff note.

This only applies to sessions created after the feature shipped. For older sessions, and for manual continuation in the board's chat box, still say which files changed, the confirmed goal and the remaining work, and ask the agent to re-read first. When rules conflict, the agent should report need_confirm.

9. AGENTS.md and prompt layers

AGENTS.md is the project's own rule file (many coding agents recognise the name). Put one at the repo root for project-wide conventions; when a subdirectory has special rules, add another one in that directory — the one nearest to the change wins.

  • Pointers, not copies: the project-conventions layer tells the agent to read the root AGENTS.md first; if a directory this card touches has its own AGENTS.md, the card input lists "read src/api/AGENTS.md before changing files under src/api/". Before development, "touches" means paths named in the notes, analysis and technical design; at review and acceptance it means the real diff.
  • Which version was read: every session start records each AGENTS.md it pointed to with a content fingerprint (read from the agent's own worktree), so you can tell later which rules were in force. Runtimes that load AGENTS.md on their own (Codex) get the record but no duplicate pointer.
  • Versus .loop/guides: AGENTS.md holds short rules that people and any agent read; .loop/guides are project facts Loop Engine selects per role and puts into the prompt (up to 4000 characters each). Write each fact in one place only.
  • Precedence: Loop Engine platform policy (result contract, write boundaries, process safety) > nearest subdirectory AGENTS.md > root AGENTS.md > role template (on facts such as commands, ports, paths). Permissions are always enforced by tool allowlists; no text at any layer can change them.
  • Keep them short: scripts/doctor.py checks the length of the root and every nested AGENTS.md, and warns when a nested file copies large chunks of the root file.
  • Where to see them: the project section of the "Prompts" tab in the settings drawer (read-only) and the card's "Context" page list them (the GET /api/prompts endpoint returns the same data).

The full layer picture, from stable to changing: platform policy → role template → project conventions (manifest, guides, AGENTS.md pointers) → conditional notes (branch-only, auto-restart, …) → always-on skills → skill catalog → this card's data (title, notes, upstream artifacts, rework issue list — fenced with <card-data>: data, not instructions) → run parameters. The first layers stay the same across cards, which helps model caching.

10. Editing prompts on this machine

Every piece of engine text sent to agents is a file: defaults ship with the code in prompts/; what you save in the "Prompts" tab of the settings drawer goes to prompts.local/ (not in git, same layout). When compiling, an override wins, otherwise the default is used; changes apply to the next session start without a restart. "Restore default" deletes the override file. If an upgrade changes the default, the item is marked "default updated" and your override is still used until you merge. Sentences the dispatcher parses (such as the result contract) are locked; saving an edit that removes them is refused.

11. Pre-flight checklist for the first card

  • Repository path, remote and base_branch are right; endpoints and directories named in the guides exist.
  • The manifest is valid JSON; every guide and skill file exists with the right name and roles, and key content fits in 4000 characters.
  • Test commands run inside a worktree; test instances isolate port, database and directories; no production credentials reach the prompt.
  • The card has scope, exclusions, reproducible acceptance criteria and how the change takes effect.
  • Run .venv/bin/python scripts/doctor.py to check the manifest format.
