What Loop Engine is

Loop Engine is a requirements board backed by a team of role-specialised AI agents. You write a requirement as a card; the dispatcher then runs the card's flow, starting one role after another: analysis, tech design, design review, development, code review, acceptance, and finally an automatic merge.

  • Reviewers are read-only and can reject. Rejected work goes back to the previous step for a redo; after repeated rejections it comes to you.
  • Every card gets its own git worktree and branch, merged into the main branch only after every gate has passed.
  • When something is wrong, it stops (fail-closed): invalid config, a missing review verdict or a failed exit check means no progress and no merge — it leaves a record and waits for a human.
  • When a decision is needed, the agent asks a question (need_confirm). Answer it on the board (or in Feishu) and the work continues.

The board is a local tool: it listens on 127.0.0.1:8899 only and has no login.

If an agent process fails (crash, timeout, no result written), it is retried once automatically. If it fails again the card moves to Deferred with the reason in its summary. Fix the cause and set the card back to open to rerun it.

Flows and roles

When a card is picked up, the Analysis role (analysis) reads the requirement and the code, recommends a flow and lists the repositories involved. The card then moves through that flow node by node:

FlowStepsUse it for
quick Quickdev → finalizeTiny changes such as wording or config values. Touching a high-risk path declared by the project upgrades the card to standard.
standard Standarddev → code review → acceptance → finalizeRoutine changes whose approach is obvious.
heavy Complextech design → design review → dev → code review → acceptance → finalizeChanges that need design trade-offs, span repositories, or carry high risk. Also the fallback when analysis gives no valid recommendation.

tech Tech designWrites the technical design tech.mdRead-only
tech_review Design reviewReviews the design and returns pass / rejectRead-only

Flows, role names and models come from flows.json and prompts/*.md at the repository root; the "Built-in agents" section at the end of this page shows the live configuration. Restart the board and the dispatcher after changing either.

There is no separate product-spec step, so the card's notes are the only place the scope is defined. Writing down the background, the scope and the acceptance criteria is the most effective way to avoid rejections.

Review, rejection and escalation

  • A reviewer (design review or code review) that returns pass moves the card on; reject sends it back to the previous producing step together with the review comments.
  • For the same review step, rejections 1–3 are redone automatically. On the 3rd one, if the project sets escalation_model, the author role is switched to that stronger model first.
  • A 4th rejection becomes a need_confirm question for you, listing the points raised in each round: reply y to let it through, n to send it back for one more round.
  • A missing or malformed verdict counts as a rejection — it is never merged by default.

Answering agent questions (need_confirm)

When a human decision is needed, the card stays in doing and shows the pending question. The usual cases: an agent asks something (usually with a suggested answer); a review step was rejected a 4th time; you need to confirm the flow that analysis recommended.

  • On the board: open the card and type your answer in the chat box on the right, or click one of the buttons on the card. Your answer is passed to the agent, which resumes the same session; it is also recorded in the card summary so later sessions see it and do not ask again.
  • In Feishu (optional): reply y <id> [note] to agree or n <id> <reason> to reject. Board buttons and Feishu y/n go through the same logic and have the same effect.

Reply format

IntentFormatNotes
Agree / continuey 116 [note] (or 同意 116 [note])The id may be prefixed with #; the note is passed to the agent
Reject / send backn 116 reason (or 拒绝 116 reason)The reason is written to the card summary and timeline — please include one
  • Only replies starting with y / yes / 同意 or n / no / 拒绝 are recognised; anything else does not change the card.
  • Use the id of the card the question belongs to. If the id and the question do not match, the reply is refused and nothing changes — resend with the id given in the notice.

Feishu card creation and the board assistant (optional)

With a Feishu bot connected, plain messages sent to the bot are answered by the cross-project board assistant: it can look up projects, cards and service status, or create a card once you have confirmed the project. Ids and statuses in its answers come from the server's data; if it cannot find something it says so. Four extra abilities are switched on one by one under Settings → Feishu bot → assistant abilities, and all four are off by default:

  1. Read-only code analysis: reads and searches files across projects, citing files and line numbers;
  2. Status change: only from Deferred to Open;
  3. Card list: sends a project's cards as an interactive card, paginated when long;
  4. Pull and commit: you name the project; it pulls the latest code of the current branch and pauses with options on a conflict; commits are previewed first and only made in the next turn after you confirm. It never pushes or switches branches.
Command / messageEffect
确认建卡 (confirm card)Creates the card from the current draft via /api/chat/<id>/confirm (status Deferred by default). Without a draft it only replies that there is no draft yet.
结束建卡 (end)Ends the current card-creation session.
新建建卡 (new)Closes the current session; the next message starts over by choosing a project.
Group messagesOnly text and rich-text messages that @mention the bot are handled, by the board assistant, with the reply sent to that group. Groups never take part in y/n or card creation.
Images / document linksPassed to the assistant or the card-creation session as attachments (≤ 20 MB each, at most 5 per turn).

Matching rule (whole line): the three commands only work when the whole message, after trimming spaces and punctuation, is exactly the command, and only while a card-creation session is active — mentioning the phrase inside a sentence does nothing. y/n replies take priority over these commands.

Creating cards

  1. Click + next to a project name in the left sidebar to open its chat-to-create panel.
  2. Describe the requirement in the chat; the agent drafts a title and notes, you preview and confirm. You can attach a local HTML prototype for reference (paste, drag in, or use the reference-file button).
  3. New cards start as Deferred. Change the status to Open to start development.

Writing notes: describe only what to build — goal, scope, acceptance criteria, references — not the discussion that led there; write exclusions as "Not provided: X, Y". Notes and the summary go into every role's prompt. For multi-repo projects, repos: repo-a, repo-b pins the repositories; timeout: 120 changes the per-run time limit (minutes, 15–480).

Card assistant

Every card has an "Assistant" entry at the top of its session list, available in any status. It is a separate conversation about that card: ask about progress, have artifacts explained, edit the notes, or move the card from Deferred to Open. It is read-only by default and only writes when you explicitly ask it to.

Worktrees, branches and merging

  • The first time a card starts, the dispatcher creates a worktree from the main branch for each of the project's repositories (under ~/.req-board/worktrees/), on branch f-YYYYMMDD-<id>. Every role for that card works there; your main working copy is untouched.
  • At finalize, the dispatcher checks that there is a real code change (or the expected artifact), merges with --no-ff into the main branch, and removes the worktree and branch.
  • For PR / CI-based repositories, set branch_only: true in projects.json: the branch is pushed to the remote and nothing is merged locally. git_sync configures remote sync (fetch/pull before a card, push after done); without it the remote is never touched.
  • On a merge conflict the conflict-resolution role runs first; if it cannot fix it, the card comes to you (see "Merge conflict" above).
  • Services with a restart recipe in projects.json are restarted and health-checked by the dispatcher when the card is done.

Artifacts, sessions and the timeline

  • Artifact directory: ~/.req-board/artifacts/<project>/req-<id>/, holding analysis.md, tech.md, tech_review.md, self-test.md, code_review.md, accept.md and so on. It lives outside every repository, so cleaning up branches never loses it. Open any artifact from the card's artifact row.
  • Result file: before finishing, each role writes result.json (status done / blocked / need_confirm, plus a summary and any question); the dispatcher moves the card on from it. Agents can list follow-ups that need a human (todos); they appear in the done notice and the card summary.
  • Sessions: the bottom of the card lists every agent session for it (model, context usage, branch). Open one to see its live timeline on the right: messages, thoughts, tool calls, diffs.
  • Continuing a session: send a message in the chat box under the session; the dispatcher resumes that session and hands your message to the agent. Always continue sessions this way.
  • Status line: the line above the chat box shows whether the session is alive. Green means working; amber means responses are slow; red means it looks stuck, and a "restart dispatcher" action appears.

Settings and models

Projects (left sidebar)

The + at the top of the sidebar adds a project: name, repository paths (one or more), main branch and a one-line goal (given to the analysis role). Hover a project to edit it or disconnect it; disconnecting only hides it, and its cards are kept. A project with cards in progress cannot be disconnected.

Settings drawer (gear at the bottom left)

  • Overview: read-only view of flows, roles, runtime environment and tools.
  • Models: edits the config.toml read by the kimi runtime (in the harness home, ~/.kimi-code-deepseek by default): providers, API keys, model aliases and the default model. Changes are validated before saving; nothing is written if validation fails.
  • Feishu bot: App ID / App Secret, a connectivity test, and the assistant ability switches. Restart the dispatcher after changing credentials.

Per-project model tuning (right end of the project bar)

Pick a model per project and role. Saved changes apply from the next card on, with no restart. A role's model is the first value found in this order:

  1. Project level (models in projects.json — this panel);
  2. Role level (roles.<role>.model in flows.json);
  3. Environment variable KIMI_MODEL_<ROLE>;
  4. Global KIMI_MODEL (default deepseek/v4.1-flash).

Project conventions: .loop/project.json

Each connected repository can carry a .loop/project.json declaring its test commands, test-instance start/stop commands, guide files and skills per role, and high-risk paths. These go into the "project conventions" layer of the prompts and take effect the next time a prompt is built. See the "Project setup" tab for how to write them.

Budgets

A single run is limited to 240 minutes by default. Tool-call step limits default to dev 1000, accept and code_review 500, merge_resolve 200, and 400 for the rest. A run that hits a limit is stopped and given one final turn to wrap up. Adjust per role with budgets in projects.json, e.g. {"dev": {"max_steps": 800, "max_minutes": 120}}.

Agent runtimes

Each role drives an agent runtime over ACP (Agent Client Protocol):

RuntimeRolesNotes
kimi (default)allkimi-code CLI (kimi acp); models are configured in the harness home's config.toml
claude-codedev onlyVia @zed-industries/claude-code-acp, using your logged-in claude CLI
codexdev onlyVia @zed-industries/codex-acp, using your logged-in codex CLI

{"my-project": {"paths": ["/path/to/repo"], "runtimes": {"dev": "claude-code"}}}
Claude Code and Codex are limited to the dev role for now: it cannot yet be proven that the read-only limits hold on those runtimes, so analysis, review, acceptance, conflict resolution and assistant sessions refuse to start on them. Keep those roles on kimi.

Troubleshooting

SymptomWhat to do
A card is never picked upCheck that it is open, has not been edited for at least a minute, and that its project name matches a key in projects.json exactly. The health badge in the header should not be red.
Sessions do not start / model errors / 401Check the API key and model names in the harness home's config.toml and align KIMI_MODEL with them; set KIMI_BIN if kimi is not found.
Agent says the directory is not trustedRun kimi interactively once in that directory with the same harness home and accept: KIMI_CODE_HOME=~/.kimi-code-deepseek kimi.
Worktree creation failsThe project path must be a git repository with at least one commit on its main branch; set base_branch if needed.
Browser verification reports no toolsAdd an MCP server named exactly playwright to mcp.json in the harness home.
Changes to flows.json / prompts/ have no effectThere is no hot reload: restart the board and the dispatcher (in foreground mode, Ctrl-C and rerun scripts/run_local.sh).
Card moved to Deferred with a failure reasonFix the cause and set the card back to open, or give instructions in the session chat box to continue.

Dispatcher health

The badge at the top right of the board shows the dispatcher's state. Every poll (about every 15 seconds) the dispatcher updates the heartbeat file data/dispatcher_heartbeat.json; if it has not been updated for 180 seconds the badge shows "Heartbeat stale", which usually means the dispatcher is hung or not running. Its pending work (open questions, retry counts, worktree bases and so on) is kept in data/dispatcher_state.json.

  • Environment self-check: .venv/bin/python scripts/doctor.py (passes when it exits 0 and reports 0 hard failures — 「硬失败 0 项」).
  • Restart the dispatcher: scripts/dispatcher-restart.sh <pid>; make sure no agent is running first.
  • More detail: docs/quickstart.en.md and docs/dispatcher.md in the repository.

Project setup: make agents follow your project's rules

When you connect a project, write down in its own repository what already exists, how to extend it, the business boundaries and how to verify work. Each card then only says what to do this time and how to accept it. You do not need to change Loop Engine's global role templates. The examples below use a hypothetical ERP platform gaining a new module; replace paths, module names and scripts with your project's real ones.

1. What goes where

Long-lived facts and constraints go in guides, reusable procedures go in skills, this card's goal and acceptance go on the card.

  • Putting a file in .loop/guides/ does not load it; it must be registered in the manifest.
  • Guides are filtered by roles (omit it for all roles); skills are attached per role.
  • Each guide or skill is capped at 4000 characters in the prompt; the rest is cut. Put key rules first and link to longer docs in the repo.
  • AGENTS.md is not inlined — the prompt only tells the agent to read it first — so keep it short.

2. Onboarding order

  1. Check the baseline: repository path, remote and main branch are right; set base_branch in project management.
  2. Map the framework: pick a similar module already in production and note the real entry points for layers, routes, menus, permissions and migrations.
  3. Write stable rules: business and extension boundaries for everyone go into guides; short red lines and pointers go into AGENTS.md; register commands and guides in the manifest.
  4. Prove the environment: install, start, health check and tests all work against an isolated test database.
  5. Write the first card: use the format below and start with one well-scoped card to exercise the whole pipeline.
erp-platform/
  AGENTS.md                         # short rules and pointers
  .loop/project.json                # commands, guide roles, skill roles
  .loop/guides/business.md           # business terms and lasting constraints
  .loop/guides/framework.md          # existing capabilities, extension points, reference module
  .loop/guides/validation.md         # acceptance and regression standard
  .loop/guides/instance.md           # isolated instance, test DB, how changes take effect
  .loop/skills/erp-module.md         # reusable steps for adding a module
  docs/platform/module-map.md        # details: linked from guides, read on demand

4. Guides: facts, boundaries and where the evidence is

Start each guide with what it covers and the baseline it was checked against. Make rules concrete — what to reuse, where to find it, when to stop — rather than "follow best practices", which nobody can verify.

AGENTS.md short rules example
# ERP platform
New modules are added inside the existing platform; framework capabilities and extension points: .loop/guides/framework.md.
Business terms: .loop/guides/business.md; acceptance standard: .loop/guides/validation.md.
New modules reuse the existing layering, components, permission and tenant mechanisms; the verified purchase-order module is the reference.
Do not edit the framework core, third-party dependencies or generated directories; if unavoidable, report the impact and ask first.
Never connect to or modify production data. Schema changes use incremental migrations; never drop and recreate tables.
Work only inside this card's worktree; do not push, merge to main or change card status.
On conflicting permission, tenant, amount or workflow semantics, report need_confirm and cite the sources.

5. Skills: repeatable methods

Guides answer "what is this project and what must be respected"; skills answer "for this kind of task, which steps to follow". A project skill replaces a global skill of the same name entirely. Missing skills are skipped with a log line, so check them when onboarding.

.loop/skills/erp-module.md example
# ERP module extension checklist
1. Read AGENTS.md, the framework/business/validation guides and this card's notes.
2. Using the reference module, locate the entity, API, service, page, route, menu and permission registration points.
3. List "new in this card / reused / not involved", with file or endpoint evidence.
4. Check tenant, organisation, data permissions, transactions, idempotency, workflow, audit and migration compatibility.
5. Dev implements through the existing extension points and runs tests; read-only roles only verify and report.
6. Map every acceptance criterion in the notes to its implementation and test evidence; mark anything not run.
7. Write to the artifact path for your role; paths and the result JSON contract are as injected at runtime.
On undefined business semantics, framework-core changes or permission conflicts, report need_confirm.

6. The card only says what to do this time

Card example
title: Add a purchase request module to the ERP platform

notes:

Scope: list, detail, create, edit draft, submit, approve, reject and search.

8. Resuming after rule changes

A new session gets the full prompt; a resumed session only gets a short continuation message and is not guaranteed to see guides, skills or card notes you just changed. When you continue after changing rules, say so explicitly in the board's chat box: which files changed, the confirmed goal, the remaining work — and ask the agent to re-read those rules first. When rules conflict, the agent should report need_confirm.

9. Pre-flight checklist for the first card

  • Repository path, remote and base_branch are right; endpoints and directories named in the guides exist.
  • The manifest is valid JSON; every guide and skill file exists with the right name and roles, and key content fits in 4000 characters.
  • Test commands run inside a worktree; test instances isolate port, database and directories; no production credentials reach the prompt.
  • The card has scope, exclusions, reproducible acceptance criteria and how the change takes effect.
  • Run .venv/bin/python scripts/doctor.py to check the manifest format.
