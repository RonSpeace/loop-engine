> 由 AGENTS.md「自动开发调度器」章节拆出（2026-08 瘦身，2026-09 二次瘦身）：实现细节、派生关系、流程叙事与排障参考。**红线与行为契约（进程安全、结果契约、验证约定、时间感知、安全边界）以 AGENTS.md 为准**，本文档只写细节、不重复红线；修改本文档所述行为时同步维护。

## 运维与排障

- 日志：`/tmp/req_board_dispatcher.log`；各 agent 的 kimi acp stderr 在 `/tmp/req_board_agent_<id>.log`；launchd 层面 stdout/stderr 在 `~/Library/Logs/req-board/`（`req-board-dispatcher*.log` / `req-board*.log`，由 `plists/` 的 `StandardOutPath` 指定；`REQ_BOARD_LOG_DIR` 可覆盖；非 macOS 默认 `${XDG_STATE_HOME:-~/.local/state}/loop-engine/logs`）。旧布局的 `automation/data/` 仅作遗留兼容（`board_modules/services/dispatcher_ops.py _reqchat_automation_data()`，仅当 `projects.json` 配有名为 `automation` 的项目时生效，否则不生效）
- 状态：`data/dispatcher_state.json`（重试计数、待确认问题、飞书 chat_id、各需求的 ACP 会话信息；#385 起重试计数语义为纯进程级失败——崩溃/超时/未提交结果/非法 JSON，`blocked` 不经计数；`pending_confirm` 条目按 kind 分派：普通提问（无 kind，评审轮次超限人工裁决也走这条）/ `merge` 合并冲突 / `confirm_override` 收尾校验豁免（#399）——`review_gate`（#337/#411 三档裁决）为历史 kind，#419 起不再新写入，仅保留消费分支兼容过渡窗口旧条目；`pending_route`/`pending_review` 已弃用——#419 起新流程不再写入，仅保留历史遗留分支（on_message 消费 + reconcile_decisions 扫描）兼容过渡窗口照存的历史条目；`pending_merge_review` 为 #337/#411 历史键，仅残留清理点）
- **状态文件隔离与落盘守卫（#420）**：`STATE_FILE` 支持 `REQ_BOARD_STATE` 环境变量覆盖（Path 类型，测试运行器可指到临时目录）；`save_state()` 有「未 load 不落盘」守卫——未调用 `load_state()` 的进程一律拒绝写盘并告警（防「只 import、不跑 main」的进程用 import 空骨架覆盖生产 state）；`ensure_dev_worktrees()` 在测试进程（`REQ_BOARD_TEST=1` 或已加载 unittest）且 `WORKTREES_ROOT`/`dev_worktree_path` 均未 patch 时短路（不 mkdir / 不跑 git / 不写 state，只返回形状），已隔离用例（路径被 patch）照走真实逻辑。**边界**：兜底只覆盖这两处，不代表测试进程零副作用（如 `spawn_agent` 真拉起进程不在范围），用例仍须显式隔离。
- **心跳与五态健康判定（#40）**：每轮轮询结束原子写 `data/dispatcher_heartbeat.json`（`last_poll_at`；设了 `REQ_BOARD_DATA` 时写该目录，与看板同口径）。`main` 启动首写即归位 `pid`/`boot_at` 并把 `feishu` 清成 `phase=starting`——**禁止新进程在 `init_feishu` 之前带着上一进程的 `connected=true` 被看板读走**；此后每轮 `write_heartbeat` 在锁内校正 `pid`、不刷新 `boot_at`（exec 自重启同 PID，靠 `boot_at` 变化判定已发生）。看板 `/api/dispatcher-health`、页头角标、设置页、guide 与调度器日志共用一套短路口径（唯一判定入口 `board._feishu_runtime_status`）：`disabled / not_loaded / failed / stale / connected` 五态，外加 `unknown`（心跳缺 `feishu` 对象、`last_poll_at` 非法或 `phase=starting` 的启动窗口）——心跳年龄 > 180s 一律 `stale`（角标「心跳过期」，不再沿用上一次上报的 connected）；网络连接失败只来自新鲜心跳的 `failed`/`reconnecting` 且凭据指纹一致；显式停用（`REQ_BOARD_NO_FEISHU=1` 或心跳 `disabled_reason=env`）显示「显式停用」，凭据文件缺失/不可读/非法显示「凭据未配置」，二者不混。`pid` 只影响 `pid_status`（ok/missing/dead/unknown：`os.kill` + `ps` 末个 token 为 dispatcher.py，2s 超时、5s 缓存）与 reason 注解，不改 `state`；`ok`/`age` 语义不变（年龄 < 180 为 ok=true，不看 pid）
- **主循环看门狗（#412）**：独立 daemon 线程（5s 轮询）检测 `_main_loop_tick` 停滞——每个 tick 起点更新内存时间戳 `last_tick`（wall clock，供日志展示）与 `last_tick_mono`（`time.monotonic()`，**停滞判定基准**），超过 `REQ_BOARD_TICK_WARN_SEC`（默认 60s，可 env 覆盖）无新 tick 时日志告警「主循环 tick 停滞告警」（含落后时长与最后 tick 时间）；只告警不 kill（fail-closed，不自动熔断/重启）。与心跳角标互补：角标 180s 阈值偏保守，看门狗 60s 先告警（#410 形态：tick 阻塞在锁内时心跳永不更新，同步计时永远执行不到，必须独立线程）
- **系统睡眠的时钟穿透（2026-09-17 修复）**：macOS 合盖睡眠期间进程整体冻结，但 **wall clock（`time.time()`）继续走、`time.monotonic()` 暂停**，且 `threading.Event.wait` 在 macOS 上是 realtime 语义（CPython 走 `pthread_cond_timedwait`，本机 3.11 只链接该符号、无 `relative_np` 变体）——基于 wall clock 的超时预算会被睡眠吃掉。三处判定因此改用单调时钟：① 看门狗停滞判定（否则合盖被误判「tick 停滞」：现场合盖 8 小时产生 36 条误报，09-13 起每天 26~115 条）；② `ACPSession.request` 改「分片等待 + monotonic 记账」（每片 `ACP_WAIT_SLICE`=5s，睡眠最多造成单片误差；否则唤醒后仍在运行的 agent 被误判超时 cancel、丢失已完成工作）；③ `run_agent` 无结果续接预算按 `time.monotonic() - started_mono` 记账（否则唤醒后把睡眠算进已用预算、误判预算耗尽而放弃续接）。排障：`pmset -g log | grep -E "Entering Sleep|DarkWake"` 与告警时间戳逐秒对齐即可确认是睡眠而非真阻塞（真阻塞时 monotonic 正常前进，仍会告警）
- **重启原因可见化（#373）**：调度器注册 SIGTERM/SIGINT handler——收到信号把「上次退出 = 信号名 @ 时间（来源?）」写入心跳扩展字段 `last_shutdown`（`{at, signal, source?}`，保留 `last_poll_at`）后退出；启动时写日志「上次退出 SIGTERM @ 时间（来源: script/reqchat/未知）」——该信息仅存心跳文件与启动日志，**不再透出到看板健康角标**（#408，角标只显示正常/疑似故障/异常终止）。有心跳但无 `last_shutdown` → 启动日志警告「异常终止（崩溃/被强杀）」（kill -9 不经过 handler，角标显示「上次退出异常终止（无正常关闭标记）」）；无心跳记录 → 首次部署，不误报。**来源识别仅对约定入口有效**：`scripts/dispatcher-restart.sh <pid> [来源]` 与看板需求助手 `restart_dispatcher` 工具先写 `data/dispatcher_restart_source.json` 再重启，调度器读出即删（防残留误标）；裸 `kill <pid>` 只能显示「来源未知」（macOS 不记录信号发送者身份，物理上无法定位到具体会话/人）。**#8 直跑扩展**：`REQ_BOARD_SUPERVISOR=run_local`（`run_local.sh` 导出）下，信号 handler 对「SIGTERM + 来源标记新鲜（≤300s）」改走进程内 `os.execv` 自重启——同 PID 重载（run_local 判活循环不触发整组停止）、先记录 `last_shutdown` 再 exec（复用本自证链）；exec 失败=拒绝重启绝不裸退出（写心跳 `restart_exec_failed`）；SIGINT（Ctrl-C 的 kill 0）与陈旧/无标记一律维持原退出语义
- **重启对账（#388，收尾韧性）**：调度器启动序列在 `reconcile_startup` 退 open 之前先跑 `reconcile_adopt_results`——doing 卡 + 产物 `result.json` 存在、JSON 合法且 status ∈ {done, blocked, need_confirm}（上次回合收尾结果被重启打断、handle_result 未执行）→ 直接按正常完成归因（returncode=0/未超时）走 `handle_result` 采纳推进（前置环节 → 采纳流程并拉起首节点；流程内节点 → 按快照推进），**不退 open、不重跑**，并把手尾 running 会话行标 idle（消除 #386 现场的「合法结果被丢弃重跑 + doing/open 闪变 + 会话行僵尸」）；缺失/非法/非收尾状态不动，维持退 open 重跑（行为不变，非法 JSON 的 `.invalid` 现场保留）。采纳成功后 unlink result.json 天然防重复采纳；本要点处于启动序列，看板不可达整体跳过。合法结果未被采纳的僵尸会话行（有持有者键但进程确死）由 `reconcile_orphan_sessions` 扩展一并标 interrupted（与 #374 二分：无持有者键/进程确死都清，进程存活绝不误动）。运行期主循环每 tick 另补一道 `_sweep_dead_running_once` 兜底：`agent_sessions` 中 running 行 + 有持有者键 + `active_runs` 有记录且 `proc.poll()` 非 None（调度器存活期间进程死掉、会话线程收尾未执行）→ 独立线程补收尾（先按对象匹配摘除旧的死进程登记——否则 `_spawn_safe` 被陈旧记录误拦、下一阶段不被拉起——再行置 idle + 运行记录落库 + handle_result），`_swept_rows`（加锁）防会话线程恢复后重复收尾；`run_agent` finally 删除登记同样按对象匹配，防误删 sweep/失败通道后新会话的登记（审查问题 1/2/4）。无结果续接轮（#273 followup）prompt 注入产物目录现状文件清单 + 「写入失败必须重写、不许乐观声明」强化（#388）。
- **done 流程自动重启（#380）**：dev 分支改动涉及**调度器模块**（`is_restart_trigger`：`RESTART_TRIGGER_FILES` 按文件名 = dispatcher.py / acp_shared.py / git_ops.py / storage_time.py，`RESTART_TRIGGER_DIRS` 按仓库根下目录 = dispatcher_modules/ / acp_modules/ / notifiers/；#423 起只改 acp_shared.py 也会触发）的需求转 done 时，`_set_done` 不再只发「需手动重启」提醒——在 done 通知/合并/看板重启全部完成后登记 `state["pending_restart"]`（req_id → {at, attempts}）；主循环每轮先做重启检查再做 spawn（防同轮新 agent 线程未登记 active_runs 即被 kill 的竞态，S1）：pending 写入已满 `POLL_INTERVAL`（确保先写通知最后重启，#266）且 `active_runs` 空（不打断并行 agent，顺延到全部结束后自动生效）、无外部存疑 kimi 进程（`pgrep -f "kimi acp"` 兜底，排除 board 助手进程与保持池；启发式，主安全阀是 active_runs）→ 写 `data/dispatcher_restart_source.json`（source=auto，复用 #373）→ `kill -TERM` 自身，launchd KeepAlive 自动拉起；新进程启动 `_verify_pending_restart` 按心跳 `last_shutdown.at` 自证（旧进程确认退出）→ 清标记 + 逐需求补发「调度器已自动重启，调度器模块改动已生效」（来源非 auto 时注明来源；异常终止被拉起时注明 KeepAlive）；kill 重试第 `MAX_AUTO_RESTART_ATTEMPTS`(3) 轮判定放弃（最多实际发起 2 次 kill）转原「需手动重启」提醒兜底（summary + 时间线，不静默）。⚠️ 本机制对新代码生效前提：合并后调度器仍运行旧代码，**首次部署仍需一次人工重启**（`scripts/dispatcher-restart.sh <pid>`，KeepAlive 拉起），此后命中场景免人工。**#8 直跑适配**：`REQ_BOARD_SUPERVISOR=run_local` 下 kill 自身由 handler 内 `os.execv` 自重启承接（整组不停止；launchd 路径逐字不变）；直跑加固——来源标记写失败跳过本轮 kill（下轮重试，不计尝试次数）、kill 异常清标记（防残留标记劫持 Ctrl-C 停止语义）、kill 前对 pending 各补发一条「将 exec 自重启」merge 事件；combo 兜底文案在直跑下改「Ctrl-C 后重跑 run_local.sh」（去 KeepAlive 措辞）；看板自动重启（`_kickstart_board_if_own`）在直跑下不调 launchctl，降级为事件 + 心跳 `board_restart_pending`（经 `/api/dispatcher-health` 透出为页头琥珀角标提示）。
- **会话活性心跳（#421）**：`ACPSession` 新增 `activity_sink` 回调（默认 None = 建卡会话/需求助手零行为变化），在**状态切换时**上报五类事件——`llm_request`（`session/prompt` 发出）/ `llm_thought`（`agent_thought_chunk`，60s 节流，只刷时间戳不写事件流）/ `llm_response`（message chunk，首个必报、其后 60s 节流，保证长输出期间不误判卡死）/ `tool_start`（在途工具集合由空转非空，detail=工具标题）/ `tool_end`（集合清空；并发工具的中间完成不上报，并重新武装响应上报）。上报点位于 `_tool_posted` 去重早退闸**之前**（真实序列是 rawInput 分块先行打标、completed 后到）。调度器侧 `_touch_session_activity()` 把 kind 映射为注册表字段 `turn_step`（llm/tool/''）+ 四个 epoch 秒时间戳（`last_llm_request_at` / `last_llm_response_at` / `last_thought_at` / `last_tool_started_at`）+ `turn_step_detail`，每次写自带一次 `sessions` poke；**无定时写库**（每次工具调用 ≤2 次写 + 每轮 ≥3 次 + 输出/思考期 ≤1 次/分钟）。每轮（含保持池复用轮）重绑 sink 到新 holder，holder 行 id 为 None（注册表写失败）时跳过并只告警一次。收尾/中断四点（run_agent 收尾、采纳后置 idle、孤儿清算标 interrupted、运行期 sweep 兜底）统一经 `_close_session_row()` 清 `turn_step=''`（只为证据整洁，前端正确性不依赖）。网页端「疑似卡死 → 重启调度器」入口（`POST /api/dispatcher/restart`）由看板按同一红态口径复核（服务端取 DB 最新事件，不受前端 500 条窗口限制），有意不做「有运行中 agent 即拒」预检（卡死现场本就有活进程）；重启不回收孤儿 agent，人工处置：`ps -axo pid,ppid,command`（或 `pgrep -f "kimi acp"`）定位 ppid≈1 的 kimi 进程，人工确认后 kill（agent 不自行 kill）
- **输出守卫（#28，复读/超长单请求兜底）**：给调度器会话加两个「本轮无效」判据——判据 A `stall_request`（同一 LLM 请求在途时长超 `GUARD_REQUEST_SEC`，默认 1200s；工具执行期不计时，`tool_start` 暂停计时、`tool_end` 重置起点）+ 判据 B `repeat_output`（同会话连续 `GUARD_REPEAT_N` 条 message 事件相邻文本相似度 ≥ `GUARD_REPEAT_SIM`）。阈值 4 个 env 常量单一源在 `acp_shared.py`（`KIMI_GUARD_REQUEST_SEC` / `KIMI_GUARD_REPEAT_N` / `KIMI_GUARD_REPEAT_SIM` / `KIMI_GUARD_REPEAT_MIN_LEN`），改后重启调度器生效。触发即 `_trip_guard` 单次置位（加锁原子 check-and-set）→ 留痕（`agent_events` kind=system + `dispatcher_events` kind=action + `requirements.summary` 单行事实句）→ `cancel` 本会话 → 唤醒在途 `session/prompt` 抛 `TurnAborted`（只影响本会话，`close(kill)` 仅杀本进程组）。dispatcher 侧 `run_agent` 首轮与续接轮均捕获 `TurnAborted`，走超时同款收束（跳过无结果续接、`close(kill=True)`、`agent_runs.status=aborted`、进失败重试通道），`handle_result` 归因「本轮输出复读/单次请求超长」。检测载体复用 `_flush_loop` 守护线程（无输出也跑，故事件持续在写时也有兜底——#421 的「双静默 >180s」红态对「事件持续在写」的复读不触发）。守卫仅调度器会话启用（`output_guard` 非 None），board 建卡/需求助手会话不传 = 零行为

## projects.json 可选配置

- 如需建卡聊天 agent 只读查询该项目 MySQL 生产库，可在项目配置里加可选 `"mysql": {"env_file": "<绝对路径 .env>"}`（省略 env_file 默认项目首个路径下 .env），未配置的项目不暴露 `mysql_query` 工具
- 多仓库项目可配可选 `"repo_map": "<仓库地图绝对路径>"`（analysis prompt 注入「先读地图再定位代码」指引，路径不存在则不注入）
- 项目开发主线非本地 master/main 时可配可选 `"base_branch": "<分支名>"`（worktree 基线起点，`_default_branch` 优先使用；支持字符串或 `{仓库绝对路径: 分支名}` dict）。示例：`my-app` 本地 master 落后开发主线 `f-20260303-feature` 上百个提交，配置后 analysis/dev 基线取 `f-20260303-feature`，避免「代码搜不到」误判。配置分支在仓库不存在时回退默认探测（master → main → origin/HEAD → HEAD）。
- 需在需求 done 时自动重启服务的项目可配可选 `"restart": {"cmd": "<启动命令>", "verify": "<就绪校验 URL>"}`（#318，如本地常驻的 `web` / `api-server` 服务）：调度器在 done 收尾执行并做就绪校验，agent 声明的重启类 todos 会被对账剔除或标注「调度器已自动重启」。
- 远端同步/推送可配可选 `"git": {"remote": "origin", "url": "https://…", "credential": "system|token|ssh", "ssh_key": ""}`、`"worktree": "per-requirement"` 与 `"git_sync": {"before_card": "off|fetch|pull", "on_done": "off|auto|manual", "diverge": "overlap-check|ff-only|stop", "timeout": 120}`（缺省 = 完全不碰远端，行为与旧版逐字一致；旧布尔 `fetch_before`/`push_after` 自动折算为新枚举）。详见「项目级 Git 同步与推送（git_sync）」节。

## 项目级 Git 同步与推送（git_sync）

`projects.json` 项目级可选配置；未配置 = 零远端操作（是否配了 `git_sync` 都不影响现有调度/合并行为）。

- **before_card**：`ensure_dev_worktrees` 仅在本次确需新建 worktree 时同步一次（复用/重试路径零 git 调用）。`fetch` = 只 `git fetch --prune <remote>`；`pull` = fetch 后，若主工作区干净且 HEAD==`base_branch` 再快进：本地仅落后 → `merge --ff-only <remote>/<base>`；本地分叉（有未推送提交）按 `diverge` 处理——`overlap-check`（默认）= 用 `merge-base` 两侧 `diff --name-only` 求交集，交集空 → `merge --no-edit <remote>/<base>`，交集非空 → 只写事件转人工、不制造 MERGE_HEAD；`ff-only` = 分叉跳过；`stop` = 分叉报事件。任何失败只 `log.warning` + `kind=merge` 事件，不阻断卡。
- **on_done**（仅普通项目「本地合并回主干」路径；仅推分支项目（branch_only）的 #288 push f-分支路径原样）：`auto` = 合并成功后逐仓库 `git push <remote> <base>`（只推主干、禁 force；失败先 `fetch`+`ff-only` 重试一次，仍失败记失败集但**不阻断 done**，done 卡红字提示手动推送）；`manual` = 不推送，计算领先远端提交数写进 summary/事件（项目页/卡片手动推）；`off` = 不碰远端。
- **主干守卫**：`git_sync` 启用时，合并前校验主工作区 HEAD==`base_branch`；不一致不合并（防落错分支），走人工合并通道且文案明确「主干守卫」而非「工作区脏」。
- **并发**：所有远端/合并操作在 `git_ops.repo_lock(<仓库真实路径>)` 下串行（与看板项目页 pull/push 共用同一跨进程 fcntl 锁，避免两进程同时动同一 `.git`）。
- **凭据**：`git.credential=system` 用系统钥匙串；`token`/`ssh` 由 `data/git_credentials.json`（0600、gitignore）提供，`git_ops.git_env(project)` 注入 `GIT_ASKPASS`/`GIT_SSH_COMMAND`，密码不进 argv、日志与 API 响应。看板「项目 → 编辑」可一键保存并测试连通性。

## 进程保持（#284）

人工续跑一轮正常结束后进程不关闭（复用 kimi 会话跨轮 prompt，省拉起+resume，对齐建卡页模型），闲置超时（默认 300s，`REQ_BOARD_HELD_TTL_SEC` 可调）由 `held_reaper` 回收；下一条消息优先复用保持进程（进程已死自动回退正常拉起），复用轮事件打「agent 复用保持进程」；保持进程 pid 镜像在 `state["held_procs"]`，调度器重启时按 pid+命令行含 kimi 校验清理孤儿（防 pid 复用误杀）；自动开发（spawn_agent）不保持进程，行为与旧版一致。

## 会话毒化与孤儿清算（#273/#374）

- **毒会话（#273）**：进程级失败自动重试耗尽后不删除会话记录，而是标记 `poisoned`——调度器自动路径跳过它（`find_resume_sid` 返回空，重开卡默认开新会话），但中间栏仍展示并带「已停止自动重试」徽标，人可在右栏聊天框发消息继续它，或点「新建聊天」（#431 起为前端草稿态，不预建空行；发送首条消息才经 `POST /api/requirements/<id>/sessions/messages` 单事务落注册行 + 入队命令，调度器接管后回填 session_id）。需求之间平级独立，无会话组/共享会话概念。
- **孤儿会话清算（#374）**：调度器启动时扫描 `agent_sessions`，`status='running'` 且 state.sessions 无「req_id:role」持有者键（或键存在但 session_id 不匹配，含被覆盖键如 `review:370` 换新会话后旧行无人认领）的会话，视为调度器重启被杀进程的僵尸记录，标记 `interrupted`（行/session_id 保留，人工可发消息继续）并写一条 phase 调度事件留痕；state 中仍有持有者键且 id 匹配的会话（resume 路径）不受影响。运行期另有 `_sweep_dead_running_once` 兜底（见「重启对账 #388」）。

## dev worktree 与写权限边界（#303）

- **创建与基线**：需求从 analysis 阶段起，调度器即在项目全部仓库创建独立 worktree（分支 `f-YYYYMMDD-<req_id>`，日期取需求创建日；需求来自 TAPD——notes 含 `tapd.cn/.../prong/stories/view/<id>` 或 `.../bugtrace/bugs/view/<id>` 链接——时追加 `-tapd<需求ID>`，如 `f-20260810-284-tapd1155306211001645897`），分支显式从各仓库主干默认分支（本地 master/main，fallback origin/HEAD）拉取。analysis/proposal/tech/accept/dev 全部角色共用同一 per-requirement worktree（幂等复用，跨重试/评审不重建），调研基线 = 开发基线 = 主干，不随主工作区 checkout 状态漂移；会话信息栏分支名统一记录 `f-<req_id>`。基线 commit 记录在 `state["worktrees"][<req_id>]["base"]`，`changed_repos`/`_touches_dispatcher` 三点 diff 以此为准（无记录回退主工作区当前分支）。
- **空会话行清理（#431）**：`session_id` 为空、`status=created`、非毒的注册行（「新建聊天」首条消息落行后调度器长期未接管的残留）由 `sweep_empty_sessions` 清理——主循环按 `REQ_BOARD_EMPTY_SESSION_SWEEP_SEC`（默认 1800s）节流触发、删龄超 `REQ_BOARD_EMPTY_SESSION_TTL_SEC`（默认 86400s；**0 = 关闭定期清理**）者；启动序列在 `recover_manual_commands()` 之后调一次不限龄清理（幂等，上线存量清理）。删除一律经看板 `DELETE /api/requirements/<id>/sessions/<asid>`（**唯一删除闸门**，服务端 fail-closed：真实会话/有 pending·running 人工命令/行 running 一律 409，跨需求 404），调度器只做候选筛选，409/404 视为跳过并计入日志四类计数（候选/删除/跳过 409/跳过 404；看板不可达单列 warn）；`created_at` 解析失败不删（fail-closed）。
- **回收时机与安全闸（#428）**：worktree/分支回收除 done 收尾路径外，还有启动对账与主循环定期巡检（`cleanup_stale_worktrees`，间隔 `REQ_BOARD_STALE_WT_SEC` 默认 300s）——覆盖人工合并、人工置 done 不走调度器收尾的场景（原实现只在启动跑一次，残留会留到下次重启）。回收前逐仓库校验「worktree 无未提交改动」+「dev 分支已合并入主干」，任一不满足即保留现场并告警一次（`state["stale_wt_blocked"]` 同因去重，恢复可回收后清标记）——定期执行不得放大强删风险（人工置 done 但分支未合并时删分支会丢内容）；非 done/dropped/卡不存在的卡一律不碰。
- **内置写工具白名单（#303）**：各角色的内置 Edit/Write 与 fs 写绝对路径仅限三处——各仓库 worktree 目录、产物目录、临时目录（/tmp 与系统 TMPDIR）；写真实仓库主工作区（含软链指向的仓库文件，如 `~/.agents/skills/` 下指向仓库的软链）会被拦截——内置 Edit/Write 事后取消本轮（fs 写为进程代办、可落地前拒绝），目标代码不在 worktree 内时报 need_confirm 等待人工处理。
- **Bash 写主工作区护栏（#336/#344）**：见上文「运维与排障」工具审批条（同一实现，只写细节不重复红线）。

## 流程配置（#419，flows.json + prompts/）

研发流程是**配置数据**，唯一源 = 仓库根 `flows.json`（前置槽位 / 流程 / 节点 / 角色元数据）+ `prompts/<role>.md`（提示词正文，免 JSON 转义、diff 可读）。`acp_shared.load_flow_config()` 启动加载一次：聚合全部错误一次抛出（fail-fast）；消费端自决——board 展示层降级（flows 空 + config_error，页面显示原文标签），**dispatcher 侧 fail-closed 安全停泊**（#430：配置非法时不拉起、不推进、不收尾，仅 `log.error` + 时间线留痕；收尾判据 = 卡上快照当前节点为 `terminal`，不得以「无角色」代替）。无热加载。

- **契约**：`default_flow` + `pre.role`（前置槽位）+ `flows[]`（`id`/`name`/`description`/可选 `enabled`/可选 `color`/`nodes`，节点 = `role` + `node_type` + 可选 `name`）+ `roles.<id>`（`display`/`order`/`artifact`/`prompt_file`/可选 `model`）。内置 3 条流程 quick（快速：dev → 收尾，仅限文案/配置/提示词措辞/单文件样式微调，无代码审查与验收；dev 完成时改动命中高风险范围——调度器模块 `RESTART_TRIGGER_FILES`、项目清单 `high_risk_paths`、`.loop/`——或改动清单采集失败 → `_quick_upgrade` 把快照改写为 standard 并进入代码审查；standard 不可用则转暂缓，不无审查收尾）/ standard（标准：dev → code_review → accept）/ heavy（复杂：tech → tech_review → dev → code_review → accept），`default_flow` = `heavy`（前置环节没产出合法推荐时兜底走「更完整」那条）；退役流程直接删条目（删前冻结历史卡 `flow_name`）。显示名取自 `flows.json` 的 `name`，全站文案（含历史遗留通知）由 `flow_names()` 派生，禁止代码里手写流程名副本。`color`（#428）= 流程档位配色的**语义色名**（枚举 `green`/`indigo`/`fuchsia`/`slate`，缺省 `slate`，禁写 hex）：色值唯一落点在 `static/board.css` 令牌块（词表↔CSS 由 `tests/test_flow_color.py` 双向锁定），经 `/api/meta` 注入前端渲染中间栏流程 chip，未命中（无流程快照/已退役流程/配置降级）= 中性灰。
- **流程软禁用（`enabled: false`）**：定义保留（改回 `true` 即恢复，历史卡展示名照旧），但不进前置推荐目录与 need_confirm 的可选流程列表——模型看不到，也就不会推荐。**存在面不动**：`flows()`/`flow_by_id()`/`flow_ids()` 仍含禁用流程，故存量卡、在途卡、启动回填、`PATCH` 校验全部零变化（禁用只作用于「可选面」`enabled_flows()`/`flow_enabled()`）。模型若仍推荐被禁 id → 与非法 id 同路径**静默兜底** `default_flow` + `flow_fallback` 留痕（文案区分「已禁用 / 不存在」），不转人工。`/api/meta` 照返全部流程 + `enabled` 标记，guide 流程表照列并标「已禁用」。校验：`enabled` 必须布尔（缺省 true）；`default_flow` 必须指向启用流程、至少留一条启用流程，否则加载期报错。
- **`description` = 适用场景判据，只写「什么样的需求用它」**：不写节点形态（跳过/新增哪些环节）与代价高低——形态由 `nodes` 唯一表达（提示词目录行会另拼「节点：…」，guide 有独立的节点序列列），同一事实两处维护必然漂移。判据之间要互斥可判（「需不需要先对齐边界或方案」「是否跨仓库 / 动长驻进程」）。
- **加载期校验（`load_flow_config()` 聚合全部错误一次抛出 `ValueError`）**：顶层/`flows`/`roles` 非空；`default_flow` 必须是已定义 flow id；**`roles` 键集与能力表 `ROLE_CAPABILITIES` 双向一致**（配置里出现能力表没有的角色 = 报错，防拼写错误按能力默认值 fail-open 拉起；能力表角色缺配置条目也报错）；`pre.role` 必须存在且该角色有 `artifact`（防配成 dev/merge_resolve）；flow `id` 非空唯一、`nodes` 非空；flow `color` 命中 `FLOW_COLORS` 词表（缺省 `slate`，非法值报错，禁 hex）；node `node_type ∈ NODE_TYPES`（`human` 本期显式拒绝）；`terminal` 每条流程恰一个且必须为末节点、不得配 role；非 terminal 节点必须有 `role` 且在 `roles` 中；`review` 节点必须有前驱且前驱为 `artifact`/`code`（打回目标可复修）；`artifact`/`review` 节点的角色必须有产物；**同一流程内 role 不得重复**（会话归属键 `role:req_id` 会互相覆盖）；role `order` 唯一整数、`prompt_file` 为仓库内相对路径且文件存在（拒绝绝对路径与 `..` 越界）；`roles.<id>.thinking` 为 #50 已下线字段（旧配置静默忽略、不校验、不进入规范化结果）。
- **单一源拆分**：**能力/安全档位**只在代码 `acp_shared.ROLE_CAPABILITIES`（readonly/bash/artifact_write/cancel_on_redline/manual_mode/tapd_readonly/python_safe）；**展示/内容档位**（display/order/artifact/model/prompt_file）只在配置——能力表不再保留这两类字段，双源漂移由加载期键集校验挡住。`ROLE_MODELS` 退役（模型读 `roles.<id>.model`）；未知角色能力兜底 fail-closed（只读 + Bash 白名单，`python_safe` 显式 False）。新增角色须同时改能力表与 `flows.json`（`roles` 条目 + 节点引用 + `prompts/<role>.md`），键集双向一致由加载期校验强制。
- **前置槽位（1 个共享槽位）**：角色可换（`pre.role`，当前 analysis）。完成契约按槽位判定：本节点产物非空 + `suggested_flow`（流程 id，命中配置即采用；缺失/非法 → `default_flow` 兜底 + 事件留痕 `flow_fallback`，不阻塞）+ `repos`（涉及仓库数组，空数组合法；缺失/非法按收尾校验不通过走既有重试）。`build_prompt` 在卡处于前置阶段（无快照）时追加契约段 `PRE_SLOT_CONTRACT`，不依赖角色模板——换 `pre.role` 后任何角色都会被告知输出要求。`suggested_mode`/`manual_close` 退役（agent 自判需人工直接报 need_confirm）。
- **节点类型语义（`node_type`）**：`artifact`（本节点产物非空 → 进入下一节点）、`code`（有代码变更 → 进入下一节点）、`review`（只读；上游含 `code` 节点时调度器代写 `diff.patch`；产物非空 + `verdict ∈ {pass, reject}` → pass 前进、reject 打回前驱节点复修并 resume 上游会话；打回轮次按评审节点下标累计，超上限转 need_confirm 人工裁决）、`terminal`（调度器动作节点，不拉起 agent）、`human`（本期只预留枚举位，配置出现即加载报错）。
- **terminal 与 merge_resolve**：terminal 是流程末位收尾节点——普通项目合并分支回 main、仅推分支项目（branch_only）只 push f-分支到 origin（由 `projects.json` 的 `branch_only` 决定，旧名 `company` 兼容，与流程定义解耦），成功置 done + 清理 worktree 与分支；冲突拉起 `merge_resolve`（配额 2 轮 / 单轮 15 分钟），耗尽转 need_confirm（分支/worktree 保留）。terminal 触发闭包三个入口：推进链内联（正常路径）、启动扫描（doing/open + 当前节点为 terminal）、主循环兜底——都不拉起 agent，收尾全程卡保持 doing，成功才置 done（防 open+terminal 死锁）。
- **卡上快照与按快照推进**：采纳流程时写 `flow`（id，调度用）+ `flow_name`（名称快照，仅展示）+ `nodes_json`（节点序列快照）+ `node_index`（当前下标，未入流程 NULL）；推进只读快照、不查配置——删流程 / 改名 / 复用 id 均不影响进行中卡与历史卡。快照写入带**回读校验**（未生效 → 事件留痕 + 暂停该卡推进，不重复拉起前置环节，防旧看板静默丢字段）。`role_allowed` 放行角色 = 无快照时 `pre.role`、有快照时当前节点 role（terminal 行不拉起 agent；`merge_resolve` 另有 state 闸门）。
- **存量卡回填（`backfill_flow_snapshots()`，调度器启动执行、幂等）**：仅处理 `nodes_json IS NULL` 且 status ∈ {open, doing, route, review} 的卡——`route` → open（清快照重走前置环节）；`review` → 视为所在节点已通过（按旧 `phase` 定位下标 +1，落到 terminal 的卡由启动扫描直接收尾）；`mode=auto` → `flow=auto` + index 0；`mode=semi` → `flow` 保留或取 `standard`，index = 旧 phase 下标（缺失取 0）；旧 flow id 已不在配置 → `default_flow` + 留痕。进入流程的卡一并冻结 `flow_name`。
- **状态与人工通道收缩**：`STATUSES` 5 值（later/open/doing/done/dropped），调度推进不再写 route（通道待确认）/review（评审中）——两值为历史值，仅历史状态日志回放与过渡窗口照存；人工介入只剩 need_confirm 一条通道（agent 自判 / 评审打回超限 / 合并冲突配额耗尽 / 收尾校验不通过 + `waive_gate` 仲裁；历史 review_gate 条目按过渡窗口消费）。state 键 `pending_route`/`pending_review` 已弃用——新流程不再写入，`on_message` 与 `reconcile_decisions` 保留的历史遗留分支仅兼容过渡窗口照存的历史卡/幽灵 pending；`pending_merge_review` 为 #337/#411 历史键，代码仅保留残留清理点。
- **改配置的生效方式**：无热加载——改 `flows.json`/`prompts/` 后**必须重启两个进程**：看板 `./start.sh`、调度器 `scripts/dispatcher-restart.sh <pid> config-change`。本次合并落 main 时看板由 `_kickstart_board_if_own` 自动重启、调度器由 #380 `pending_restart` 自动重启；此后日常改配置属人工重启，不在自动链路内。

## 角色能力与展示单一源（#339/#419）

- **能力层单一事实源（#339）**：各流水线角色（analysis/proposal/tech/review/accept/dev/merge_resolve 等）的**能力档位**（只读路由/Bash 策略/写白名单/取消红线等）集中声明在 `acp_shared.py` 的 `ROLE_CAPABILITIES`；`_auto_approve` 审批路由、ACPSession 构造参数、收尾校验、`artifact_ok`、`build_prompt` 模板选择均经 `role_capability()` 从中派生。dev_auto/dev_semi 共享 `_DEV_TAIL` 要求正文，改 dev 约束只改 `_DEV_TAIL`。
- **展示层单一源（#419 取代 #403 的多份手写副本）**：角色中文名/顺序/产物/提示词改由 `flows.json` 的 `roles.<id>` 承载——`ROLE_PROMPTS`、`SEMI_PHASES`、`board._AGENT_OVERVIEW` 手写副本退役，`board.ARTIFACT_FILES` 改为配置派生（保留非角色条目 `diff → diff.patch`）；前端经 `GET /api/meta`（状态/流程/节点标签）与 `GET /api/roles`（角色 display/order）注入，无手写映射表。
- **新增角色 = 改两处**：`acp_shared.ROLE_CAPABILITIES`（能力/安全档位）+ `flows.json`（`roles` 条目 + 流程节点引用，并新增其 `prompt_file` 指向的 `prompts/<role>.md`）；未知角色兜底 fail-closed（只读 + Bash 白名单），不配即不放行。一致性由 `tests/test_flow_config.py` 与 `tests/test_role_manifest.py` 锁定（键集与显示名逐键对齐，测试变红即漏同步）。

## ACP 协议契约测试（离线，手写客户端 vs 官方 schema）

- 背景：ACP 客户端是**手写**的（不用 acp SDK），协议面靠约定维持——kimi 0.37.2 新增「Bash 委托客户端执行」（`terminal/*`，upstream#351）就是「上游新增客户端方法、手写端只有真跑起来才发现」的实战教训。
- 做法：官方 `schema/v1/meta.json` 逐字节 vendored 到 `tests/fixtures/acp_meta_v1.json`（sha256 锁在 `scripts/acp_schema_sync.py`），`tests/test_acp_schema_contract.py` 离线校验：我方**实际收发**的方法名（从 `acp_shared.py` 源码提取，不是手抄清单）∈ 官方方法表；「官方有、我方未实现」的客户端方法集合写死为断言——上游新增方法时测试变红，提示评估是否要支持；`initialize` 的 `protocolVersion` 必须等于官方 schema 版本，且必须声明 `clientCapabilities.terminal`（不声明则 kimi 0.37.2+ 禁用 Bash/Grep/Glob）。源码里新增/删除 ACP 方法必须同步该测试的 `EXPECTED_*` / `DEVIATIONS`。
- 漂移检查与刷新：`python3 scripts/acp_schema_sync.py`（联网，对比上游 `main`，列出新增/删除的方法，退出码 1 = 有漂移）；`--ref <tag>` 对比指定版本，`--write` 覆盖 vendored 文件（记得同步脚本里的 sha256 常数）。
- 报文字段级校验（可选，装官方 SDK 才跑，默认 skip）：`python3 -m venv /tmp/acpcheck && /tmp/acpcheck/bin/pip install -q agent-client-protocol && /tmp/acpcheck/bin/python -m unittest discover -s tests -p 'test_acp_schema_contract.py' -t tests` —— 用官方 Pydantic 模型校验真实报文形状（我方出站 + kimi 反向的 `request_permission`/`terminal/*`/`fs/*`/`session_update`）。**不把 SDK 加进仓库依赖**：它还没到 1.0（0.12.1 / 1.0.0rc1），且仓库测试环境刻意保持零第三方依赖。

## review 节点（合并前只读 diff 审查，#419 取代 #337 特判）

含 review 节点的流程（standard 的 code_review、heavy 的 tech_review/code_review）由这一节点类型统一承载：拉起只读 `review` 会话（`READONLY_ROLES` 档位，仅只读 MCP 工具 + 内置写工具拦截 + Bash 只读白名单；#423 起评审角色可跑受限 python 自验——`unittest discover` / `py_compile`，由「机制上不可能执行」变为「护栏 + 受限形态」），对照需求 title/notes + 上游产物 + 代码 diff 审查（范围覆盖/夹带需求外改动/空实现 TODO/删测试改断言/自测与 diff 自洽性）。

- **diff 输入**：只读 MCP `git_diff` 白名单仅 stat 类、reviewer 拿不到范围 diff（Bash 被拒），故由调度器在拉起前用 subprocess 生成三点 diff（`_branch_base` 基线）写产物目录 `diff.patch`；单仓库超 `REVIEW_DIFF_MAX_LINES`（2000）截断并如实标注（reviewer 可用 `git_diff --stat` 定位后 Read 补看）。#384：`code` 节点完成时同样代写 `diff.patch`（相对基线三点 diff），供后续评审/验收节点（#381 前端 diff 视图）读取；无实际 diff（parts 空）不写文件（#383），文件在=有内容。
- **输入注入**：仅当流程中存在位于本评审节点之前的 `code` 节点时才注入 diff（tech_review 无 diff、code_review 有 diff）。
- **产物与留档**：结论产物写角色配置里的 artifact（`code_review` = `code_review.md`，`artifact_ok` 校验）；评审结论另经调度器代写 `req_reviews`（append-only，不进 notes/summary，#342）。
- **出口（verdict 驱动）**：`pass` → 清该评审节点轮次、推进下一节点；`reject` → 打回前驱节点复修（**先回退 `node_index` 再 resume 前驱会话**，否则 #279 角色守卫按当前节点校验会拦截致卡死），打回意见与评审产物全文经 `extra` 注入前驱续跑消息（resume 路径 build_prompt 被丢弃，不注入前驱看不到审查发现；评审结论本身只进 `req_reviews`，不写 summary），轮次键 = 评审节点下标，第 1–3 次拒自动打回重做，第 `FLOW_REVIEW_ROUNDS_MAX`(3) 次拒时作者模型升级为 projects.json 的 `escalation_model`（C3：未配置/不在池/不可用/与作者同模型则不升级并留痕；记录存 `state["review_escalation"]`，spawn_agent 拉起该角色时自动带上，评审通过/人工放行/新周期清除），超过上限转 need_confirm 人工裁决（问题附各轮打回要点，存 `state["review_round_points"]`）（y 放行进入下一节点 / n 打回前驱再修一轮，人工原因同样经 `extra` 注入）；verdict 缺失/非法 fail-closed 按打回处理。会话自身失败（超时/无结果/非法 JSON）→ 通用重试 1 次 → 耗尽转 later + 毒会话，**全程不直通合并**（fail-closed，与全系统一致）。
- **审查发现问题（#419 起）**：`review` 节点 result.json 一律 `status=done` + `verdict`（pass/reject）——发现问题 = `reject` 自动打回上游开发节点复修（见上条「出口（verdict 驱动）」），不转人工三档裁决。评审 agent 自判需要人工（如产物缺失、环境不可用）时才报 `need_confirm`，走普通 confirm 通道（options 按对话类解析）。
- **`review_gate`（#337/#411 历史）**：`kind=review_gate` 三档裁决（飞书 y=确认仍合并 / `n <编号> 转开发`=退开发复修 / 普通 n=否决合并转 later，网页 action 白名单 `pass/rework/reject` 由 `_review_gate_rework` 共用）为历史条目消费路径——#419 起调度器不再新写入该 kind，`on_message`/`reconcile_confirmations`/`reconcile_decisions` 的消费分支仅兼容过渡窗口内已落表的旧条目。
- **角色守卫**：评审节点是普通节点（两条内置流程共用 `code_review`，同一角色、同一提示词、同一产物），`role_allowed` 按快照当前节点放行（#279 防线），原 `pending_merge_review` 门禁特判退役（该键为 #337/#411 历史键，代码仅保留残留清理点）。
- **措辞如实**：LLM reviewer 对删测试/夹带是**概率改进非机制保证**；reviewer 价值不在更聪明，而在没有「证明自己是对的」的动机。
- 普通项目本地合并与仅推分支项目 push f-分支两条 done 收口路径都在 terminal 节点内执行（收尾动作，见「流程配置（#419）」节）。

## 验收节点（accept 验证方式契约，#433）

accept（测试验证）的验证方式为显式契约（唯一载体 `prompts/accept.md`）：按「项目实例脚本能否拉起被测进程」判承载关系——能则在 per-requirement worktree 起独立测试实例（req-board 用 `scripts/test_instance.sh`，`REQ_BOARD_PYTHON` 指主工作区 `.venv/bin/python`；端口 = 段基址 + 需求 id 取模、先 `status` 探测被占则段内顺延）跑真实链路，accept.md「验证方式与证据」小节留痕（实例地址/启动命令/操作步骤/结果/未覆盖项/worktree 状态/`lsof` 清理确认，并以 `git status --porcelain` 为空自证现场）；不能（被测对象是 launchd 单例/自宿主进程、项目无实例脚本、脚本拉起的进程不是被测对象）写明「不可行 + 原因」降级到单元/脚本级验证，人工验收项入 accept.md「未覆盖项」并在 summary 指引；判据不以耗时/成本放松。**accept 不声明 `todos`**（accept 声明的会覆盖 dev 声明的，且其上下文拿不到 dev 待办）——需 done 通知红字展示的人工待办由 dev 声明。改 `prompts/accept.md` 无热加载：重启调度器（`scripts/dispatcher-restart.sh <pid> config-change`）后新拉起的会话才生效。

## 收尾校验内容仲裁（#399，机制不符的 done 豁免出口）

done + 进程正常退出 + 收尾校验失败（dev `has_code_changes` 无变更 / artifact 角色 `artifact_ok` 失败 / 前置槽位 `repos` 缺失或非法）时，原行为走进程失败通道重试→耗尽转 later（#395 教训：实现已人工提交 main 导致 diff 恒空，内容性完成被机制拒绝、被当进程失败重复重试）。#399 引入内容仲裁通道：

- **触发**：四条件同时满足——进程正常退出（rc=0 且未超时）+ status=done + 收尾校验失败 + result.json 带 `waive_gate`（非空字符串，agent 申报豁免理由，如「实现已由人工提交 main」）。
- **分流**：不计 retries、不走失败重试，转 `pending_confirm(kind=confirm_override)` 人工裁决（仲裁等待期间卡保持 doing，主循环既有跳过重捞，人工裁决无时限）。
- **出口**：飞书 y=豁免完成——summary 红字「机制校验未过，人工确认豁免」+ todos 暂存 + `finalize_done` 统一收口（合并/冲突/#380 重启判定照常，不跳过）；n=退 open + 清 retries（按卡上快照的当前节点重跑），原因以 `later` 开头 → 转 later 人工收口（分支/worktree 保留）。
- **fail-closed**：未申报 `waive_gate` = 视为谎报/契约缺失，保持原失败通道（retries+1 → 重试 → 耗尽 later）不变；进程异常（超时/非 0 退出码）不设校验失败原因，天然排除在仲裁外。
- **人工收口（②）**：agent 识别「实现已人工提交 main / 需求为验证记录类」时不再走 `suggested_mode: manual_close`（退役），直接 result.json 报 `need_confirm` 转人工处理（与其它节点同一通道，y=恢复会话继续/n=退回）；识别不出由仲裁兜底。
- **与 blocked 关系**：两类都是「内容性结论不走进程失败通道」——blocked=带原因转 later（无重试）；confirm_override=校验不符但完成结论转人工（y 豁免/n 退回）。彼此独立，无重叠触发。
- #388 重启对账预检不含 waive_gate 放行：重启窗口恰逢仲裁等待时结果不采纳、退 open 重跑一次（窗口极小，明确取舍，不扩散改动面）。

## 仅推分支项目（branch_only，#288）

`projects.json` 项目配置 `"branch_only": true`（旧名 `company: true` 作为兼容别名继续生效）声明该项目为**仅推分支项目**：main 由外部 CI/CD 或人工发版时合并，调度器 done 收尾**不本地合并 main**，而是自动把有改动仓库的 f-分支 push 到 origin（只 push 分支本身、不 `--force`、不推其他 refs），push 失败不阻断 done，事件 + done 通知红字提醒手动 push；该类项目强制走人工确认通道。done 后清理 worktree，**仅保留实际有改动仓库的分支到发版**（未改动仓库的分支与 worktree 一并删除，避免空分支噪音）。普通项目（未配置）走本地合并回主干路径。

## 自动合并冲突自动解决（#396，merge_resolve）

自动合并冲突（terminal 收尾 `finalize_done` 合并失败）先自动拉起 `merge_resolve` 会话解决，失败/耗尽/语义冲突才转人工通道（#386 双确认通道，行为不变）：

- **触发**：`finalize_done` 普通项目（非 branch_only）`merge_dev_branches` 冲突 → `_start_merge_resolve` 登记 `state["merge_resolve"][req_id]`（failed 仓库/attempts 轮数/bin 分支/dev 摘要）并拉起 `merge_resolve` 会话（每次冲突事件一条，`kind=merge`），不立即转人工；#419 起该触发点位于 terminal 收尾节点内（卡保持 doing，成功才置 done）。
- **main 工作区脏现场不算冲突**：合并失败后（仅失败路径）`_merge_dirty_blockers` 判定——无 `MERGE_HEAD`（git 预检拒绝）且 main 工作区未提交/未跟踪文件与 dev 分支改动文件有交集 → 不拉起 merge_resolve（它改 dev 分支，解决不了 main 脏现场），直接转人工通道，summary/事件/确认问题列出挡路文件并提示先提交或 stash；飞书 y / 网页重试仍失败时同样给出文件提示（`_merge_fail_text`）。探测异常按真冲突处理（fail-closed）。
- **能力**（`ROLE_CAPABILITIES` 新档位 `bash="git_merge"`，= #355 需求助手合并授权子集）：Bash 仅放行 `git_cmd_safe(allow_merge=True)` 受限形态（只读子命令 + add/commit + merge/checkout/switch/stash 受限，push/reset/rebase/rm/mv/cherry-pick/任意 shell 拒绝——`_auto_approve` 预检 + `_terminal_approve` 完整命令复核 fail-closed）；内置 Write/Edit 与 fs 写限 `write_roots`（worktree/产物/tmp，主工作区 #303/#336 硬拦不变）。
- **方向**：agent 在 dev 分支 worktree 内 `git merge main`（主干并入 dev）→ 解冲突（Edit/Write）→ `add`/`commit`；耗时上限 15 分钟每轮、最多 2 轮（`MERGE_RESOLVE_MAX_ROUNDS`，独立计数不污染 dev `retries`）。**语义冲突**（业务方向需人工决策）报 need_confirm，禁止强行解决（fail-closed）。
- **收尾**（`handle_result` 完成分支）：调度器先对失败仓库 `git merge --abort` 恢复 main worktree 现场（恢复动作在调度器，不进 agent 权限）→ 重试 `merge_dev_branches` → 成功：cleanup + restart 配方 + `_set_done`（dev 摘要透传 + agent 解决说明留 summary，含 #380 自动重启）；仍冲突/need_confirm/blocked/进程级失败耗尽 → `_merge_conflict_fallback` 转现有 #386 人工通道（pending_confirm kind=merge + 红卡 + 按钮，分支/worktree 保留）。
- **角色守卫**：`role_allowed` 特判——仅 `state["merge_resolve"]` 有登记时放行（spawn/run 两层，防绕过拉起）。会话归属键 `merge_resolve:<id>`，走 #273 毒会话/#374 孤儿清算同框架。

## 自动合并冲突网页决策（#386，对账式）

自动合并冲突（`finalize_done` 合并失败，merge_resolve 未解决/耗尽后）有双确认通道，语义一致、同锁互斥：

- **飞书 y/n**：`on_message` 消费 `state["pending_confirm"]`（kind=merge），y=重试合并、n=人工接管（置 later）。
- **网页按钮**：`finalize_done` 冲突时向看板新表 `merge_conflicts`（req_id PRIMARY KEY, action, updated_at）登记（action=NULL，按钮出现）；卡片/详情页在 `doing + 冲突表命中` 时渲染「重试合并 / 人工接管」按钮，点击 POST `/api/requirements/<id>/merge-conflict` `{action: retry|takeover}`；`reconcile_decisions` 每轮（`POLL_INTERVAL` 15s）经 `api_board GET /api/merge-conflicts` 扫描 action 非空记录，**以 pending_confirm（kind=merge）为权威**在同 `state_lock` 下 pop 消费（与 on_message 互斥，先 pop 者执行）：
  - `retry`：与飞书 y 同逻辑——先 `_touches_dispatcher` 判定，`merge_dev_branches` 成功 → cleanup + restart 配方 + `_set_done`（含 `_kickstart_board_if_own` 与 #380 `_queue_auto_restart`）；仍冲突 → 重挂 pending + 重置按钮（POST action=NULL）等待再次点击，提示继续处理。
  - `takeover`：与飞书 n 同逻辑——置 later、分支/worktree 保留、summary 留痕。
  - 幽灵决策（无 pending，如已由飞书 y/n 并发消费）→ 清表 + 事件留痕。
- **一致性兜底**：以 pending 为权威，表仅渲染信号+决策通道；dispatcher 写表失败不阻断收尾（降级=按钮不可见，飞书通道仍可用），事件/日志留痕；消费/接管/重试失败后均清表或重置，孤儿记录由「无 pending 清表」路径兜底。

## 网页确认通道（#400，渲染数据源读 state + confirm_decisions 对账）

agent 确认裁决（need_confirm/review_gate/confirm_override）双通道，语义一致、同锁互斥（on_message 零改动，对等复刻）：

- **渲染数据源**：board `GET /api/confirmations` 直接读 `data/dispatcher_state.json` 的 `pending_confirm`（`pending_route`/`pending_review` 已弃用——新流程不再写入，仅过渡窗口照存的历史条目仍以 kind=route/review 透出，前端不渲染入口、仅留痕；同 `api_sessions` 读取模式，state 是事实源、零新双存储），联新表 `confirm_decisions`（req_id PRIMARY KEY, kind, action）透出 action——有未消费行 = 已点击待调度器消费（前端按钮「已提交待处理」，跨 15s autoRefresh 不丢态）。
- **双轨制**：动作类点击（click）走 `POST /api/requirements/<id>/confirmations` 写 `confirm_decisions`，调度器 `reconcile_confirmations`（挂主循环，与 reconcile_decisions 同轮）以 pending_confirm 为权威在同 `state_lock` 下 pop 消费（与飞书互斥，先 pop 者执行），执行对等 on_message 对应分支（confirm_override y/n/n+later 与飞书 y/n 等价；历史 review_gate 条目的 y/转开发/n 分支仅过渡窗口消费）；confirm 超限 stop_later 为新增明示出口语义（网页专属，非飞书对等复刻——飞书 n 普通确认=退 open）——不经 agent 会话，守 fail-closed；对话类选项 + 人工输入 = 消息发回 agent 会话（复用 #273 人工续跑通道，人工输入恒对话类，不触发机制动作）。
- **action 白名单**（board 端点与 dispatcher 对等校验）：review_gate→`pass|rework|reject`（三档：仍合并/转开发/转暂缓，#411；rework 经 `_review_gate_rework` 与飞书 `n <id> 转开发` 对等，看板前端当前未渲染该组按钮、实际入口为飞书回复）；confirm_override→`pass|reject|reject_later`；confirm→仅 `stop_later`（超限态明示出口）；merge 首期不走本通道（沿用现有合并冲突卡片按钮）。
- **追问护栏**：`state["confirm_rounds"]` 单调计数（need_confirm 落表 +1，**无任何清零/复位点**，响应不清零）；N ≤ `CONFIRM_ROUNDS_MAX`(5) 通知带「第 N 轮待确认」；N > 5 仍落表 + `entry["over_limit"]=True`（**不自动转 later**，明示出口：飞书 y/n 照常、网页渲染「停止追问转暂缓」按钮），通知/卡片注明已连续第 N 轮。
- **result.json options**（仅 need_confirm 合法）：`[{label, hint}]` 纯对话类声明（label ≤20/hint ≤50/上限 5），未知键（含 action 动作码）丢弃（fail-closed——agent 不能声明机制动作）；review_gate/confirm_override 丢弃 options（按钮由调度器按 kind 生成）；解析失败/非法置空，页面退化 question 全文 + 回复入口。
- **幽灵决策**：confirm_decisions 有 action 但 state 无对应 pending（已由飞书并发消费）→ 清表 + 事件留痕，不执行任何动作；kind 不匹配同按幽灵处理（消费带 kind 校验）。
- **终态清账单点（#25，取代 #407 的 kind 白名单口径）+ 键与内容同源（#27 并存）**：`pending_confirm` 只在事件驱动路径（飞书 y/n、网页 action）消费，人工置 done/dropped 或推进路径完成会绕过消费而永久残留（#388/#380/#383/#302/#24 现场），残留让 done 卡显示「待确认」徽标且裁决按钮仍可点（误 finalize_done/误打 later）。终态收尾统一调用 `_purge_ghost_confirm` 单点：清同需求 `pending_confirm` **任意 kind**（含普通 confirm/confirm_override）、`pending_merge_review`（#337/#411 历史键）、`confirm_decisions` 全部决策行与 merge 冲突表行，事件留痕——`terminal=True` 仅由 `_set_done` 在 `set_status(done)` 成功后传入（不依赖置 done 前旧快照）；`terminal=False` 一律现取 `fetch_req` 最新状态裁决，回读异常/缺卡/缺 status/非终态均 no-op（不误清 #394 保护范围）。清理入口三处：`_set_done` 收尾、启动对账 `reconcile_ghost_pending`（扫 done/dropped 卡，覆盖人工置终态）、`reconcile_confirmations` 执行 action 前发现终态卡时走同一 helper 后跳过 action（防残留 reject/stop_later 把终态卡改回 open/later）。非终态卡任意 kind 逐字保留（**#394 红线按卡状态豁免**，非按 kind 豁免）；`reconcile_decisions`/`reconcile_confirmations` 相对顺序不变、不新增第二套终态守卫，pending 消费与清理同 `state_lock` 互斥（先 pop 者执行）。**与 #27 身份守卫共存**：`_purge_ghost_confirm` 清账前按「条目内容卡 id == 本卡 id」判身份，不同源（内容属别的卡）则不清、返回 False 由调用方留痕转人工；启动对账 `reconcile_ghost_pending` 判据改为内容 id 权威（`_pending_content_req_id`），键与内容不同源时不按键误清。
- **键与内容同源（#27）**：`pending_confirm` 条目的「键」必须等于「条目内容卡 id」——内容卡 id（`entry["req"]["id"]`）是身份权威，键服从内容；卡是否终态一律 `fetch_req` 现取，不用条目内快照的 `status`。三层闸门：**写入期**唯一落表出口 `_put_pending_confirm`（裁剪 req 快照为七键 `id/title/project/status/flow/flow_name/node_index`，去卡片对象别名）+ 回读校验，键与内容不一致即 `log.error` + 时间线留痕（不静默）；**启动期** `reconcile_pending_confirm_source()`（**必须先于** `reconcile_ghost_pending`——后者按键判终态并 pop）按键修正（目标键已占用则保留原键 + 告警，不覆盖在途条目）、内容卡现取终态（done/dropped）则清条目 + 留痕；`reconcile_ghost_pending`/`_purge_ghost_confirm` 判据一并改为内容 id 权威（`_purge_ghost_confirm` 仅加身份守卫，kind 白名单与 `_set_done` 调用时机一字不改）；**消费期**三处消费点（飞书 y/n、网页确认动作、网页 merge 决策）锁内纯判定「命中不 pop」，出锁后 `_pending_rehang` 按内容归属归位/清理（目标键被占则保留原键并累计 `src_conflict_hits`，≥3 次清条目转人工，通知带问题全文与正确编号）——全程不改动任何卡的状态。**#394 边界**：启动期新函数对「内容卡现取终态」的清理**不限 kind**（有意覆盖，条目挂终态卡时任何编号的 y/n 都必然作用在错卡上，清理不丢问题全文），范围仅限「内容 id 权威 + 现取终态 + 启动期」这一组合，两条老清理路径的白名单红线继续 100% 生效。**兼容**：条目 `req` 缺失/非 dict、条目本身非 dict、`fetch_req` 不可达一律 fail-open（不判定、不清理、不抛）；`confirm_rounds` 归位/清理**一律不搬运**（错源两键分属两张卡，搬运会虚高）。历史错键条目在调度器重启后由启动对账修正/清理，人工可在需求时间线看到留痕。

## 可插拔通知渠道（notifiers/：飞书 / Webhook / Slack）

出站通知统一经 `notifiers.NotifierRegistry`（调度器内单例 `NOTIFIERS`）扇出，渠道接口 = `Notifier.deliver(NotifyEvent)`：

- **入口不变**：`notify(text)`（缺省 chat_id）→ `NOTIFIERS.send_text`（事件名 `message`）；`notify_req_card(event, req, **kw)` → `NOTIFIERS.send_event`（`need_confirm` / `done` / `failed` / `blocked` / `merge_conflict`，历史 `route` / `review`）。`notify(text, chat_id=...)`（飞书会话内回复）只回飞书，不进注册表。
- **飞书**＝同步渠道 `notifiers.feishu.FeishuNotifier`，回调 `_feishu_notify_text` / `_feishu_notify_req_card`，发送逻辑、降级文本、异常传播与接入前逐字一致；凭据仍读 `feishu.json`。入站 y/n、看板助手、建卡会话仍是 `on_message` 专属；`on_message` 处理期间（`NOTIFIERS.inbound_scope()`）的缺省 `notify` 回执只回飞书，不扇出到 Webhook/Slack。
- **Webhook / Slack**＝配置驱动的异步渠道：每渠道一个后台线程 + 有界队列（200 条，满了丢新消息并告警），**绝不阻塞调度主循环**；发送失败只记日志（不重试）。日志只记渠道名、事件名与 HTTP 状态码/异常类型，不记 URL 与密钥。
- **配置**：`notifiers.json`（0600，gitignore；路径口径 `notifiers.config_path`：`REQ_BOARD_NOTIFIERS_JSON` → 与 `feishu.json` 同目录 → 仓库根），设置抽屉「通知渠道」tab 读写。每次发送前按文件 mtime/size 检查并自动重载——**保存即生效、无需重启调度器**。
  ```json
  {
    "board_url": "https://board.example.com",
    "channels": {
      "webhook": {"enabled": true, "url": "https://example.com/hook", "secret": "…", "timeout": 5,
                  "events": ["need_confirm", "done", "failed", "blocked", "merge_conflict", "message"]},
      "slack": {"enabled": true, "webhook_url": "https://hooks.slack.com/services/…", "timeout": 5}
    }
  }
  ```
  `events` 缺省 = 全部；`timeout` 缺省 5 秒、上限 30；`board_url` 缺省由 `REQ_BOARD_API` 派生（`http://127.0.0.1:8899`），卡片链接 = `<board_url>/?req=<id>`（看板首页识别 `req` 参数直接定位该卡）。
- **fail-closed**：文件损坏/顶层非对象 → Webhook/Slack 全部停用；单渠道字段非法（URL 非 http(s)、Slack 非 https、未知事件、启用但无地址等）→ 只停用该渠道；均 `log.warning` 留痕，绝不抛到调用方。
- **Webhook 请求体**：`{source:"loop-engine", schema:1, event, title, text, requirement:{id,title,project,status,url}|null, details, sent_at}`；配置 `secret` 时附 `X-Loop-Timestamp` 与 `X-Loop-Signature: sha256=<hex(HMAC_SHA256(secret, "<timestamp>." + 原始请求体))>`，另恒带 `X-Loop-Event`。
- **Slack**：Incoming Webhook + Block Kit（header 事件标题、section 卡片链接 + 正文、context 项目/状态、「在看板中打开」按钮）；webhook URL 按密钥对待。

## 飞书交互细节

机器人走 WebSocket 长连接（无需公网）。首次使用需在飞书里私聊机器人任意发一条消息建立会话；agent 报 need_confirm 时会推送问题，回复 `y <编号>` 同意、`n <编号> <原因>` 否决。#419 起 y/n 通道只剩 need_confirm 一类：普通提问 y=答复并 resume 恢复会话、n=退回 open；代码审查发现问题（review_gate）三档——y=确认仍合并、`n <编号> 转开发 [原因]`=退开发复修、普通 n=否决合并转 later；评审打回超限的人工裁决 y=放行进入下一节点、n=打回前驱再修一轮（轮次键 = 评审节点下标，上限 `FLOW_REVIEW_ROUNDS_MAX`=3，第 3 轮升级作者模型（配了 escalation_model 时），第 4 轮转人工）；合并冲突 y=重试合并、n=人工接管（置 later）；前置槽位流程确认 y=采纳推荐流程、n=转人工。历史遗留：原「route 通道确认」（含 `y <编号> standard|lean|heavy` 流程指令）与「review 评审通过/否决」两条分支已随中间态取消（新流程不再产生），`on_message` 仅保留消费过渡窗口照存条目的兼容分支。关键状态通知（需要确认/开发完成/自动开发失败/合并冲突等）为 interactive 卡片（颜色语义：橙/绿/红/红），普通回执类通知保持文本；卡片发送失败自动降级为对应文本，回复指令格式不变。**凭据源（#22）**：飞书凭据唯一源 = 仓库根 `feishu.json`（`{"app_id","app_secret"}`，0600，gitignore）——看板侧经设置抽屉「通知渠道」tab 的「飞书机器人」小节读写与连通性测试，调度器**仅在启动时读取一次**，**改凭据后需重启调度器**（`scripts/dispatcher-restart.sh <pid> config-change`）。旧的 `.env` 两键（`FEISHU_BOT_APP_ID/SECRET`）已删除且不再读取；`.env` 缺失凭据时脚本不再自动设 `REQ_BOARD_NO_FEISHU=1`——改为调度器启动时自行降级（`init_feishu()` 返回 None → 跳过 ws 线程 + 日志留痕，**不再崩溃**），显式 `REQ_BOARD_NO_FEISHU=1` 仍尊重。**群聊 @ 消息（#22 行为变化 2）**：`chat_type != 'p2p'` 的**文本**消息只路由到看板助手（回复按群 `chat_id` 显式发回该群），**不写** `state["chat_id"]`（私聊通知通道保持唯一）、不问候、不走 y/n 与建卡链路；群聊素材与非文本消息仍忽略。前提：应用只订阅「群组中@机器人消息」事件（未开 `im:message.group_msg`），能收到的群消息必然 @ 了机器人。

**改动 on_message 的 y/n 回复处理逻辑时，必须同步更新 `docs/guide.html` 的「飞书回复与状态流转」表与回复格式说明。**

## 建卡对话流程（#107，聊天建卡页 = agent 会话框）

左侧项目行右侧的 `+` 进入对应项目的「聊天建卡」页（项目已绑定，无下拉框），由 board 进程内直接起 `kimi acp` 子进程（共享模块 `acp_shared.py` 的 ACPSession，事件注入写 `chat_events` 表），不走调度器轮询。一个会话绑定一个项目，每项目最多 1 个活跃会话；切换项目不中断其它项目正在跑的一轮（后台继续跑完），全站最多 3 个项目的会话并行 running（超出返回 429），空闲会话切走后回收进程、切回自动恢复；回合制：用户发一条 → kimi 完整跑一轮 → 页面轮询展示，下一轮 `session/resume` 续上下文；board 重启后残留 running 会话标 interrupted，页面可一键继续（省配额）。agent 产出 ```draft 草稿块（JSON 或 title:/notes: 键值）→ 页面预览 → 用户确认 → agent 调 create_requirement 建卡（默认 later，接入自动开发的项目不会被误捞）。安全边界（读写白名单、mysql 凭据隔离）见 AGENTS.md。

建卡对话的创建、挂起、恢复、服务重启等生命周期事件继续写入 `chat_events` 供排障，但不在聊天消息区渲染；当前阶段由输入框上方的状态行覆盖展示（#430 起是与会话页面同款的**状态卡片**：五档配色 + 状态图标 + 计时 + 可展开判定依据，主按钮恒为「发送」，「取消本轮」在卡片动作位；创建/恢复/建卡阶段与已建卡状态不显示输入区）。失败、超时、异常、取消等需用户关注的 system 事件仍在消息区保留。

## 飞书多轮聊天建卡（#22）

飞书长连接仍只由调度器持有（`lark.ws.Client`）；调度器经看板 HTTP API 起/驱动 `channel='feishu'` 的建卡会话，复用 #107 全链路（系统提示词、`create_requirement` 唯一写工具、材料目录、10 分钟轮次超时与恢复、`chat_events` 落库、SSE poke），**不新增 agent 驱动面**。

- **链路**：飞书消息 → `on_message`（解析 + 入队，秒回不阻塞 ws 回调线程）→ per-chat worker 串行 → 项目解析（按 `projects.json` 项目名整词匹配；未命中则追问并列出项目名 + 括号目录名，连续 2 次不合法提示清单并清 pending）→ 素材**按句柄延迟下载**（`state["feishu_chats"]` 只存下载句柄，**素材字节永不进 `dispatcher_state.json`**）→ 落素材/抓正文（docx `raw_content`、wiki 两步 `Space.get_node`（仅解析一层，非 docx 类型降级）、普通 `http(s)` 链接 `_fetch_link_text`，每步失败降级为仅传原链接 + 提示）→ **等会话 idle** → `POST /api/chat/<id>/prompt` → 轮询至本轮结束 → agent 文本 `send_text_chunked` 发回飞书（>2000 字分段，末条提示「剩余内容见看板」）。
- **首轮 boot 等待（#22，打回主因）**：`POST /api/chat` 返回 201 时会话即 `status='running'`，`_chat_boot` 异步进行；建会话后**必须先轮询 `GET /api/chat/<id>` 至 `status='idle'` 再回放前置对话 + 发首轮 prompt**（间隔 1s，上限 `FEISHU_BOOT_WAIT_SEC` 默认 180s）。任何 409（「会话正在运行，请等待本轮结束」，含 boot 窗口）统一按「等到 idle 再发」处置——不静默、不重复投递、**不引入固定次数重试**；boot 超时/转 failed → 飞书提示「启动超时/失败，回复任意消息重试」+ 保留 session_id。
- **pre-prompt 状态对账（#22）**：发 prompt 前 `GET /api/chat/<id>`——`idle`/`interrupted` 直接发；`running` 等到 idle；`closed`/`failed`/`created`/`suspended` 清本地状态 + 飞书回「会话已结束/不可用，回复『新建建卡』开始新会话」（`created` 另提示看板卡号）。
- **素材白名单同源分流（#22）**：`channel` 同时决定**上传侧与 prompt 复核侧**白名单——飞书会话用图片/文档白名单 `FEISHU_MATERIAL_EXTS` + 单文件 ≤20MB、单轮 ≤5（网页侧仍 `.html/.htm` + 10MB，逐字不变）；prompt 复核侧 `_chat_material_paths` 按会话行 channel 取白名单，杜绝「落盘成功但 /prompt 400」的断链。`over_read_limit`（超 agent 单文件读取上限 1MB）**只提示不阻断**，由调度器转飞书提示 + system 事件。
- **释放路径三档（#22）**：① 飞书侧文本指令「结束建卡 / 新建建卡」（**匹配规则 = 文本 `strip()` 后循环去首尾空白与中英文标点直至不变，再整行全等**，不做包含/前缀匹配，且**仅在存在活跃建卡会话时判定**——讨论原话如「那就确认建卡，结束建卡流程」不误触发）；② 看板「飞书建卡」视图唯一写动作位「关闭会话」（二次确认）；③ dispatcher 主循环 idle 过期兜底（`_feishu_expire_idle_chats`，默认 24h，`REQ_BOARD_FEISHU_CHAT_IDLE_SEC=0` 关闭）。任一生效即释放该项目 `(project,'feishu')` 名额。
- **确认建卡（#22，用户侧唯一落卡口令）**：`确认建卡` 指令（`FEISHU_CMD_CONFIRM`，匹配规则同上述两条）；每轮结束读会话行，`draft_title` 非空且未提示过即回「草稿已就绪：<标题>。回复『确认建卡』落卡；回复其它内容继续讨论」；`_feishu_confirm` 调 `POST /api/chat/<id>/confirm` 驱动 `create_requirement` 建卡（status 默认 later）后经 `_feishu_await_round` 把建卡结果回发飞书。尚无草稿 → 只回提示、不调 confirm；`status='created'` → 回已有的卡号。
- **前置对话回放（`POST /api/chat/<id>/feishu-events`）**：只承载①会话创建前的飞书对话（机器人追问项目、用户选择，带 `[飞书]` 方向前缀）②**仅 dispatcher 侧产生的**辅助提示（下载失败、上传失败、超限、文档类型降级/抓取失败，`kind=system`）；**不回放**用户原始需求（由首轮 `/prompt` 落唯一一条 user 事件）与建卡成功事件（board 侧已写 system 事件，避免重复）。

## 飞书看板助手（#24，跨项目自然语言查询/建卡）

飞书私聊的普通文本（非 y/n、非素材、非建卡指令）由跨项目常驻「看板助手」接管：可用自然语言查项目/需求卡/服务状态，也可先确认项目再跨项目建卡。**与单项目建卡会话完全分离、与会话注册表体系（`agent_sessions`/`agent_events`）也分离**——助手会话与事件落 board 侧独立表（见 `docs/data-model.md`），本节的 dispatcher 侧只做编排（经 `/api/assistant/*` 与看板交互）。

- **路由优先序（`on_message`，从高到低）**：非 `text/file/image` 忽略 → 非私聊群聊：@ 文本 → 看板助手（不写 `state["chat_id"]`、不问候、不走 y/n 与建卡）→ `file/image` 素材分支（#44：**无活跃旧建卡会话**时下载后交给看板助手（`_feishu_material_to_assistant`，payload 带 `message_id`），**有活跃旧建卡会话**时白名单与前置回放逐字不变地进旧 pending 链路）→ **首条问候**（同 chat 只问候一次；#24 去掉原 `return`，问候后**继续处理本条**的 y/n、素材与文本路由，改由独立「已问候 chat 集合」`state["feishu_greeted"]` 保证一次）→ 文本 y/n 确认（语义逐字不变，仍是文本最高优先级）→ `_feishu_route_text`：**有活跃旧建卡会话**（`state["feishu_chats"][chat_id]` 命中）则三条指令与所有文本走旧链路；**无活跃旧会话**时只有**整行精确规范化命令「新建建卡」**走旧建卡新建分支（`_feishu_start_build`）；无活跃会话的「结束建卡」「确认建卡」**只回状态提示、不启动任何会话**；其余普通文本 `_feishu_enqueue(..., {"kind": "assistant"})` 进入助手。**原 `_feishu_route_text` 的「无活跃会话默认新建单项目建卡会话」兜底分支已删除**（普通文本不再由旧路由新建单项目建卡）。
- **「正在输入」反馈（#44 Typing 表情）**：飞书无原生 typing 接口，改用**用户消息上的 Typing 表情**（`_feishu_typing`：`CreateMessageReaction` / `DeleteMessageReaction`，可选依赖 `lark_oapi`；未安装时飞书通道整体停用、等同 `REQ_BOARD_NO_FEISHU=1`）。只对**真正入队处理**的三类 payload（`assistant` / `legacy_text` / `material`）贴：`_feishu_worker` 处理前 create、`finally` 撤（create 失败/无 `reaction_id` 则不撤，只 `log.info`，**不做开关/熔断/保活重贴**）；close/confirm/new 与一切未入队的提示（y/n、无会话提示）不贴。表情在用户消息上，可能收到「机器人回应了你的消息」；应用需 `im:message.reactions:write_only`（或 `im:message`），未开通时无表情、业务不受影响。`message_id` 只在队列 payload 里短暂存在，不写 `_feishu_save()` 持久化结构（worker 重启不恢复表情）。
- **消息幂等与串行**：去重键 = `feishu_chat_id` + `message_id`（`state["feishu_seen"]` 近期窗口，覆盖 y/n、素材和助手文本），同一 message_id 只处理一次；`_feishu_worker` 仍按 chat 串行、不同 chat 不共享上下文。
- **助手会话与状态**：`state["feishu_assistant"][chat_id]` 只存编排元数据（`session_id` / `feishu_chat_id` / `last_event_id` / `pending` / `awaiting_project` / `turn_id` / `updated_at`），**不存会话原文与素材字节**，与 `state["feishu_chats"]`（单项目建卡）完全分离。编排走 `_feishu_assistant_*` 系列：`_feishu_assistant_ensure_session` 按 `feishu_chat_id` 幂等 get-or-create 会话（带解析后的 `assistant_model`，未配置传 `None` 时由 board 回落到全局默认模型 `ACP_MODEL`）→ `_feishu_assistant_submit` 提交一轮 prompt → `_feishu_await_round_assistant` 轮询状态/事件、只把 `kind='message'` 的助手正文回发飞书（`kind='agent'` 是回放事件不回发）。**不复用**建卡的 `_chat_boot`/`_chat_prompt_thread`/`_start_chat_round` 与 `CHAT_TIMEOUT`(600s) 语义。
- **素材进助手（#44）**：文本路径与素材路径共用同一编排 `_feishu_assistant_round(chat_id, text, attachments=None, prepare=None)`（90s deadline → pending cancel → ensure_session → 提交 → 收尾，409 栅栏重试只重发同一轮）；素材路径的 `prepare` 在会话就绪后、提交前下载（`_feishu_download_resource` 复用旧链路），扩展名不在 `_FEISHU_MATERIAL_EXTS`、下载失败、单文件 >20MB 一律只回复原因、**不发起本轮**；字节只存局部变量与本次请求体（`{name, content_b64}`），不写 `state`。无文字时文本用「（上传了图片）」/「（上传了文件）」；一条素材消息一轮提交（单轮 ≤5 的批量上限只在 board 端点契约层兜底）。
- **90 秒超时与 cancel**：worker 起表跨 boot 的 90 秒总 deadline（`FEISHU_ASSISTANT_DEADLINE_SEC`，可经 env 覆盖），每次调 `/api/assistant/*` 把剩余秒数传给 board——**权威计时在 board 助手轮次**（`_assistant_boot`/`_assistant_prompt_thread` 共享同一剩余预算），dispatcher 只做超时兜底：deadline 到点且 board 未收尾 → 调 `POST /api/assistant/sessions/<id>/cancel`（带 `feishu_chat_id` + `turn_id`，board 锁内置 `cancelling`、`session.cancel()` 并关进程、保留 ACP `session_id` 供下次 resume）并回固定文案一次（`FEISHU_ASSISTANT_TIMEOUT_TEXT`）；晚到输出不再回发。cancel 期间的短暂 409 由 `_feishu_assistant_wait_resumable` 按状态栅栏等到 `idle`/`interrupted` 再重试提交，新消息不被 409 永久挡住。
- **启动对账**：`_feishu_assistant_reconcile()`（`init_feishu` 内调用）按 `chat_id` 读持久化的 `state["feishu_assistant"]` 与 board 助手表对账——僵尸 `running`/`cancelling` 取消本轮并**保留 `session_id` 供下次续跑**，终态 `closed`/`failed` 清本地条目；看板不可达保持原状。
- **assistant_model 读取**：`init_feishu` 启动时 `_read_feishu_assistant_model()` 只取 `feishu.json` 的 `assistant_model`（`app_secret` 明文不离开该函数），`_feishu_assistant_model_resolve()` 按与角色模型同一别名池口径（`model_alias_pool`/`model_alias_usable`）静态校验，缺失/非法值 fail-soft 回落全局默认并 `log.warning` 留痕；创建助手会话时把解析值经 `model=` 真实传给 board。**改 `assistant_model` 无热加载**——由用户在设置抽屉确认后走 `POST /api/feishu-settings/restart` 生效，不静默重启。
